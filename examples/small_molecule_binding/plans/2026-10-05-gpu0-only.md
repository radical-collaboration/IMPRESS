# Every GPU tool runs on GPU 0; GPUs 1–3 sit idle

**Severity:** high (3 of 4 GPUs per node unused) · **Status:** open, diagnosed, no fix implemented
**Evidence:** telemetry `ResourceUpdate` per-GPU samples from merge-gate job `22684833` (2 × A40x4: gpub082 primary, gpub084); `/proc` env samples from `22669434`

## Symptom

Mean `gpu_percent` per GPU over the whole 1-hour run of `22684833`:

| Node | GPU 0 | GPU 1 | GPU 2 | GPU 3 |
|---|---|---|---|---|
| gpub082 (primary) | **51.8%** | 0.0% | 0.0% | 0.0% |
| gpub084 | **45.3%** | 0.0% | 0.0% | 0.0% |

GPUs 1–3 never registered a single busy sample.

Every earlier campaign reported a per-node "mean GPU" of about 10–15% (for example 9.8–14.7% on `22675825`, and 11.1% at the start of `22534628`). That figure is one busy GPU averaged over four, not four lightly used GPUs.

## Cause

- **No GPU assignment from Dragon.** rhapsody's `DragonExecutionBackend` builds process-mode tasks as `ProcessTemplate(target, args=...)` with no `policy`. Dragon therefore assigns no `gpu_affinity` and sets no `CUDA_VISIBLE_DEVICES` restriction.
- **Every tool sees all four GPUs.** Sampling `/proc/<pid>/environ` on `22669434` showed every tool process with `CUDA_VISIBLE_DEVICES=0,1,2,3`.
- **Each tool picks the first device.** rfd3, boltz (`--devices 1`) and LigandMPNN (`torch.device("cuda")`) each take the first visible device, so all of them land on GPU 0.
- This example deliberately does no pinning of its own; see CLAUDE.md "Execution backends". The pinning that existed (`_gpu_env()`, `CUDA_VISIBLE_DEVICES`) was removed in `dafbbf5` / `825018c` as "the backend's responsibility". The backend doesn't do it.

## Impact

- With 4 pipelines per node, up to 4 GPU tools at once contend for one A40 while three idle.
- Throughput figures so far (11.46 baseline; ~13 rfd3/pipeline/h in the 1-hour runs) were all measured under this contention. They are not a hardware ceiling.

## Candidate fix (not implemented)

Assign each GPU task a device through the backend's own per-task mechanism, the same place the thread caps live (`_tool_task_description`):

- **Dragon (preferred):** add `policy=Policy(gpu_affinity=[g])` to `process_template` for rfd3, boltz and mpnn.
  - Dragon local services then set the accelerator env var for the process (`dragon/localservices/server.py`, `props.layout.accelerator_env`).
  - Pick `g` per pipeline, e.g. `pipeline_index % gpus_per_node`. Dragon places tasks on nodes itself, so two pipelines can still collide on one node's GPU. That is better than all four always colliding.
- **Simpler, backend-agnostic:** add `CUDA_VISIBLE_DEVICES=<g>` to the per-task env delta. The trade-offs are the same and nothing Dragon-specific is needed.
- **Proper fix:** rhapsody/Dragon should allocate GPUs as a resource, with a task requesting 1 GPU and being placed on a free one. Worth raising upstream alongside `plans/upstream/dragon-batch-idle-spin.md`.

**Verify any fix:**
- Per-GPU `ResourceUpdate` means all non-zero on every node.
- `/proc` samples show distinct `CUDA_VISIBLE_DEVICES` per tool process.
- No rise in `TaskFailed` (e.g. GPU OOM from co-located tools).
