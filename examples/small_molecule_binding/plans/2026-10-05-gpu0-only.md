# Every GPU tool runs on GPU 0; GPUs 1–3 sit idle

**Severity:** high (3 of 4 GPUs per node unused) · **Status:** fixed and verified on Delta (`22692293`): all 8 GPUs used, 0 failures, +18% rfd3 / +28% boltz in 1 h
**Evidence:** telemetry `ResourceUpdate` per-GPU samples from merge-gate job `22684833` (2 × A40x4: gpub082 primary, gpub084); `/proc` env samples from `22669434`

## Symptom

Mean `gpu_percent` per GPU over the whole 1-hour run of `22684833`:

| Node | GPU 0 | GPU 1 | GPU 2 | GPU 3 |
|---|---|---|---|---|
| gpub082 (primary) | **51.8%** | 0.0% | 0.0% | 0.0% |
| gpub084 | **45.3%** | 0.0% | 0.0% | 0.0% |

GPUs 1–3 never registered a single busy sample.

Every earlier campaign reported a per-node "mean GPU" of about 10–15% (for example 9.8–14.7% on `22675825`, and 11.1% at the start of `22534628`). That figure is one busy GPU averaged over four, not four lightly used GPUs.

## Cause (confirmed in the installed source, dragonhpc 0.14.1 / rhapsody 0.5.0)

1. rhapsody `backends/execution/dragon.py` builds each task as `ProcessTemplate(target, **process_template)`. We sent only `env`, so there was no `policy`.
2. Dragon Batch launches every process task as its own `ProcessGroup` (`workflows/batch/batch.py`, `JobCore` launch). It uses `template.policy or Policy()` and only adds `HOST_NAME` placement for the node it chose.
3. `globalservices/policy_eval.py` `_get_gpu_affinity`: **an empty `gpu_affinity` resolves to every device on the node.**
4. `localservices/server.py` `PopenProps` writes that list into `CUDA_VISIBLE_DEVICES` (`0,1,2,3`). This matches the `/proc/<pid>/environ` samples from `22669434`.
5. rfd3, boltz (`--devices 1`) and LigandMPNN (`torch.device("cuda")`) each take the first visible device, so every one of them lands on GPU 0.
6. Batch has no GPU accounting. Even its own pool workers pick a GPU with `random.randint` (`Manager.__setstate__`).

This example deliberately does no pinning of its own; see CLAUDE.md "Execution backends". The pinning that existed (`_gpu_env()`, `CUDA_VISIBLE_DEVICES`) was removed in `dafbbf5` / `825018c` as "the backend's responsibility". The backend doesn't do it, so the fix below has the app ask for a device through the backend's own per-task interface.

## Impact

- With 4 pipelines per node, up to 4 GPU tools at once contend for one A40 while three idle.
- Throughput figures so far (11.46 baseline; ~13 rfd3/pipeline/h in the 1-hour runs) were all measured under this contention. They are not a hardware ceiling.

## Fix (implemented)

Each pipeline is given one GPU, round-robin. Its GPU tasks ask the backend for that device.

- **`run_small_molecule_binding.py`:**
  - `_node_gpus()` reads the device IDs from Dragon's node descriptor (`dragon.native.machine`). Off Dragon it uses `CUDA_VISIBLE_DEVICES` or `torch`.
  - Pipeline `pN` gets `gpu_index = gpus[(N-1) % len(gpus)]`.
  - The mapping is logged as a `[GPU]` line at startup.
- **`small_molecule_binding.py` `_tool_task_description(threads, gpu=True)`**, used by mpnn, rfd3 and boltz:
  - on Dragon, adds `process_template["policy"] = Policy(gpu_affinity=[gpu_index])`;
  - on `ConcurrentExecutionBackend`, adds `CUDA_VISIBLE_DEVICES=<gpu_index>` to the env;
  - Rosetta stages are unchanged.
- **Why `policy` and not `CUDA_VISIBLE_DEVICES` under Dragon:** local services merges the template env first and then applies the policy layout's accelerator variable. A policy without `gpu_affinity` resolves to all GPUs, so an env-only `CUDA_VISIBLE_DEVICES` is always overwritten. The earlier "simpler, backend-agnostic" candidate here was wrong.
- **What it does not guarantee:** Batch still picks the node. Each pipeline runs its stages one at a time, so it has at most one GPU task in flight. Two pipelines with the same device number can still share a GPU if Batch puts them on one node at once.
  - Pinning node as well was considered and declined, to leave placement to the backend.
  - The proper fix is GPU accounting in Batch; see `upstream/dragon-batch-no-gpu-accounting.md`.

**Offline checks (passed):**
- for p1–p8, the Dragon description carries `Policy(gpu_affinity=[(N-1)%4])`, which survives Batch's `copy.copy` and `Policy.merge`;
- the Concurrent description carries `CUDA_VISIBLE_DEVICES`;
- Rosetta stages carry neither;
- `gpu_index=None` sends no request.

**Delta verification: `22692293`** (2 × A40x4, gpub002 + gpub084; 8 pipelines; `gpuA40x4-interactive`; `TIMEOUT` 01:00:01 as planned)

- **Mechanism works.**
  - `/proc` samples on both nodes: every rfd3, mpnn and boltz process saw a single device (`CUDA_VISIBLE_DEVICES=0`, `1`, `2` or `3`), never `0,1,2,3`.
  - The startup `[GPU]` line showed p1:0 … p8:3.
- **First-wave collision, then mixing.**
  - In the first rfd3 wave, Batch put every odd pipeline on gpub084 and every even one on gpub002. With `(N-1) % 4` that left each node using 2 GPUs, with 2 rfd3 per GPU.
  - By the second minute the stages had desynchronised and placement mixed. Sampled every 2 min, nodes typically ran 3–4 tools on distinct GPUs, with occasional sharing (e.g. p2 and p6 both on GPU 1 of gpub002).
  - A `((N-1) // nodes) % gpus` mapping would remove only that first-wave collision, so it was not adopted.
- **Per-GPU mean `gpu_percent` over the hour** (`22684833`: GPU 0 at 51.8% / 45.3%, the rest 0%):

  | Node | GPU 0 | GPU 1 | GPU 2 | GPU 3 |
  |---|---|---|---|---|
  | gpub002 | 14.8% | 14.3% | 10.3% | 11.6% |
  | gpub084 | 10.7% | 8.1% | 9.9% | 11.5% |

  Every GPU is used. Each node's **sum** (51% / 40%) is about what GPU 0 alone carried before, so the GPUs are now far from saturated. The remaining limit is not GPU capacity: each pipeline is a serial state machine, and a GPU tool is only one of its stages.
- **Throughput vs `22684833`** (same 2 nodes / 8 pipelines / 1 h, from `/work/nvme`):

  | Stage | Completed (before → after) | Median duration (before → after) |
  |---|---|---|
  | rfd3 | 99 → **117** (+18%) | 93.8 → **74.3 s** (−21%) |
  | boltz | 29 → **37** (+28%) | 51.5 → 47.8 s |
  | mpnn | 357 → 394 | 12.6 → 11.1 s |
  | fastrelax | 82 → 110 | 121.8 → 105.4 s |

  - CPU stages also sped up (fastrelax −13%), consistent with less GPU-side queueing per pipeline.
- **Failures:** 0 `TaskFailed`, 0 tracebacks, 0 CUDA OOM.
- **Folds passed:** 33/37 (89%) vs 27/29 (93%), within noise at these counts.
- **Lost first attempt, `22692267`.** It crashed at startup: `gpu_index` was assigned after `super().__init__()`, which registers the tasks. Fixed by assigning it first. The offline check had called `_tool_task_description` on a stub, so it never ran the constructor. A second check now builds real pipelines on a real `WorkflowEngine`.
  - Slurm recorded that crash as `COMPLETED`, because `dragon -w ssh` exits 0 even when the runner raises (BACKLOG 12; fixed).
