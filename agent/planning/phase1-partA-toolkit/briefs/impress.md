# IMPRESS

**One-line identity.** The async adaptive-pipeline framework this project's own coarse-grained composite pipelines are built on — a thin orchestration layer (`ImpressManager` + `ImpressBasePipeline`) over `radical.asyncflow.WorkflowEngine` and pluggable `rhapsody` execution backends, whose `examples/` directory ships three real multi-stage protein-design campaigns.

## Identity
- **Version / release examined:** `tools/IMPRESS/pyproject.toml` — `name = "impress"`, `version = "0.1.0"`, `requires-python = ">=3.9"`. Dependencies: `radical.pilot`, `radical-asyncflow>=0.4.0`.
- **Provenance:** RADICAL Lab / Rutgers (Aymen Alsaadi et al.), GitHub `radical-collaboration/IMPRESS`. Refcode: `tools/IMPRESS/` (full repo, including `docs/`, `examples/`, `src/impress/`, `tests/`).
- **Maturity:** active research infrastructure. Real unit + integration test suite (`tests/unit/test_manager_*.py`, `tests/integration/test_manager.py`), MkDocs documentation site (`docs/`, `mkdocs.yml`), CI workflows (`.github/workflows/{docs,tests}.yml`). The three example pipelines carry their own revision-history tables documenting active, dated engineering work as recently as 2026-09-09 (`examples/small_molecule_binding/README.md`).

## Scientific role
IMPRESS itself solves no scientific problem — it is the **orchestration layer** that sequences other tools (RFDiffusion3, LigandMPNN/ProteinMPNN, Boltz-2, Chai-1, PyRosetta/Rosetta FastRelax) into iterative design→predict→score→adapt campaigns. Per this project's convention (compute-pattern-taxonomy.md, classification rule 4: "P7 is reserved for IMPRESS pipelines in this project"), each example pipeline is briefed here as **one coarse-grained composite tool (pattern P7)** — the agent parameterizes and launches a whole pipeline, then observes; it does not individually steer RFD3 vs. MPNN vs. Boltz calls inside it. The three example pipelines span all four in-scope problem classes except pure stability/thermostabilization: `protein_binding` (protein–protein binder design against a peptide), `small_molecule_binding` (de novo binder design against a small-molecule ligand), and `discontinuous_scaffolds` (motif/enzyme-active-site scaffolding — the closest fit to catalytic/enzyme design in this toolkit).

## Invocation & I/O contract

### Framework core
- **How it's invoked (Python API only, no CLI):**
  ```python
  from radical.asyncflow import WorkflowEngine
  from impress import ImpressManager, PipelineSetup

  flow = await WorkflowEngine.create(backend=backend)   # caller-owned
  manager = ImpressManager(flow, telemetry_config={...}, telemetry_subscribers=[...])
  await manager.start(pipeline_setups=[PipelineSetup(name="p1", type=MyPipeline, config={...}, adaptive_fn=my_fn), ...])
  await flow.shutdown()
  ```
  `ImpressManager.__init__` (`src/impress/impress_manager.py:20-48`) takes an already-constructed `flow: WorkflowEngine` — "The caller owns the engine: create it, pass it here, and shut it down when done. The manager never creates or shuts down the flow" (docstring, verbatim). `PipelineSetup` (`src/impress/pipelines/setup.py`) is a Pydantic `BaseModel` with fields `name: str`, `type: type[ImpressBasePipeline]` (validated by `field_validator` to be a real subclass), `config: dict`, `adaptive_fn: Optional[Callable]`, `kwargs: dict`.
  A concrete pipeline subclasses `ImpressBasePipeline` (`src/impress/pipelines/impress_pipeline.py`) and implements two abstract methods: `register_pipeline_tasks(self)` (registers `self.flow.executable_task(...)`-wrapped or local coroutine tasks via `self.auto_register_task(local_task=..., **task_kwargs)`) and `async run(self)` (the pipeline's own control flow / state machine).
- **Inputs:** pipeline-specific — see each example below. Generically: a `base_path`, an `<name>_in/` input directory, tool paths (`mpnn_dir`/`mpnn_path`, `foundry_sif_path`), and per-pipeline JSON/PDB/SMILES/params files.
- **Outputs:** pipeline-specific working directories under `base_path`, per-pass/per-stage CSVs, and (for `protein_binding`) telemetry checkpoints under `./telemetry/` when `telemetry_config` is passed to `ImpressManager`.
- **A concrete example**, real, from `docs/getting-started/adaptive-pipelines.md`:
  ```python
  execution_backend = await LocalExecutionBackend(ThreadPoolExecutor())
  flow = await WorkflowEngine.create(backend=execution_backend)
  manager = ImpressManager(flow)
  pipeline_setups = [PipelineSetup(name=f'p{i}', type=DummyProteinPipeline,
                                    adaptive_fn=adaptive_optimization_strategy)
                     for i in range(1, 4)]
  await manager.start(pipeline_setups=pipeline_setups)
  ```

### The three example pipelines, as distinct composite tools

#### 1. `discontinuous_scaffolds` (`examples/discontinuous_scaffolds/discontinuous_scaffolds.py`)
Motif-scaffolding campaign: given a target binding motif, generate discontinuous backbones around it, design sequences, fold, and check motif RMSD — closest fit to enzyme/catalytic-site design in this toolkit.

- **Stage sequence** (`DiscontinuousScaffoldsPipeline.run()`, three stages / eight steps, each gated by a local analysis check + `run_adaptive_step()`):
  1. **Backbone stage** — Step 1 `backbone_gen` (RFDiffusion3 via `apptainer exec`, GPU, `step1_backbone_gen.sh`) → Step 2 `backbone_post` (`cif_to_pdb.py`, CPU) → Step 3 `backbone_analysis` (`analysis_backbone.py` + `plot_backbone_analysis.py`, CPU) → `check_backbone_results()` (local task, reads CSV against `backbone_*_bounds` thresholds via `_identify_passing_models`) → `adaptive_decision()`.
  2. **Sequence stage** — Step 4 `seq_pred` (LigandMPNN `run.py`) → Step 5 `seq_post` (`split_seqs.py`) → Step 6 `seq_analysis` (`analysis_sequence.py` + `plot_sequence_analysis.py`) → `check_seq_results()` → `adaptive_decision()`.
  3. **Fold stage** — Step 7 `fold_pred` (Chai-lab `chai_batch.py`, GPU) → Step 8 `pipeline_analysis` (`analysis.py` + `plot_campaign.py`) → `check_fold_results()` (classifies by `rmsd_threshold` against best `motif_rmsd`) → `adaptive_decision()` → pipeline always terminates after fold stage.
- **Adaptivity is real branching, not just retry**: after each stage, mixed pass/fail results spawn a branch `DiscontinuousScaffoldsPipeline` (via `start_step` kwarg, which makes `run()` skip earlier stages) that re-enters at the failing stage with only the failing models, while the main pipeline continues with the passing subset. Fold-stage failures can additionally spawn a **redesign branch**: `scripts/create_redesign.py` builds a hybrid structure (well-predicted anchor regions Kabsch-aligned from the best Chai-1 output, combined with the original motif residues renumbered at 900+) and feeds it back into `backbone_gen` as a new, better-constrained RFD3 input — gated by `MAX_REDESIGN_DEPTH=3` and `MIN_RMSD_IMPROVEMENT=0.10 Å` stopping conditions.
- **Inputs:** `rfd_input_filepath` (RFD3 `InputSpecification` JSON keyed by model name, with `select_fixed_atoms`), auto-derived `lmpnn_pdb_multi_json`/`lmpnn_fixed_res_json` (via `generate_lmpnn_jsons()`), optional `island_counts_csv`, `mcsa_pdb_dir` (reference structures for RMSD).
- **Outputs:** per-branch `{base_path}/{branch_id}/{N}_{taskname}/{in,out}/` directories; `campaign_analysis.csv` (Step 8) carries `anchor_residues`/`anchor_sequences`/`anchor_ref_residues` columns that drive the redesign strategy.
- **Caller-variable parameters:** `diffusion_batch_size` (default 10), `lmpnn_num_batches` (default 4), `rmsd_threshold` (default 1.5 Å), and six `(lower, upper)`-tuple threshold pairs for backbone (`backbone_rog_bounds`, `backbone_ala_bounds`, `backbone_gly_bounds`, `backbone_helix_bounds`, `backbone_sheet_bounds`, `backbone_lig_dist_bounds`) and two for sequence (`seq_ligand_conf_bounds`, `seq_overall_conf_bounds`).

#### 2. `protein_binding` (`examples/protein_binding/protein_binding.py`)
Iterative PDZ-domain binder design against a fixed target peptide: `s1` MPNN → `s2` rank → `s3` write paired FASTA → `s4` structure-predict (×N, parallel) → `s4_post_exec` (stage files, parallel) → `s5` pLDDT/PTM extraction → `run_adaptive_step()`.

- **Adaptivity**: `adaptive_decision()` (defined in the *runner*, `run_protein_binding.py`, not the pipeline class — the pipeline only exposes the hook) compares each protein's current vs. previous-pass pLDDT score; degraded proteins are popped out and a child pipeline is spawned (`{parent}_sub{N}`, `seq_rank+1` — try the next-best MPNN candidate) via `submit_child_pipeline_request()`, capped at `MAX_SUB_PIPELINES=3`. If the parent's structure list empties after spawning, `pipeline.kill_parent = True`.
- **A second, LLM-adaptive runner exists in the same example** (`protein_binding_run.py`) — directly relevant to this project's Control-Mode-B design: it replaces the numeric score-comparison predicate with a real call to `claude-opus-4-6` (`anthropic.AsyncAnthropic().messages.create(...)`). Each pass, per-protein MPNN + Boltz confidence metrics are appended to a running `ensemble.csv`/`ensemble_distributions.npz`, formatted as a text prompt with histogram-binned prior-ensemble distributions and the current candidate's percentile rank, and the LLM is asked to answer with exactly one of two fixed sentences ("The current sequence should be refined." / "A new sequence should be sampled.") — parsed by substring match. This is a working precedent for exactly the P5 LLM-oracle-in-the-loop pattern this project is evaluating; see `briefs/llm-oracle.md`.
- **Inputs:** `<name>_in/` PDB files, `mpnn_path` (env `MPNN_PATH` or kwarg, required), hardcoded target peptide `EGYQDYEPEA` (in `s3`), pre-computed Boltz MSA cache at `~/boltz/msa_cache` (compute nodes have no internet in the reference deployment — MSAs are embedded in the FASTA header by path, or `|empty|` for single-sequence mode).
- **Outputs:** `af_pipeline_outputs_multi/<name>/{mpnn,af}/...`, `af_stats_<name>_pass_<N>.csv` staged back to the client node via `output_staging` (`task:///` → `client:///`).
- **Caller-variable parameters:** `max_passes` (default 4, production runner uses 10), `num_seqs` (MPNN sequences per job, default 10), `seq_rank` (which ranked candidate to fold, default 0), `N_PIPELINES` (parallel independent pipelines, runner default 16), `MAX_SUB_PIPELINES` (child-spawn depth cap, default 3).
- **Execution backend**: selected via `IMPRESS_BACKEND` env var — `dragon` (default, `rhapsody.backends.DragonExecutionBackend`, multi-node HPC) or `local` (`ConcurrentExecutionBackend(ProcessPoolExecutor())`).

#### 3. `small_molecule_binding` (`examples/small_molecule_binding/small_molecule_binding.py`)
De novo binder design against a small-molecule ligand: `rfd3` (backbone diffusion) → `mpnn`+`packmin` refinement cycle (×`num_refine_cycles`) → `fastrelax` (Rosetta) → `filter_shape` (PyRosetta shape complementarity) → `boltz` (protein+ligand co-folding) → loop back to `rfd3`, optionally **guided** by the best fold decoy.
- Implemented as an explicit state machine (`STEP_RFD3`/`STEP_MPNN`/`STEP_FASTRELAX`/`STEP_INTERFACE`/`STEP_AF2`/`STEP_RETRY_SEQ`/`STEP_DONE`), not a linear sequence — `next_step` is set by `adaptive_decision()` after every stage.
- **Adaptivity — an ensemble-based "selective average" router**, distinct from the other two pipelines' threshold-only gating: every analysis task appends `(type, score, input_path, output_path)` to `pipeline.state['ensemble']`; the router computes the mean score of prior entries most *structurally/sequence similar* to the current candidate (Kabsch-RMSD for backbones/folds, per-position identity for sequences) and continues only if that "selective average" beats the overall ensemble average — i.e., it routes based on whether the current result sits in a locally productive region of design space, not just an absolute threshold. A separate **non-improvement short-circuit** (`_stage_metrics_improving`, 5% relative-gap-closure test) escalates straight to a new backbone after one non-improving fastrelax/interface retry, based on real HPC data showing flat failures never recover.
- **Guided partial diffusion**: on a productive fold, the current Boltz co-folded decoy is fed back into RFD3 as a *partial-diffusion* guide (`partial.input` + `partial_t` in the `InputSpecification` JSON) after a real, non-trivial atom-identity/atom-name remapping step (`_infer_ligand_atom_mapping`, graph-isomorphism + Kabsch tie-break) — RFD3 has no scaffold-guidance CLI flag; this is the only mechanism.
- **Inputs:** `<name>_in/ALR_binder_design.json` (RFD3 spec), `<ligand>.params` (Rosetta), `<ligand>.smiles` (derived once via `scripts/derive_ligand_smiles.py`), `fixed_residues.txt`.
- **Outputs:** numbered `{N}_{taskname}/{in,out}/` dirs; terminates purely on `max_tasks` ensemble-entry budget (default 300), never on a "success" condition — this pipeline is an exploratory search, not a fixed campaign.
- **Caller-variable parameters:** `num_refine_cycles` (3), `mpnn_ensemble_size` (1), `diffusion_batch_size` (2), `rfd3_partial_t` (10.0 Å), `max_tasks` (300), plus five quality thresholds (`backbone_max_ca_deviation`, `backbone_min_ss_fraction`, `fastrelax_max_*`, `interface_min_sc`, `fold_min_plddt`, `fold_min_ligand_iptm`).
- **Execution backend**: `DragonExecutionBackend` (production) or `local` via `IMPRESS_BACKEND` env var, same convention as `protein_binding`.

## Compute pattern
- **Pattern:** **P7 (composite pipeline)** for all three examples — per taxonomy rule 4, IMPRESS pipelines are reserved for P7 in this project regardless of what individual stages could theoretically be addressed as. Internally, stages are a mix of **P1** (GPU, RFD3/MPNN/Boltz/Chai — `gpus_per_rank: 1` task descriptions), **P2/P6** (CPU local tasks — `cif_to_pdb`, analysis/plotting scripts, `local_task=True` coroutines), and (for `protein_binding`'s LLM runner) **P5** (the Claude API call inside `adaptive_criteria`).
- **GPU vendor portability:** **CUDA-only, by inheritance** — every GPU stage in all three pipelines shells out to a tool briefed elsewhere in this toolkit as CUDA-only or CUDA-primary (RFDiffusion3 via `apptainer` with `--nv` semantics implied by the Foundry container conventions, Boltz-2, Chai-lab). IMPRESS itself has no GPU-touching code — `task_description={"gpus_per_rank": 1}` is an advisory resource hint passed to the backend, not a device-selection mechanism — so portability is entirely a function of what each stage's underlying tool supports (see `foundry.md`, `rfdiffusion3.md`, `boltz.md`, `chai.md`).
- **State model:** **checkpointable at the pipeline-manager level** — `ImpressManager` accepts `telemetry_config={"checkpoint_path": ..., "resource_poll_interval": ...}` forwarded to `flow.start_telemetry()`, used in the `protein_binding` production runner. Individual pipeline *stage* state lives in an in-memory `self.state` dict (all three pipelines) with no built-in persistence — a pipeline killed mid-run loses `self.state` unless the caller has separately persisted it; branch/child pipelines carry state forward explicitly through `config`/`initial_state` at spawn time, not through any framework-level checkpoint/restore.
- **Data locality:** shared-FS required for multi-stage handoff — every example writes/reads plain files (PDB/CIF/FASTA/JSON/CSV) between stages under a shared `base_path`; no in-memory or object-store handoff between stages exists in any of the three examples.
- **Staging burden:** none from IMPRESS itself; inherited entirely from whatever the stage tools need (RFD3/Boltz/Chai weights — see `foundry.md`/`boltz.md`/`chai.md`), plus, for `protein_binding`, a pre-computed Boltz MSA cache staged from a login node with internet access before the compute-node run (`~/boltz/msa_cache`, populated by `delta_env_setup.sh`) — a concrete, working precedent for this project's own MSA-staging problem on air-gapped-ish compute nodes.
- **Container availability:** n/a for IMPRESS itself (pure Python package, `pip install`-able); `small_molecule_binding` and `discontinuous_scaffolds` both invoke RFD3 through an Apptainer/Singularity `.sif` (`foundry_sif_path` kwarg, required, raises `ValueError` if unset) — build-required per the Foundry brief's container findings.

## Deployment on DOE & ACCESS
- **Delta (ACCESS, CUDA)** is the only platform with real, working deployment scripts in the refcode: `delta_env_setup.sh` and `delta_gpu_run.sh` in both `protein_binding/` and `small_molecule_binding/`, and `run_islands.slurm` in `discontinuous_scaffolds/rfd3_benchmark/`. These set `MPNN_DIR`/`FOUNDRY_SIF_PATH`/`BOLTZ_CACHE` and submit via `sbatch`.
- **Polaris/Aurora/Frontier:** no example-specific deployment script exists in this refcode; IMPRESS itself is platform-agnostic (it never touches CUDA/HIP/SYCL directly — see GPU vendor portability above), so deployment reduces entirely to (a) whether `radical.pilot`/`radical-asyncflow` and `rhapsody`'s `DragonExecutionBackend`/`RadicalExecutionBackend` are available on the target scheduler (SLURM vs. PBS Pro — RADICAL-Pilot has PBS support; not independently re-verified here), and (b) whether the stage tools themselves run there (per their own briefs — RFD3/Boltz/Chai are all CUDA-primary with unproven-to-absent HIP/XPU paths, which is the real Frontier/Aurora blocker, not IMPRESS).
- **License gates:** none in IMPRESS itself. `small_molecule_binding` requires Rosetta/PyRosetta (`packmin.py`, `fastrelax.sh`, `filter_shape.sh`) — see `rosetta.md`/`pyrosetta.md` for that license gate.
- **A real, load-bearing version conflict to flag:** IMPRESS declares `requires-python = ">=3.9"` (`tools/IMPRESS/pyproject.toml:18`), while `foundry` (which RFD3/MPNN/RF3 are packaged on, per `briefs/foundry.md`) declares `requires-python = ">=3.12"`. Since `small_molecule_binding` and `discontinuous_scaffolds` both shell out to Foundry-packaged tools via `apptainer`/subprocess rather than importing `foundry` in-process, this is not a hard install-time conflict *today* — but it means IMPRESS and Foundry-based tools cannot share a single Python environment if any future integration wants to call Foundry's `BaseInferenceEngine` in-process from inside an IMPRESS task (e.g., a P6-style direct Python call instead of a subprocess), and it flags that IMPRESS's own dependency floor (`radical.pilot`, `radical-asyncflow>=0.4.0`) has not been re-verified against Python 3.12+ in this refcode.

## Agentic surface
- **Native MCP:** no. Repo-wide grep across `tools/IMPRESS` for `mcp`/`model context protocol`/`modelcontextprotocol` returns zero hits. Confirmed independently by the `mcp-landscape.md` sweep.
- **Parameters worth exposing for autonomous variation:**

| Parameter | Type | Sane range | Default | Trade-off |
|---|---|---|---|---|
| `N_PIPELINES` / initial `pipeline_setups` list length | int | 1–32 | 16 (`protein_binding` runner) | Independent-lineage breadth vs. total GPU-hour cost; each pipeline is a fully independent campaign |
| `max_passes` / `max_tasks` (pipeline-specific budget cap) | int | pipeline-dependent (`protein_binding`: passes; `small_molecule_binding`: ensemble-entry count) | 4–10 / 300 | Primary lever on total compute spent per lineage before forced termination |
| `MAX_SUB_PIPELINES` / `MAX_REDESIGN_DEPTH` | int | 1–5 | 3 | Bounds child/branch fan-out depth — directly bounds worst-case total task count for a single root pipeline |
| Quality thresholds (`*_bounds`, `fold_min_plddt`, `rmsd_threshold`, etc.) | float / tuple | pipeline-dependent, documented per-pipeline in each README | pipeline-dependent | Tightening raises design quality bar at the cost of more branch/retry spawns; loosening trades quality for throughput |
| `diffusion_batch_size` / `num_seqs` / `lmpnn_num_batches` | int | 1–20 | 2–10 | Per-stage ensemble width; larger batches amortize GPU task-launch overhead but increase per-pass wall time |
| `telemetry_config` (`checkpoint_path`, `resource_poll_interval`) | dict | n/a | `None` (disabled) | Enabling gives crash-recoverable campaign state and event history — should be on by default for any autonomous, unattended run |

- **Parameters that must NOT be agent-varied:**
  - The `adaptive_fn` callable's *decision logic* itself should not be silently swapped mid-campaign by the agent without an explicit, logged decision — this is exactly the Part-B question ("how does our agent relate to IMPRESS's adaptivity hook") and swapping it invisibly would make campaign provenance unreconstructable.
  - `foundry_sif_path`/`mpnn_dir`/`boltz_cache_path` — these fail loudly (`ValueError`) if unset, by design; an agent should treat them as fixed deployment configuration, not something to vary per design attempt.
  - `WorkflowEngine`/backend construction and shutdown — per the explicit ownership contract ("The caller owns the engine... The manager never creates or shuts down the flow"), an agent driving `ImpressManager` must not attempt to re-create or tear down the flow mid-campaign; that is the orchestration layer's job, one level above IMPRESS.

## `adaptive_fn` hook and `run_adaptive_step()` / `submit_child_pipeline_request()` — precise mechanics
This is the pre-existing adaptivity mechanism Part B must decide how our agent relates to (wrap it, replace it, or drive it as a policy input). It is entirely pull-based and synchronous-from-the-pipeline's-perspective:

1. A pipeline calls `await self.run_adaptive_step(wait=True)` (`impress_pipeline.py:62-71`) at a point of its own choosing in its `run()` method (after each stage in all three examples). This sets `self.invoke_adaptive_step = True` and clears an internal `asyncio.Event` (`self._adaptive_barrier`), then (if `wait=True`) blocks on that event.
2. `ImpressManager.start()`'s poll loop (`impress_manager.py:151-260`, no fixed tick — busy-polls with `asyncio.sleep(0.5)` only when idle) notices `pipeline.invoke_adaptive_step` is set and not already running, and launches `self._run_adaptive_fn(pipeline)` as a separate `asyncio.Task` (`impress_manager.py:100-122`).
3. `_run_adaptive_fn` calls `pipeline._adaptive_fn(pipeline)` — **the adaptive function receives the entire pipeline object**, not a restricted view: it can read *any* pipeline attribute (`self.state`, `self.current_scores`, `self.iter_seqs`, file paths, everything) and can call `pipeline.submit_child_pipeline_request(config_dict)` to queue a new pipeline, or mutate `pipeline.next_step` / `pipeline.kill_parent` directly. There is no sandboxing or schema on what the adaptive function is allowed to see or do — it is a plain Python closure with full object access, typically defined in the *runner* script (`run_protein_binding.py::adaptive_decision`), not the pipeline class.
4. On completion (success or exception — exceptions are caught and logged, not propagated), `_run_adaptive_fn`'s `finally` block sets `pipeline.invoke_adaptive_step = False` and calls `pipeline._adaptive_barrier.set()`, unblocking step 1's `await`.
5. Back in the manager's poll loop, `pipeline.get_child_pipeline_request()` (`impress_pipeline.py:34-49`) is checked every tick — if `submit_child_pipeline_request()` was called, the buffered config is converted to a `PipelineSetup` and queued in `manager.new_pipeline_buffer`, submitted as a new independent pipeline task on the next loop iteration via `submit_new_pipelines()`.

**What this means for Part B:** the adaptive function is a full-context, synchronous (from the calling pipeline's view — it blocks that one pipeline, not the whole manager) decision point that already has everything an LLM oracle would need (full pipeline state, all scores, all file paths) and already has a working mechanism to act on a decision (mutate `next_step`/`kill_parent`, or spawn a child/branch pipeline with an inherited or new `adaptive_fn`). The `protein_binding_run.py` LLM-adaptive runner (see above) is direct proof this slot can host a remote-API call with real network latency without any framework changes — it just makes `adaptive_fn` an `async def` that awaits `anthropic.AsyncAnthropic().messages.create(...)`. The open design question for Part B is not "can the oracle plug in here" (it demonstrably can) but "should our agent *be* the `adaptive_fn` for every pipeline, or sit one level above IMPRESS and treat each P7 pipeline launch (with a chosen `adaptive_fn`) as its own action" — the latter preserves IMPRESS's existing per-pipeline adaptivity as an internal implementation detail the agent doesn't have to re-implement, at the cost of the agent only getting to steer at pipeline-launch granularity, not mid-campaign.

## Failure modes & what the agent must check
- **Loud failure:** `PipelineSetup`'s Pydantic `field_validator` raises `ValueError` immediately if `type` is not an `ImpressBasePipeline` subclass. `small_molecule_binding` raises `ValueError` at construction if `mpnn_dir`/`foundry_sif_path`/`boltz_cache_path` are unset (no silent default). Subprocess-based tasks (`mpnn`, `packmin`, `fastrelax`, `filter_shape`, `filter_energy` in `small_molecule_binding`) raise `RuntimeError` on non-zero exit code, with the log file path included in the message.
- **Silent bad output — the important category for an autonomous agent:**
  - **Spurious backend failures that are actually successes.** Both `protein_binding.py::run()` and the `_guarded_s4` wrapper explicitly work around this: MPNN (`s1`) and Boltz (`s4`) sometimes raise a `TypeError`/`NoneType` or `ProcessGroup` state error from the *execution backend* even though the underlying tool completed correctly — the pipeline code checks for expected output files on disk before deciding whether to treat the exception as real. **An agent driving IMPRESS pipelines directly (not through the examples' own guards) must apply the same check-the-filesystem-before-trusting-the-exception discipline**, or it will spuriously kill or retry successful work.
  - **`small_molecule_binding`'s RFD3 guided-diffusion silent fallback.** `_prepare_guided_rfd3_inputs` returns `None` on any of several failure conditions (no ligand HETATM found, atom-name mapping fails, `select_exposed`/`select_buried` atom coverage check fails) — the caller (`rfd3()` task) falls back to **unguided** diffusion without raising. This is correct-by-design (documented, deliberate fail-safe) but means a run that was *intended* to be guided can silently degrade to unguided for an entire campaign if the upstream Boltz output happens to be malformed; an agent should log/alert on this fallback path, not just trust that "guided mode requested" implies "guided mode ran."
  - **`analysis_backbone`'s NaN-driven false pass in guided mode.** RFD3's partial-diffusion output never populates `helix_fraction`/`sheet_fraction` (literal JSON `NaN`); `ss = NaN + NaN`, and the code correctly special-cases `guided` mode to skip the SS-fraction check rather than let `NaN > threshold` silently evaluate `False` — but this is a documented one-off fix, not a general defense; any *new* metric added to this analysis path that isn't guided-mode-aware would reintroduce the same class of bug.
- **What to check post-hoc:** presence and non-empty-ness of the expected output directory/file before trusting a task's return value; for `discontinuous_scaffolds`/`small_molecule_binding`, the analysis CSV's row count against the expected batch size (a CSV with fewer rows than `diffusion_batch_size` indicates partial GPU-stage failure that didn't raise); for `protein_binding`'s LLM-adaptive runner, that `ensemble.csv` actually grew by one row per pass (a stalled ensemble means the LLM call path is silently no-op-ing).

## Cost per unit of work
`unit of work · typical wall-clock · resource shape · checkpointable?`
- **One `protein_binding` pass** (MPNN + N-parallel Boltz + pLDDT extract): dominated by the Boltz co-folding step, minutes per structure on one GPU, parallelized across `num_seqs`-derived structures within a pass via `asyncio.gather` — total pass wall-clock is roughly one Boltz-call's time if GPU concurrency is available, resource shape 1 GPU/rank × however many ranks the backend schedules concurrently. Checkpointable only via the manager-level telemetry checkpoint; individual in-flight pass state is not independently recoverable.
- **One `small_molecule_binding` cycle** (rfd3 batch → mpnn+packmin ×`num_refine_cycles` → fastrelax → filter_shape → boltz): the longest-running of the three examples per iteration — RFD3 backbone generation and Rosetta FastRelax are both real minutes-scale GPU/CPU-heavy steps; a full loop-back to `rfd3` (guided or not) can run for many cycles up to the `max_tasks=300` ensemble-entry budget, which is an explicit compute-cost circuit breaker, not a scientific stopping condition — the agent should treat `max_tasks` as the primary dial for bounding total spend on one lineage.
- **One `discontinuous_scaffolds` full 8-step run**: RFD3 (`backbone_gen`, GPU) and Chai-lab (`fold_pred`, GPU) are the two GPU-bound steps; the five CPU steps (post-processing, analysis, plotting, LigandMPNN, split) are comparatively cheap. Branch/redesign spawning multiplies total campaign cost roughly linearly with `MAX_REDESIGN_DEPTH` in the worst case (3× by default).
- General note: **none of the three example pipelines report their own wall-clock or resource-hour cost** in the refcode (no benchmarking data found); the above is inferred from stage composition (which GPU tools are called, how many times, in what loop structure), not measured.

## Verdict
**Core**, exactly as scoped by the user: IMPRESS is not being evaluated for adoption/rejection here — it is the P7 composite-pipeline substrate this project has already decided to build on, and the three example pipelines are directly re-launchable as agent actions today with real, working (if Delta-specific) deployment scripts. The two findings that matter for planning rather than for the verdict: (1) the `adaptive_fn` mechanism already has a working LLM-oracle precedent (`protein_binding_run.py`) that Part B should study closely rather than design from scratch, since it demonstrates the exact P5-oracle-inside-a-P7-pipeline integration this project's Control Mode B calls for; and (2) the `requires-python>=3.9` (IMPRESS) vs. `>=3.12` (Foundry) floor mismatch is not a blocker today because the two integrate via subprocess/container boundaries, not in-process imports, but it forecloses a future in-process Foundry integration inside an IMPRESS task without a Python-version reconciliation.
