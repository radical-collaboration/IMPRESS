# AgentRosetta

**One-line identity.** An LLM agent (`agr` CLI) that drives RosettaScripts through a custom hand-rolled agent loop — not LangGraph or any other agent framework — with a tree-structured trajectory supporting backtracking and a Pareto-front multi-objective design selector; prior art directly relevant to IMPRESS-A's own outer loop.

## Identity
- **Version / release examined:** `pyproject.toml` — `name = "agent-rosetta"`, `version = "0.1.0"`, `requires-python = ">=3.11.11"`. Refcode path: `tools/agent-rosetta/`.
- **Provenance:** Polymathic AI (Teneggi, Turzo, Marwah, Bietti, Renfrew, Mulligan, Golkar), MIT License (`tools/agent-rosetta/LICENSE`). Companion paper: arXiv:2603.15952, "Protein Design with Agent Rosetta: A Case Study for Specialized Scientific Agents" (Teneggi et al., submitted 2026-03-16, ICML/NeurIPS 2026 poster).
- **Maturity:** active research prototype. Working CLI (`agr`), recorded terminal demo (`assets/vhs/output/hello-rosetta.gif`), example configs for two published tasks (fixed-backbone sequence design, NCAA packing), but a 0.1.0 version number and single-repo scope — this is a research artifact, not a maintained production framework.

## Scientific role
AgentRosetta is not a new scientific method — it is an **agentic wrapper around RosettaScripts** (see `rosetta.md`) that lets an LLM choose which Rosetta mover to apply next, informed by the actual structure/score state after each previous action, rather than committing to a fixed multi-stage pipeline up front. Per the paper abstract (via WebSearch): "LLM agents can interact with Rosetta more frequently, selecting the next Mover immediately after the previous one completes... enabling adaptive guidance of the design process informed by the properties of intermediate structures." It covers fixed-backbone sequence design (canonical amino acids, benchmarked against ESMFold-based structure prediction) and packing tasks involving non-canonical amino acids (NCAAs) where ML-only approaches (ProteinMPNN etc.) cannot participate because NCAAs fall outside their training distribution — this is presented as AgentRosetta's specific edge over specialized ML models.

## Invocation & I/O contract
- **How a unit of work is invoked:** CLI, `agr` (entrypoint `agent_rosetta.cli.main:main`, `[project.scripts]` in `pyproject.toml:52`), installed via `uv tool install -e .`. Example real invocations from `README.md`:
  ```
  agr setup                              # configure LLM API keys
  agr setup rosetta                      # resolve RosettaScripts binary paths
  agr run configs/hello-rosetta.yaml     # smoke test
  agr run configs/pack-ncaa-slurm.yaml   # NCAA packing task, SLURM-backed
  agr run configs/fixed-backbone-sequence-design-local.yaml
  ```
  Configuration is Hydra-composed YAML (`hydra-core` dependency, `hydra.utils.instantiate` used throughout `agent_rosetta/runner.py`), assembling `environment` + `model` + `task` + `parser` + `runner` sub-configs (`configs/environment/rosetta.yaml`, `configs/model/*.yaml`, `configs/task/*.yaml`, `configs/parser/rosetta.yaml`, `configs/runner/refine.yaml`).
- **Inputs:** a starting PDB (`assets/pdbs/6V67.pdb`, `assets/pdbs/9PL1_gly.pdb` are the two example structures shipped in the repo), a task config specifying objective and constraints, and an LLM provider/model choice (`litellm`-mediated: Anthropic `ant-sonnet-4.6`/`ant-opus-4.6`, OpenAI `oai-gpt-5`/`oai-gpt-5-mini`, OpenRouter `or-sonnet-4.5`/`or-qwen3-235b`/`or-gemini-2.5-flash`, per `agent_rosetta/cli/constants.py`).
- **Outputs:** a `trajectory.json` (`Trajectory.save()`, `agent_rosetta/trajectory.py:53-56`) recording the full tree of steps taken, plus per-step Rosetta output PDBs/scorefiles and (for reward-scored tasks) ESMFold-predicted structures and Pareto-front membership flags.
- **A concrete example:** `configs/pack-ncaa-slurm.yaml` (real file) configures the `pack-ncaa` task to run RosettaScripts via SLURM with `partition: ${oc.env:AGR_SLURM_PARTITION}`, `cpus_per_task: 1`, `ntasks: auto`, `mem: 0`, `time: "01:00:00"` — i.e. the agent submits a 128-rank MPI RosettaScripts ensemble (per README: "generate ensembles of 128 candidate designs at each step") as one SLURM job per agent step.

### The agent loop: custom, not a framework
AgentRosetta implements its own minimal agent loop from scratch — no LangGraph, no LangChain agent executor, no AutoGen. The core classes:
- **`Agent.run_step()`** (`agent_rosetta/agent.py:33-141`) — a hand-written loop: build/append the next user message, query the LLM (with retry-with-backoff on empty/malformed responses, `time.sleep(10)` between retries up to `max_query_retries`), parse the XML-tagged action out of the response (with a separate retry budget `max_parse_retries`, feeding parser errors back to the LLM as corrective user messages), then call `env.step(act_name, act_args, act_tag, task, traj)` and wrap the result in a `TrajectoryStep`.
- **`Runner`/`RefineRunner`** (`agent_rosetta/runner.py`, `runners/refine.py`) — an even simpler outer `while` loop (`runners/refine.py:13-40`): `while self.env.state.global_step < self.config.max_steps: step = self.agent.run_step(...); self.trajectory.add(step)`, breaking on a `StopStep` sentinel. There is no graph, no node/edge declaration, no conditional-routing DSL — just a Python `while` loop over a flat step budget.
- **Actions are a closed, typed enum**, not open-ended tool-calling: `EnvironmentActions` (`agent_rosetta/action.py:18-53`) pairs each action name with a Pydantic `args` model and a docs string; the Rosetta-specific action set (`environments/rosetta/actions.py`) is exactly `rotamer_change` (FastDesign with design enabled, compositional penalties, residue restrictions), `backbone_change` (`small`/`shear`/`backrub` movers), and `go_back_to_step`, plus environment-level `sandbox`/`score_pdb` (confirmed by `environments/rosetta/typing.py:18`: `"sandbox", "score_pdb", "rotamer_change", "backbone_change", "go_back_to_step"`).

### Tree-structured Trajectory and `go_back_to_step`
`Trajectory` (`agent_rosetta/trajectory.py`) stores **every** step ever taken as a node in a `dict[int, TrajectoryNode]` keyed by step index, plus a separate `_path: list[int]` representing the currently-active linear path through that tree. `add()` appends a new node whose parent is the current path's last node. `go_back_to(step)` (lines 44-51) does **not** delete history — it truncates `_path` to end at the target node (`self._path = self._path[: self._path.index(node_idx) + 1]`), so previously-explored branches remain addressable in `_nodes` even after the agent "backs up." This is exposed to the LLM as the `go_back_to_step` action (`environments/rosetta/actions.py:34-38`, docs: "Revert the environment state to a previous step in the trajectory... allowing you to retry actions or explore different paths"), letting the agent abandon an unproductive Rosetta move (e.g., a `backbone_change` that produced a clashing structure) and retry from the last good state without losing the record of the abandoned branch — a lightweight MCTS-adjacent search structure implemented in ~45 lines, not a general graph engine.

### SLURM integration
`environments/rosetta/utils/cmd.py` implements the actual job-submission mechanics used whenever a task config sets `mpi_mode: slurm` (e.g. `configs/pack-ncaa-slurm.yaml:12`). Key behavior:
- `run_cmd_slurm()` (`cmd.py:133-190`) submits via **`sbatch --parsable --wait --output=... --error=...`** — the `--wait` flag makes this a **blocking** submission from the agent's point of view: the Python process blocks until the SLURM job completes, rather than submitting and polling asynchronously. This is a deliberate simplification (the agent loop is itself already synchronous/turn-based, so blocking submission matches its control flow) but it means AgentRosetta's own SLURM integration does **not** implement the async submit/poll/durable-job-store pattern that IMPRESS-A's P4 definition calls for — a killed agent process loses track of an in-flight `sbatch --wait` job with no separate job-ID ledger to recover from.
- Structured error classification distinguishes `resource_error` (SLURM partition/QOS/processor-count rejections, `is_sbatch_resource_error()`, matched against literal SLURM error strings like `"Batch job submission failed: Invalid partition name specified"`), `transport_error` (retried up to `max_retries` with `delay`-second backoff, `run_cmd_slurm:179-185`), and `runtime_error`/`timeout` — this classification is fed back into the trajectory/reward machinery so the LLM can see *why* a step failed, not just that it failed.

### Pareto-front multi-objective selection
`environments/rosetta/reward.py` implements `get_pareto_front()` (lines 27-44) using the **`paretoset`** PyPI package (`pyproject.toml:24`, `paretoset>=1.2.5`) — not a custom implementation. Given a `pandas.DataFrame` of per-design reward fields and a `minimize: list[bool]` direction per field, `paretoset.paretoset(scores, sense=[...])` returns a boolean mask of Pareto-efficient designs; each `RosettaDesign.is_pareto_efficient` is set from that mask. Two concrete reward functions are wired up (`task_reward_map`, `reward.py` bottom):
- `fixed_backbone_sequence_design_reward` — Pareto front over `["esmfold_ca_plddt", "esmfold_rmsd_to_init", "total_score"]` with `minimize=[False, True, True]` (maximize pLDDT, minimize RMSD-to-init and Rosetta score).
- `pack_ncaa_reward` — Pareto front over `["ncaa_core_success", "total_score", "cav_vol", "rg", "rmsd_to_init"]`, `minimize=[False, True, True, True, True]`.
This is used to **select** which trajectory branches/decoys the agent should consider "good" without collapsing multiple objectives into one scalar reward — directly relevant to any IMPRESS-A selection logic that must rank stability, binding, and structural-quality metrics jointly rather than via a single weighted sum.

## Compute pattern
AgentRosetta is a **composite, multi-pattern system**, not a single-pattern tool — appropriate given it is itself an orchestrator:
- **P1** (GPU-node-local) for ESMFold structure prediction used in the fixed-backbone-design reward (`environments/rosetta/tools/esmfold.py`, `esmfold_ray.py`; `torch`/`torchvision` pinned to a CUDA 12.6 wheel index in `pyproject.toml:36-43` — confirms CUDA-only ESMFold dependency, no HIP/SYCL path).
- **P2** (CPU fan-out, in-job) for the `-local` config variants (README: "Make sure the host machine has at least 130 processes available for MPI" for local mode).
- **P3/P4 blend** for the `-slurm` config variants: RosettaScripts itself runs as an **MPI** job (`rosetta_scripts.cxx11threadmpiserialization.linuxgccrelease`, confirmed binary name in `agent_rosetta/cli/constants.py:18-20`, i.e. P3-shaped rank topology) submitted as a **separate SLURM batch job per agent step** via blocking `sbatch --wait` (P4-shaped external submission, but synchronous rather than async-poll as discussed above).
- **GPU vendor portability:** **CUDA-only** for the ESMFold component (explicit `pytorch-cu126` index pin, `pyproject.toml:37,41-43`) — this is the one piece of AgentRosetta that would need substitution (CPU ESMFold, or an alternate structure predictor) to run on Frontier/Aurora without a CUDA-capable partition.
- **State model:** checkpointable at the trajectory level (`Trajectory.save()` writes the full node/path state to JSON at any point) but the SLURM submission layer itself is not independently checkpointed (see blocking-`--wait` caveat above).

## Deployment on DOE & ACCESS
AgentRosetta is not deployed on any of these platforms today, and the refcode gives no platform-specific setup beyond generic SLURM. What would actually block or complicate a port: (1) the ESMFold reward component is **CUDA-only** (`pytorch-cu126` pin, see above) — it would run on Polaris/ACCESS as-is but needs a CPU or HIP/SYCL substitute (or simply dropping the ESMFold-based reward term) to run on Frontier or Aurora GPU partitions; (2) its SLURM integration (`run_cmd_slurm`, `cmd.py`) is written directly against `sbatch`/SLURM semantics with no PBS Pro path, so it would need adaptation, not just configuration, to run natively on Polaris or Aurora (both PBS Pro); ACCESS (SLURM) and Frontier (SLURM) are the only target platforms where its job-submission code would work unmodified. (3) It depends on a working RosettaScripts `cxx11thread`/`mpi` build already being present (`agr setup rosetta` only *records* binary paths, it does not build Rosetta) — so it inherits all of the same build-from-source, license-gated deployment burden documented in `rosetta.md`, with no shortcut of its own.

## Agentic surface
**Read this section as a design reference, not a deployable-tool spec** — AgentRosetta is prior art to learn from, not infrastructure IMPRESS-A would install and call.
- **Native MCP:** **no** — a repo-wide grep of `tools/agent-rosetta` for `mcp` / `model context protocol` / `fastmcp` / `stdio_server` returns zero matches. AgentRosetta predates or deliberately bypasses MCP entirely: its LLM-to-environment interface is a bespoke `<action>` XML dialect validated against `parsers/rosetta/action.xsd`, not a tool-schema protocol. Rosetta itself likewise has no official server (a third-party `Arielbs/rosetta-mcp-server` exists, unaffiliated and flagged low-trust by at least one scanner — see `mcp-landscape.md`). Nothing here is adoptable as an MCP surface.
- **LLM backend:** `litellm`-mediated, multi-provider (`agent_rosetta/model.py`), configured per-run via `configs/model/*.yaml` (`ant-sonnet-4.6`, `ant-opus-4.6`, `oai-gpt-5`, `oai-gpt-5-mini`, `or-sonnet-4.5`, `or-qwen3-235b`, `or-gemini-2.5-flash`) — reasoning-capable models are used and the loop explicitly logs `reasoning` separately from `content` (`agent_rosetta/agent.py:66-71`).
- **Action surface is closed/typed**, not open tool-calling: every action is a `Pydantic` model with a docstring injected into the system prompt (`EnvironmentActions.to_docs()`, `action.py:33-41`) — a deliberate design choice trading flexibility for parseability/validation, worth noting since it is the opposite of "give the LLM arbitrary shell access."
- **Parser retry loop** is explicit and bounded (`max_parse_retries`, `max_query_retries` in `agent.py:54-117`), with parse failures fed back to the model as corrective context rather than crashing the run — a pattern directly reusable in IMPRESS-A's own action-parsing layer regardless of whether we adopt anything else from this codebase.

## Failure modes & what the agent must check
Beyond the standard Rosetta structural-QC concerns already covered in `rosetta.md` (which apply unchanged to every structure AgentRosetta produces), AgentRosetta-specific failure classes:
- **Loud, classified failures** — `classify_runtime_error()`/`classify_sbatch_error()` (`cmd.py:41-79`) turn raw stdout/stderr into one of `resource_error`/`transport_error`/`runtime_error`/`timeout`/`success`, including a Rosetta-specific pattern match for backbone-mover failures ("no movable positions in" → `"Backbone mover failed: no movable positions found."`, `cmd.py:33-38,53-54`) — a useful concrete example of turning a Rosetta stderr string into a structured, LLM-legible failure reason rather than a raw log dump.
- **Blocking SLURM submission risk** (see SLURM Integration above) — a process/session loss during `sbatch --wait` loses the agent's ability to resume that specific job without external SLURM-side bookkeeping; any adoption of this pattern in IMPRESS-A's own execution layer should add the missing durable job-ID ledger rather than copy the blocking-wait approach as-is.
- **Trajectory tree growth is unbounded** — `Trajectory._nodes` never prunes abandoned branches, which is correct for auditability/backtracking but means a long-running autonomous campaign accumulates memory/storage proportional to total steps ever taken, not just the current path length; worth a bound if adopting this pattern at IMPRESS-A campaign scale.

## Cost per unit of work
Per-Rosetta-call cost is identical to the underlying protocol invoked (`rotamer_change`→FastDesign-class cost, `backbone_change`→small/shear/backrub mover cost, both per `rosetta.md`'s cost figures) times the ensemble width chosen per step (README: 128-candidate MPI ensembles for the two published example tasks). The added cost specific to AgentRosetta is **LLM query cost per agent step** (one or more LLM calls per `run_step()`, with up to `max_query_retries`/`max_parse_retries` retries) plus, for `-slurm` configs, per-step SLURM queue wait on top of the 128-way MPI RosettaScripts job itself. Not independently benchmarked in the refcode; the paper (not fetched in full here) would be the source for reported wall-clock/cost numbers per published task.

## Verdict
**Mine for patterns, do not adopt as a tool.** AgentRosetta is a research prototype (v0.1.0, single-project scope, MIT-licensed) whose direct reuse value is low — it is tightly coupled to its own environment/task/parser abstractions and to litellm/Hydra/Ray choices that may not match IMPRESS-A's stack, and its SLURM integration has a real gap (blocking `--wait` submission, no durable job ledger) relative to what our own P4 execution layer needs. Its **design patterns are directly worth mining**: (1) the tree-structured `Trajectory` with non-destructive `go_back_to_step` is a clean, small (~45-line) backtracking primitive worth reimplementing natively rather than importing; (2) the Pareto-front selection via `paretoset` over named, direction-tagged reward fields is a good template for multi-objective design ranking without collapsing to a scalar reward, and `paretoset` itself is a lightweight, directly-adoptable dependency (not just a pattern to mine) if IMPRESS-A needs the same multi-objective selection; (3) the closed, Pydantic-typed action-enum-with-docstring pattern (rather than open tool-calling) and the explicit bounded parse-retry-with-corrective-feedback loop are both reusable techniques for constraining an LLM's action surface to something structurally validatable. None of the three should be pulled in as a dependency on the `agent-rosetta` package itself; they are load-bearing enough as *ideas* to reimplement natively inside whatever agent-loop code IMPRESS-A already owns.
