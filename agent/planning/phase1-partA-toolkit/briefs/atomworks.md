# AtomWorks

**One-line identity.** The shared structure I/O, preprocessing, and featurization framework that every foundry model (RFD3, RFD3NA, RF3, MPNN) is built on top of — not a design/prediction tool itself, but the plumbing layer none of them can run without.

## Identity
- **Version / release examined:** not vendored in `impress-a-refcodes/tools/` — researched entirely upstream plus inferred from how foundry consumes it. `tools/foundry/pyproject.toml` pins `atomworks[ml]>=2.1.1` as a core dependency (not an optional extra — every foundry model requires it). `tools/foundry/ci-constraints.txt` reveals active, fast-moving releases: it documents that atomworks 2.2.0 capped `torch<2.8`/`rdkit<2025.9`, and that atomworks **2.2.1 lifted both caps**, which broke foundry's CI (pulled in torch 2.12 and rdkit 2026.3.3, both of which broke type-checking) — foundry pins `torch==2.7.1`/`rdkit==2025.3.6` in CI specifically to work around this. This is real evidence of an actively developed, not-yet-fully-stable dependency.
- **Provenance:** RosettaCommons, BSD license (per GitHub listing), public repo `github.com/RosettaCommons/atomworks`. Associated paper: "Accelerating Biomolecular Modeling with AtomWorks and RF3," bioRxiv 2025.08.14.670328 (also cited in `tools/foundry/README.md`'s citation block as `corley2025accelerating`). Announced open-source alongside RF3 in September 2025 (RosettaCommons blog post, fetched via web search).
- **Maturity:** active research infrastructure, pre-1.0-in-spirit despite a 2.x version number — the observed cap/uncap churn between 2.2.0 and 2.2.1 in the same CI-constraints note indicates the API and dependency surface are still moving. Not vendored in the refcodes directory at all — this brief is the one item in this cluster the operating team should expect to need direct upstream tracking for, since IMPRESS-A's own repo has no local copy to diff against.

## Scientific role
Not a problem-class solver — it is the **data/featurization layer** underneath every generate/inverse-fold/predict stage the other four briefs describe. Per `tools/foundry/README.md`: *"All models within Foundry rely on AtomWorks... for both training and inference,"* under a strict dependency flow `foundry → atomworks`. Concretely, from the actual import surface across `tools/foundry` (grepped, real, not invented):
- **`atomworks.io`** — structure parsing (`atomworks.io.parse`, `atomworks.io.parser.parse_atom_array`), CIF/PDB/CCD handling (`atomworks.io.utils.ccd`, `atomworks.io.utils.bonds`), RDKit/ligand tooling (`atomworks.io.tools.rdkit`), and a core `AtomArrayPlus` type (`atomworks.io.utils.atom_array_plus`) built on Biotite's `AtomArray`.
- **`atomworks.ml`** — the transform-pipeline machinery every model's Hydra config instantiates: `atomworks.ml.transforms.{crop,bonds,chirals,sasa,symmetry,atomize,...}`, diffusion-specific transforms (`atomworks.ml.transforms.diffusion.edm`, `.batch_structures`), MSA loading (`atomworks.ml.transforms.msa.msa`, `atomworks.ml.preprocessing.msa.finding`), dataset/sampler infrastructure (`atomworks.ml.datasets.datasets`, `atomworks.ml.samplers`), and encoding definitions consumed directly by RFD3's/MPNN's tokenizers.
It therefore occupies every pipeline stage indirectly (generate, inverse-fold, predict) without occupying any stage directly — it is what turns a PDB/CIF file into the tensors the diffusion/MPNN/structure-prediction networks consume, and what turns a network's raw atom-array output back into a writable CIF.

## Invocation & I/O contract
- **How a unit of work is invoked:** Python API only. No CLI entrypoint for atomworks itself appears in `tools/foundry/pyproject.toml`'s `[project.scripts]` (only `rf3`, `rfd3`, `rfd3na`, `mpnn`, `foundry` are registered) — atomworks is always called *from inside* another model's Hydra-instantiated transform pipeline or directly from Python, e.g. `from atomworks.io import parse`, `from atomworks.io.parser import parse_atom_array`, `import atomworks.ml.datasets`.
- **Inputs:** structure files (PDB/CIF), CCD (Chemical Component Dictionary) entries for ligand/residue chemistry, and — for training-scale dataset construction — a full local PDB mirror plus CCD mirror (per `models/rfd3/README.md`: *"Set up PDB and CCD mirrors as described in the AtomWorks documentation... Set the `PDB_MIRROR` and `CCD_PATH` variables in your `.env` file"*).
- **Outputs:** `AtomArray`/`AtomArrayPlus` objects (in-memory, Biotite-based) for downstream featurization, and CIF files on write-back (`atomworks.io.utils.io_utils.to_cif_file`, used directly by `mpnn/utils/inference.py`).
- **A concrete example**, real code from `tools/foundry/models/mpnn/src/mpnn/utils/inference.py` (imports section — not invented):
  ```python
  from atomworks.io import parse
  from atomworks.io.parser import STANDARD_PARSER_ARGS, parse_atom_array
  from atomworks.io.utils.atom_array_plus import AtomArrayPlus, as_atom_array_plus
  from atomworks.io.utils.io_utils import to_cif_file
  from atomworks.ml.utils.token import get_token_starts, spread_token_wise
  ```
  This is the exact set of atomworks calls MPNN's CLI layer uses to go from a structure-file path to a fully-annotated atom array ready for the model, and back to a CIF on output.

## Compute pattern
- **Pattern:** **P6 (in-process library call)**, for the inference-time role that matters to this project. Structure parsing and per-design featurization are sub-second, in-memory, CPU-side operations invoked synchronously inside an RFD3/MPNN/RF3 process — per the taxonomy's own instruction, this must never become a separately scheduled task; the orchestration overhead would dwarf the work. (Training-time dataset construction against a full PDB/CCD mirror is a heavier, batch-style operation, but that is out of scope for an inference-time autonomous agent and is not something IMPRESS-A would invoke as a unit of work.)
- **GPU vendor portability:** n/a / portable — atomworks itself is a CPU-side numpy/Biotite/RDKit structure-manipulation library; the transform outputs are plain tensors later consumed by GPU models downstream, but no CUDA-specific import was found anywhere in the grepped atomworks import surface (`atomworks.io.*`, `atomworks.ml.*` — all standard Python/numpy/Biotite/RDKit namespaces). GPU vendor choice is entirely determined by whichever model (RFD3/MPNN/RF3) consumes atomworks' output, not by atomworks itself.
- **State model:** stateless per call — parsing a structure or applying a transform pipeline has no persisted state between calls.
- **Data locality:** self-contained for inference-time single-structure parsing (one file in, one AtomArray out); shared-FS required for the training-time PDB/CCD mirror use case (out of scope here).
- **Staging burden:** none for inference-time use beyond what's already implied by the per-structure input file itself. The PDB_MIRROR/CCD_PATH staging (many GB) is a **training-only** burden, not something an inference-time autonomous agent needs to provision.
- **Container availability:** n/a as a standalone item — it ships as a pip dependency inside the same `rosettacommons/foundry` container and `rc-foundry[all]` install that carry the four model briefs; there is no separate atomworks container.

## Deployment on DOE & ACCESS
Not independently deployed — atomworks arrives as a transitive pip dependency of `rc-foundry` on every target platform (Frontier, Aurora, Polaris, ACCESS). Because it is pure-Python/numpy/Biotite/RDKit with no GPU-vendor-specific code, it imposes **no additional platform risk** beyond ordinary Python-wheel availability (RDKit/OpenBabel wheels are widely available for Linux x86_64, which covers all five target machines). The one deployment risk worth flagging explicitly: the observed version churn in `tools/foundry/ci-constraints.txt` (2.2.0 → 2.2.1 breaking type-stub compatibility with torch/rdkit) means an unpinned `atomworks[ml]>=2.1.1` install could pull in an atomworks release that silently expects a newer torch/rdkit than what a given platform's module stack provides — **pin atomworks explicitly in any deployment manifest**, don't rely on the open lower bound in `pyproject.toml`.

## Agentic surface
- **Native MCP:** no. Grepped the entire `tools/foundry` tree (which is where all atomworks *usage* lives, since atomworks itself isn't vendored) for `mcp`/`model context protocol` — zero hits. No upstream MCP server or documentation was found for atomworks in web search either.
- **Parameters worth exposing for autonomous variation:** **n/a — the agent never calls atomworks directly.** It is transitively invoked inside every RFD3/RFD3NA/MPNN call via that model's own Hydra transform-pipeline config (e.g., `occupancy_threshold_sidechain`, `occupancy_threshold_backbone`, `remove_ccds`, `remove_waters` — all real MPNN CLI flags from `models/mpnn/src/mpnn/utils/inference.py` that are in fact pass-throughs into atomworks' structure parser via `STANDARD_PARSER_ARGS`). Those knobs are already covered in the MPNN and RFD3 briefs' parameter tables; there is no separate atomworks-level surface for an agent to reason about.
- **Parameters that must NOT be agent-varied:** n/a for the same reason — nothing here is agent-facing.

## Failure modes & what the agent must check
- **Loud failure:** malformed/corrupt PDB or CIF files raise parse exceptions; a ligand/residue CCD code with no entry in the local CCD mirror/cache raises a lookup error rather than silently degrading.
- **Silent bad output:** the highest-risk category, because atomworks sits upstream of every model in this cluster — bad featurization here produces confidently-wrong downstream designs with no error signal from RFD3/MPNN. Specific risks: incorrect bond-order or protonation-state inference for exotic/novel ligands (RDKit-backed heuristics can guess wrong without raising), occupancy-threshold filtering (`occupancy_threshold_sidechain`/`occupancy_threshold_backbone`) silently dropping atoms a user expected to be present, and multi-occupancy/altloc handling choosing an unexpected conformer. The concrete mitigation already exists in this cluster: RFD3's `prevalidate_inputs=True` flag (see `rfdiffusion3.md`) is explicitly designed to catch input-specification problems — many of which are atomworks-parsing problems in disguise — before a full inference run is spent on bad input. An agent pipeline should treat "did the structure parse into the atom count/composition I expected" as a standard post-parse sanity check, not assume silence means correctness.

## Cost per unit of work
Sub-second to low-single-digit-seconds per structure for parsing + transform-pipeline application on a typical single-chain-to-multi-chain complex (order-of-magnitude estimate; no dedicated atomworks benchmark found upstream or in foundry docs). Negligible relative to the GPU model call it feeds — this is precisely why the taxonomy classifies it P6 rather than a schedulable unit. Training-time PDB-mirror-scale dataset construction is a categorically different, much larger cost that is out of scope for this brief's inference-time framing.

## Verdict
**Core.** AtomWorks is unconditionally load-bearing — the prompt's framing ("strictly depends on") is accurate and verified by the actual import graph: every real code path examined in the RFD3, RFD3NA, and MPNN briefs routes structure I/O and featurization through it, and `foundry`'s own README states the dependency flow as an architectural rule (`foundry → atomworks`), not an incidental choice. The caveat that matters for planning, not for the Core verdict: this is the one dependency in the cluster with no local refcode copy and a documented history of breaking-change releases (2.2.0→2.2.1), so it needs an explicit version pin and change-tracking discipline that the other four briefs' vendored refcodes don't require in the same way.
