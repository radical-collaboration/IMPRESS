# Classical & Generative Docking: AutoDock Vina, GNINA, DiffDock

**One-line identity.** Three structurally different approaches to "predict how a small molecule sits in a protein pocket" — empirical-scoring search (Vina), CNN-rescored search (GNINA), and diffusion-generative pose sampling (DiffDock) — evaluated together because an autonomous agent needs one policy for when (if ever) to reach for any of them instead of Boltz-2's co-folding.

## Identity
- **Version / release examined:** none of the three are vendored in `<workspace>/impress-a-refcodes/tools/` — this entire brief is upstream-sourced, not refcode-grounded. (`ChemGraph`, which *is* in refcodes, wraps AutoDock Vina as an optional docking backend — see `<workspace>/impress-a-refcodes/tools/ChemGraph/src/chemgraph/tools/docking_core.py` and `docking_schema.py` — and is cited below as the one piece of local evidence for how this project's own ecosystem already treats Vina as a callable tool.)
  - **AutoDock Vina:** `ccsb-scripps/AutoDock-Vina`, 1.2.x line, Apache License 2.0.
  - **GNINA:** `gnina/gnina`, v1.3 examined (2025 paper, *J. Cheminform.*), a Vina fork augmented with 3D CNNs; dual-licensed GPL/Apache — GPL only if compiled with Open Babel linked in, Apache-only build is possible by removing that dependency.
  - **DiffDock:** `gcorso/DiffDock`, MIT license, ICLR 2023 origin (Corso et al., "Diffusion Steps, Twists, and Turns for Molecular Docking").
- **Maturity:** Vina — production, the field's default baseline for two decades. GNINA — active research/production hybrid, actively maintained with a 2025 major release (1.3). DiffDock — active research; widely cited and reused (HuggingFace Spaces, NVIDIA NIM/BioNeMo packaging exists) but the tool itself sits closer to "research artifact with strong adoption" than "hardened production pipeline."

## Scientific role
All three serve **small-molecule binding** exclusively. Pipeline stage: **predict pose** (+, with caveats below, **score**). None of the three do inverse design or generation of the *protein*; they take a fixed (or near-fixed) receptor and a candidate ligand and try to find where/how it binds. This is the same problem class Boltz-2 addresses via joint co-folding, which is precisely why this brief exists as a comparison rather than three independent entries.

## Invocation & I/O contract
- **AutoDock Vina** — CLI (`vina --receptor r.pdbqt --ligand l.pdbqt --center_x .. --size_x .. --exhaustiveness 8`) or Python bindings (`pip install vina`, `from vina import Vina`). Inputs: receptor + ligand as **PDBQT** (AutoDock's atom-typed, partial-charge-annotated format — neither plain PDB nor SDF; this is exactly the Open Babel/Meeko preparation step covered in `cheminformatics-io.md`), plus a search-box center/size. Output: ranked poses (PDBQT/SDF) each with a Vina score (kcal/mol, an empirical scoring-function value, **not a calibrated free energy**). `ChemGraph`'s wrapper shows the real call shape: `v.dock(exhaustiveness=params.exhaustiveness, n_poses=params.n_poses)` then `v.energies(n_poses=params.n_poses)` (`docking_core.py:264-268`), with ligand PDBQT built via RDKit (`Chem.AddHs` + `AllChem.EmbedMolecule` + `AllChem.MMFFOptimizeMolecule`) piped through Meeko's `MoleculePreparation`/`PDBQTWriterLegacy` (`docking_core.py:70-97`) — i.e., in practice Vina is never called on raw SMILES, it's always downstream of an RDKit+Meeko prep chain.
- **GNINA** — CLI, largely Vina-compatible flag surface plus CNN-specific flags (`--cnn_scoring`, `--cnn <model-name>`). Inputs/outputs: same PDBQT-centric contract as Vina (it is architecturally a Vina fork). Adds CNN pose/affinity rescoring on top of the empirical search.
- **DiffDock** — CLI/Python, `python -m inference --protein_ligand_csv data/protein_ligand_example_csv.csv --out_dir results/... --inference_steps 15 --samples_per_complex 10 --batch_size 10 --actual_steps 18 --no_final_step_noise` (from upstream `inference.py` usage). Inputs: a **raw receptor PDB and a ligand SMILES or SDF** — critically, **no search box, no pocket definition required** (blind docking by construction: DiffDock is "a diffusion model that predicts binding poses... anywhere inside or on the target protein's surface is a potential binding site"). Requires ESM2 protein-language-model embeddings (`esm2_t33_650M_UR50D`) as a precomputed input to the receptor representation. Output: ranked poses (SDF) with a model **confidence score**, not a physical energy.

## Compute pattern
- **AutoDock Vina:** **P2 (primary)** — CPU multi-threaded local search (`--cpu` flag), embarrassingly parallel across independent ligand-receptor pairs, the textbook P2 case ("Rosetta `nstruct` ensembles" analog for docking). **P1 (secondary)** via GPU forks: **AutoDock-GPU** (`ccsb-scripps`-adjacent, official GPU port) is available in both **OpenCL and CUDA** builds and documented to run "on CPU, GPU, and FPGA architectures" with up to ~350x speedup over single-threaded CPU; **Vina-GPU / Vina-GPU 2.0 / 2.1** (`DeltaGroupNJUPT`, third-party) is an OpenCL implementation reporting ~65.6x acceleration over base Vina in virtual-screening benchmarks. **The OpenCL path is the one genuinely portable GPU story in this entire cluster** — OpenCL runs on AMD and Intel GPUs as well as NVIDIA, unlike the CUDA-only norm elsewhere in this toolkit; worth flagging as a Frontier/Aurora-friendly option if GPU-accelerated docking throughput is ever needed.
- **GNINA:** **P1 (primary)** — CNN pose/affinity scoring is a GPU forward pass through an ensemble of 3D CNNs (default ensemble: `dense_1_3`, `dense_1_3_PT_KD_3`, `crossdock_default2018_KD_4`); CPU execution is supported but is the documented slow path (reported on the order of ~4x slower per complex without a GPU in the tool's own benchmarking discussion). **GPU vendor portability: CUDA-only**, no evidence of a HIP/ROCm or SYCL/XPU port found — GNINA's CNN backend (built on a Caffe-derived / libmolgrid stack) is architecturally CUDA-coupled, unlike Vina's portable-OpenCL GPU forks.
- **DiffDock:** **P1** — a PyTorch diffusion model; GPU is the practical requirement for the reverse-diffusion sampling loop across `samples_per_complex` poses, plus a separate P1-shaped forward pass to compute ESM2 embeddings for the receptor. **GPU vendor portability: CUDA-primary**, plain-PyTorch base like Boltz/RF3/Chai in this toolkit's other briefs — HIP/XPU port unverified, same "smoke-test, don't assume" posture as those tools.
- **State model:** all three stateless per call (no persistent process state across separate docking runs).
- **Data locality:** self-contained per job (receptor + ligand + optional precomputed embeddings); no shared reference database required at run time (contrast with AF2/AF3's genetic databases).
- **Staging burden:** Vina — none (no weights). GNINA — CNN model weights bundled/downloaded with the tool, small (single-digit GB range for the model zoo, not independently verified to an exact figure here — treat as an assumption pending direct measurement). DiffDock — score-model + confidence-model checkpoints plus the separate ESM2 `esm2_t33_650M_UR50D` weights (~2.5 GB for that ESM2 model size, a well-known public artifact) that must be staged before the receptor-embedding step can run at all.
- **Container availability:** Vina — community (conda-forge `vina`, widely packaged). GNINA — community (project ships prebuilt binaries and there are community Docker images; no first-party Apptainer image confirmed). DiffDock — community only (various academic/HuggingFace Docker/Space builds, `labdao/diffdock` community packaging); no official container.

## Deployment on DOE & ACCESS
- **Vina (CPU path):** deploys everywhere without qualification — Frontier, Aurora, Polaris, and every ACCESS machine all have the CPU cores Vina needs; this is the *safest* tool in this brief from a portability standpoint.
- **Vina-GPU/AutoDock-GPU (OpenCL path):** plausible on Frontier (AMD, ROCm has OpenCL support) and Aurora (Intel, oneAPI has OpenCL support) in principle since OpenCL is vendor-neutral by design, but **unverified in this pass** — no direct evidence of anyone running these specific forks on MI250X or PVC hardware was found; treat as a research spike.
- **GNINA:** Polaris/ACCESS (CUDA) — straightforward. Frontier/Aurora — **not expected to run** without a from-scratch ROCm/SYCL port of its CNN backend; no such port found. State this plainly as a platform gap rather than an assumed workaround.
- **DiffDock:** Polaris/ACCESS (CUDA) — straightforward, matches its PyTorch/CUDA-primary design. Frontier/Aurora — same unverified-but-plausible-via-plain-PyTorch situation as Boltz-2/RF3 elsewhere in this toolkit; not validated here.
- **License gates:** none block deployment (Apache-2.0, GPL/Apache dual, MIT are all fine for a research HPC context); GNINA's GPL exposure is only relevant if Open Babel is statically linked into a distributed binary, not for running it as a standalone tool on an allocation.

## Agentic surface
- **Native MCP:** no first-party MCP server found for any of the three. `ChemGraph` (refcode: `tools/ChemGraph/`) exposes Vina docking as a LangChain `@tool`-wrapped function (`molecular_docking` in `chemgraph/tools/docking_tools.py`, backed by `docking_core.py`) rather than an MCP server — a different agent-integration pattern (tool-calling framework, not MCP), noted here because it's the one real "agent already talks to a docking tool" example in this project's own reference codebases. Downgrade to **community/unverified** rather than "no" only for Vina given this concrete (if non-MCP) integration precedent; GNINA and DiffDock have no agentic wrapper found at all.
- **Parameters worth exposing for autonomous variation:**

| Tool | Parameter | Type | Sane range | Default | Trade-off |
|---|---|---|---|---|---|
| Vina/GNINA | `exhaustiveness` | int | 8-32 (64+ for hard targets) | 8 | Higher → more consistent/reliable top pose across repeated runs, linear-ish cost increase; `ChemGraph`'s own schema description: "higher = more thorough" (`docking_schema.py:29`) |
| Vina/GNINA | `num_modes` / `n_poses` | int | 5-20 | 9 (Vina) | More retained poses → better chance the true pose is *somewhere* in the output, more for the agent's downstream filter to sift |
| Vina/GNINA | `energy_range` | float, kcal/mol | 1-5 | 3.0 | Widens/narrows the score window of retained poses relative to the best one |
| GNINA | `--cnn_scoring` mode | enum (`none`/`rescore`/`refinement`/`all`) | n/a | `rescore` (per version) | Controls how much the CNN reshapes vs. merely re-ranks the Vina-generated poses; heavier settings cost more GPU time |
| DiffDock | `inference_steps` / `actual_steps` | int | 15-40 | ~20 (paper); example CLI uses 15 with `actual_steps 18` | More denoising steps → smoother reverse-diffusion trajectory, roughly linear cost |
| DiffDock | `samples_per_complex` | int | 5-40 | 10 | More independent samples → better mode coverage of the pose landscape (this is DiffDock's analog of Vina's `exhaustiveness`), linear GPU cost |

- **Parameters that must NOT be agent-varied:** the **receptor rigidity assumption** for Vina/GNINA (both treat the receptor as effectively rigid by default; side-chain flexibility is opt-in and expensive) should be a deliberate per-target decision, not something silently defaulted — a rigid-receptor pose against an induced-fit binding site will confidently report a plausible-looking pose against the wrong (unrelaxed) geometry. For DiffDock, `samples_per_complex` should never be driven to 1 for anything the agent intends to trust — single-sample diffusion output has no internal consistency check and the confidence score alone is a weak single-sample signal.

## Failure modes & what the agent must check — and the central finding of this brief
**Classical docking scoring functions correlate poorly with experimental binding affinity, and an autonomous agent that treats a Vina/GNINA score as a real free energy will make bad decisions.** The numbers, from the CASF-2016 benchmark (the field's standard comparative-assessment dataset):
- **Scoring power** (correlation between predicted score and experimental affinity across a diverse, non-congeneric set): AutoDock Vina's Pearson correlation coefficient is **≈0.6** — a moderate, not strong, correlation, and CASF-2016 complexes are curated/high-quality crystal structures, a *best case* relative to real prospective screening.
- **Docking power** (can the scoring function pick the near-native pose, RMSD < 2 Å, out of a decoy set and rank it first): Vina is actually the **best-performing classical scoring function on this specific metric**, ~90.2% top-1 success — so Vina is meaningfully good at "which of these candidate geometries looks right," which is a different and weaker claim than "how tightly does this ligand bind."
- **GNINA's CNN layer** improves pose *selection* (docking power) by rescoring Vina's generated poses with a learned 3D-CNN signal, but does not fix the fundamental scoring-power gap for affinity ranking — CNN rescoring is a pose-discrimination tool, not a validated affinity predictor, and should be treated accordingly.
- **DiffDock generalizes poorly outside its training distribution.** On the PoseBusters benchmark (built specifically to exclude any complex present in training data for any evaluated method), DiffDock's success rate was **~12%**, well behind classical Vina/Glide-style methods on the same held-out set — and independent analysis found many PDBBind test cases have near-identical training analogs, with success rates dropping by roughly **40 percentage points** on truly novel complexes with no training-set analog. DiffDock's headline benchmark numbers should be read as an upper bound achieved partly through train/test leakage, not as the expected performance on a genuinely novel target.
- **What docking IS good for:** cheap, fast, CPU-viable (Vina) pose generation and gross geometric filtering — "does this ligand fit in this pocket in a chemically sane orientation" — and virtual-screening-scale triage across very large compound libraries where running a full co-folding model per candidate is not affordable.
- **What docking is NOT good for:** trusting the numeric score as an affinity estimate for accept/reject decisions, or as a ranking signal across chemically diverse candidates where scoring-power's ≈0.6 correlation dominates the decision.
- **Loud failure:** malformed PDBQT, missing search-box parameters (Vina/GNINA), missing ESM embeddings (DiffDock) — all raise/exit non-zero.
- **Silent bad output:** a docked pose with a favorable-looking score but wrong induced-fit geometry (rigid-receptor artifact); a DiffDock pose with high confidence on an out-of-distribution target (per PoseBusters, confidence is not a reliable generalization signal); any Vina/GNINA score treated as a real ΔG. **Specific check:** never gate an accept/reject or ranking decision on a raw docking score alone — use docking output as a pose/pocket-compatibility filter, and route anything that clears that filter through Boltz-2 (or another co-folding affinity head) for the actual affinity judgment.

## Cost per unit of work
- **Vina (CPU, default `exhaustiveness=8`):** seconds to ~1-2 minutes per ligand-receptor pair on a modern multi-core node; scales roughly linearly with `exhaustiveness`. Resource shape: single node, N CPU cores (`--cpu`), no GPU required.
- **GNINA:** on the order of ~30 s/complex with GPU-accelerated CNN scoring vs. multiple times longer CPU-only, per the tool's own reported benchmarking discussion (treat as approximate, not independently reproduced here). Resource shape: 1 GPU.
- **DiffDock:** GPU-minutes per complex (diffusion sampling across `samples_per_complex` × `inference_steps`), plus a one-time-per-receptor ESM2 embedding cost. Resource shape: 1 GPU; ESM2 embedding step is itself a P1 forward pass that can be cached and reused across many ligands against the same receptor.
- **Checkpointable:** all three are stateless single-shot jobs — no mid-run resume; re-running is the only "recovery" path, which is cheap for Vina and moderately expensive for GNINA/DiffDock.

## Verdict
**Recommended (Vina, GNINA) as a cheap pre-filter; Defer (DiffDock).** The honest finding of this brief: **Boltz-2's co-folding + affinity head (see `boltz.md`, Core in this toolkit) largely obviates classical docking for this project's actual decision-making needs.** Boltz-2 predicts structure *and* a trained affinity estimate jointly from sequence + SMILES with no pre-existing receptor structure or binding-box definition required, approaching FEP-level accuracy per its own reporting — a fundamentally stronger claim than anything Vina/GNINA/DiffDock offer, whose scoring-power ceiling (PCC ≈ 0.6 on a *curated* benchmark) is not competitive as an affinity signal. Where docking still earns a place: **Vina specifically**, as a near-zero-cost, CPU-only, no-GPU-required geometric pre-filter ahead of a more expensive Boltz-2 call, and as the only viable option at virtual-screening scale (millions of compounds) where running Boltz-2 per candidate is not affordable — use its docking-power strength (pose plausibility, ~90% top-1 success at RMSD<2Å) and never its scoring-power weakness. **GNINA** earns a place only where a GPU is already available and its CNN pose-rescoring is used to *improve which poses survive to the Boltz-2 stage*, not as an affinity source. **DiffDock is Defer**: its blind-docking convenience (no pocket definition needed) is real, but its PoseBusters generalization collapse (12% success, ~40-point drop on truly novel targets) means it cannot currently be trusted for genuinely novel enzyme/binder targets — which is this project's actual use case — and Boltz-2 already covers the "no pre-defined pocket" use case better via full co-folding. Revisit DiffDock if a future version demonstrably closes the PoseBusters generalization gap.
