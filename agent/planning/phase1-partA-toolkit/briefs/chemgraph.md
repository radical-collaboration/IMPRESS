# ChemGraph

**One-line identity.** A LangGraph-based agentic framework for computational chemistry/materials workflows (ASE, MACE, gRASPA, XANES) that is not itself a protein-design tool, but whose HPC-aware MCP server implementation is the most directly transferable design artifact found anywhere in this toolkit sweep.

- **Version / release examined:** `tools/ChemGraph/pyproject.toml` — `name = "chemgraph"`, `version = "0.7.0"`, `requires-python = ">=3.11"`. Pinned core deps: `langgraph==1.2.11`, `langgraph-checkpoint==4.2.0`, `langgraph-checkpoint-sqlite==3.1.1`, `langchain==1.4.0`, `langchain-core==1.6.1`, `langchain-anthropic==1.5.4`, `langchain-mcp-adapters==0.3.0`, `mcp==1.28.1`, `fastmcp==3.4.4`.
- **Provenance:** Argonne National Laboratory (Thang Pham, Murat Keçeli, Aditya Tanikanti). Apache-2.0 license (`license = "Apache-2.0"`, PEP 639 expression). Refcode: `tools/ChemGraph/` (full repo — `src/chemgraph/`, `examples/`, `notebooks/`, `scripts/`, `tests/`).
- **Maturity:** active research software, `Development Status :: 4 - Beta` per its own PyPI classifier. Real breadth: 13 distinct LangGraph topologies, a full execution-backend abstraction with 4 concrete backends, 13 MCP server modules (3,704 total lines), an in-house Academy-based multi-agent runtime, CLI, Streamlit UI, and an eval harness (`src/chemgraph/eval/`). Version-pinned (not floor-pinned) core LLM/graph dependencies indicate active, deliberate compatibility management rather than a stale prototype.

## Scientific role
**Not a protein-design tool** — briefed here as prior art and a possible dependency, per this project's explicit framing. ChemGraph targets computational chemistry and materials science: ASE-driven geometry optimization/MD, MACE machine-learning interatomic potentials, gRASPA (Monte Carlo gas adsorption), XANES spectroscopy prediction, optical chemical structure recognition (OCSR), and RAG over chemistry literature. None of the four in-scope IMPRESS-A problem classes (stability, de novo binder design, enzyme/catalytic design, small-molecule binding) are addressed by ChemGraph's own tool set — its relevance to this project is entirely architectural: how it wires an LLM agent to real HPC execution through LangGraph and MCP.

## Invocation & I/O contract
- **How a unit of work is invoked:** two distinct surfaces, both real:
  1. **LangGraph agent invocation** — `construct_single_agent_graph(llm, system_prompt=..., tools=[...], human_supervised=False, ...)` (`src/chemgraph/graphs/single_agent.py:448`) returns a compiled `StateGraph` invoked the standard LangGraph way (`graph.invoke({"messages": [...]}, config={"configurable": {"thread_id": ...}})`).
  2. **MCP server invocation** — each HPC tool module (e.g. `src/chemgraph/mcp/mace_mcp_hpc.py`) is a standalone `CGFastMCP` server launched via `run_mcp_server(mcp, default_port=9004)` (`src/chemgraph/mcp/server_utils.py`), registering tools like `run_mace_single`/`run_mace_ensemble` that any MCP client (including a LangGraph agent via `langchain-mcp-adapters`) can call over stdio or HTTP.
- **Inputs:** natural-language task descriptions (LangGraph path) or structured Pydantic schemas per MCP tool (e.g. `mace_input_schema`, `mace_input_schema_ensemble` in `src/chemgraph/schemas/`) — atomic structure files (XYZ/CIF/PDB via ASE), SMILES strings, or pre-staged remote paths.
- **Outputs:** JSON result dicts (energies in eV, wall times in seconds per the MACE server's own tool instructions), written result files, or — for async-remote backends — a `batch_id` to poll.
- **A concrete example**, real, from `src/chemgraph/mcp/mace_mcp_hpc.py:350-368`:
  ```python
  mcp.tool(name="run_mace_single", description="Run a single MACE calculation",
            processes_per_node=_args.ppn, gpus_per_task=_args.ngpus_per_process)(run_mace_single)
  mcp.schema_fanout_tool(name="run_mace_ensemble", worker=_mace_worker,
            processes_per_node=_args.ppn, gpus_per_task=_args.ngpus_per_process)(run_mace_ensemble)
  mcp.init_backend(tracker_kwargs={"persist_file": _JOBS_FILE})
  run_mcp_server(mcp, default_port=9004)
  ```

## LangGraph architecture
- **Core pattern** (`src/chemgraph/graphs/single_agent.py`): `StateGraph(State)` with an `ChemGraphAgent` LLM node bound to tools via `llm.bind_tools(tools=tools)`, a `ToolNode(tools=tools)` execution node, and `add_conditional_edges` routing driven by `route_tools`/`route_after_tools` functions that inspect the last message's `tool_calls`. Two real anti-pattern guards worth noting as transferable ideas: `_is_repeated_tool_cycle()` detects when the LLM emits the *same* tool-call signature twice in a row (a stuck-loop signature match on `(name, sorted(args.items()))` tuples) and routes to `"done"` instead of looping forever; `route_after_tools(state, terminal_tool_names)` lets specific tools (e.g. a final-report generator) terminate the graph immediately after successful execution rather than looping back to the LLM.
- **~13 distinct graph topologies** in `src/chemgraph/graphs/`: `single_agent.py` (core geometry-optimization graph, with optional `structured_output` via a `ResponseAgent` retry-on-parse-failure loop, and optional `generate_report` via a second `ReportAgent`/`report_tools` sub-loop), `multi_agent.py`, `deep_agent.py`, `main_agent.py`, `mock_agent.py`, `graspa_agent.py`, `graspa_mcp.py`, `molecular_docking.py`, `ocsr_agent.py`, `python_relp_agent.py`, `rag_agent.py`, `single_agent_iri.py`, `single_agent_xanes.py`. Twelve of the 13 files define their own `construct_*` graph-builder function (verified via grep for `^def construct`); `multi_agent.py` composes sub-graphs rather than defining a single top-level constructor.
- **Human-in-the-loop**: `ask_human` tool (`src/chemgraph/tools/generic_tools.py:68-92`) calls `langgraph.types.interrupt({"question": question})` — a real LangGraph interrupt, not a placeholder — added to the tool list whenever `human_supervised=True` is passed to `construct_single_agent_graph`/`ChemGraphAgent`.
- **Checkpointing**: `langgraph-checkpoint-sqlite==3.1.1` pinned as a core (non-optional) dependency. `src/chemgraph/cli/checkpoint_runtime.py` implements "single-loop ownership for asynchronous local LangGraph checkpointers" — `open_sqlite()`/`close_sqlite()` wrap `langgraph.checkpoint.sqlite.aio.AsyncSqliteSaver` over an `aiosqlite` connection, default DB at `~/.chemgraph/checkpoints.db`. `construct_single_agent_graph`'s `checkpointer` parameter defaults to a fresh `MemorySaver()` but accepts `None` explicitly ("so it inherits the parent graph's checkpointer" — real docstring, for subgraph embedding) or a caller-supplied durable checkpointer.

## Execution backend / TaskSpec abstraction
`src/chemgraph/execution/base.py` defines the two core abstractions every MCP HPC server and workflow manager is built on:
- **`TaskSpec`** (Pydantic `BaseModel`): `task_type: Literal["python", "shell"]`, `callable`/`args`/`kwargs` (Python mode) or `command`/`working_dir`/`stdout`/`stderr` (shell mode), plus advisory resource hints `num_nodes`, `processes_per_node`, `gpus_per_task`, `env`.
- **`ExecutionBackend`** (ABC): lifecycle `initialize(system, **kwargs)` → `submit(task) -> Future` / `submit_batch(tasks)` → `shutdown()`, context-manager-compatible. Two properties are the key abstraction the whole MCP layer is built around:
  - **`is_async_remote: bool`** (default `False`) — "When `True`, MCP tools should return immediately after submission and provide separate status/result retrieval tools instead of blocking until completion" (verbatim docstring). This is the exact flag that decides whether an MCP tool call blocks synchronously or returns a `batch_id`.
  - **`shares_filesystem: bool`** (default `True`) — decides whether a path written by the submitting server is directly readable by the worker; `GlobusComputeBackend` overrides this to `False` (`src/chemgraph/execution/globus_compute_backend.py:62`, `self._shares_filesystem = bool(kwargs.get("shares_filesystem", False))`), which is what forces the inline-structure-embedding transport path described below.
- **Four concrete backends** (`SUPPORTED_BACKENDS = ("parsl", "ensemble_launcher", "globus_compute", "local")`, `src/chemgraph/execution/config.py:28`), selected via `CHEMGRAPH_EXECUTION_BACKEND` env var or `config.toml`'s `[execution]` section, with target system chosen independently via `COMPUTE_SYSTEM` (`"polaris"`, `"aurora"`, `"crux"`, `"local"`): `LocalBackend` (`local_backend.py`), `ParslBackend` (`parsl_backend.py`), `GlobusComputeBackend` (`globus_compute_backend.py`, the only one with `is_async_remote=True` and `shares_filesystem=False` by default), `EnsembleLauncherBackend` (`ensemble_launcher_backend.py`).
- **HPC configs** (`src/chemgraph/hpc_configs/`): `polaris_parsl.py`/`aurora_parsl.py`/`crux_parsl.py`/`local_parsl.py`, each returning a `parsl.config.Config` with a `HighThroughputExecutor` + `LocalProvider` + `MpiExecLauncher`, sized from live scheduler state — e.g. `polaris_parsl.py` reads `$PBS_NODEFILE` to set `nodes_per_block`, `available_accelerators=4`; `aurora_parsl.py` similarly reads `$PBS_NODEFILE` (raising `ValueError` rather than silently defaulting, unlike Polaris's soft fallback to 1 node) and sets `available_accelerators=12`, `max_workers_per_node` from `CHEMGRAPH_PARSL_MAX_WORKERS_PER_NODE` (default 9), and `address_by_interface('bond0')` — real, PBS-Pro-specific, Aurora-specific plumbing, not a generic template.

## The MCP implementation — the most valuable artifact here
`src/chemgraph/mcp/` (13 modules, 3,704 lines) demonstrates, concretely, how to expose a long-running HPC job through a synchronous-looking MCP tool interface. Three pieces compose the pattern:

1. **`CGFastMCP`** (`cg_fastmcp.py`, subclasses `mcp.server.fastmcp.FastMCP`) — every tool registered via `mcp.tool(...)` is auto-wrapped: the decorated function's call is packaged into a `TaskSpec`, submitted to the backend, and its `Future` awaited (`asyncio.wrap_future(fut)`) **if `backend.is_async_remote` is `False`** — but if `True`, the wrapper instead calls `submit_or_gather(...)` and returns immediately with tracking info, without the tool author writing any of that branching logic themselves. Two additional decorators generalize this to fan-out: `ensemble_tool` (tool schema becomes `list[Schema]`, one `TaskSpec` per list item) and `schema_fanout_tool` (tool schema stays as one ensemble object; an "expander" function server-side turns it into N per-item `TaskSpec`s dispatched to a shared "worker" callable) — this is how `run_mace_ensemble` fans a directory of structures out to N independent backend tasks while presenting the LLM with one tool call.
2. **`JobTracker`** (`job_tracker.py`) — thread-safe, in-memory batch/task tracking with **disk persistence** (`persist_file` JSON, atomic write via `tmp.replace()`) so job state survives an MCP server restart. `get_status(batch_id)` resolves live `Future`s, or (for tasks reloaded from disk with no in-memory future) queries the Globus Compute client directly by `globus_task_id` for genuinely durable cross-session job tracking. `get_results(batch_id, include_partial=False)` returns a "N of M still pending, call check_job_status" message rather than blocking, unless `include_partial=True`.
3. **Standard job-management tool set**, auto-registered by every `CGFastMCP` instance (`_register_job_tools`, `cg_fastmcp.py:204-245`): `check_job_status(batch_id)`, `get_job_results(batch_id, include_partial)`, `list_jobs()`, `cancel_job(batch_id)`, `check_endpoint_status()`. Every HPC-backed MCP server in this codebase (`ase_mcp_hpc.py`, `mace_mcp_hpc.py`, `graspa_mcp_hpc.py`, `xanes_mcp_hpc.py`, and their `_parsl.py` siblings which target Parsl specifically rather than a generic backend) gets this same submit/poll surface for free — an LLM agent (or an autonomous outer loop, in our case) sees a uniform `submit → {check_job_status | get_job_results} → cancel_job` contract regardless of which backend or which scientific tool is behind it.

**Transport concern is deliberately isolated from tool logic** — e.g. `mace_mcp_hpc.py`'s `_mace_transport_hook` (a `set_pre_submit_hook` callback) rewrites the outgoing `TaskSpec` to embed an inline structure (`_embed_inline_if_local`) when `not _backend_shares_fs()`, or leave a path untouched when the backend does share a filesystem — the tool author's own `run_mace_single`/`_mace_worker` functions never branch on backend type at all. This directly matches the taxonomy's P4 concern in this project (external HPC job, durable job-tracking store) and is worth mining as a design pattern even though ChemGraph's own tools are out of scientific scope.

## Compute pattern
- **Pattern:** ChemGraph is a **framework**, not a single tool with one compute pattern — its own graph/agent-invocation layer is P6 (in-process LangGraph execution, sub-second per node transition), while every MCP HPC server built on `CGFastMCP` is **P4 (external HPC job) when `is_async_remote=True`** (Globus Compute backend) or **P1/P2 (in-job GPU/CPU)** when using Parsl/local/ensemble-launcher backends against an already-held allocation. The `is_async_remote` property is, in effect, ChemGraph's own internal implementation of this project's P1-vs-P4 distinction — a directly reusable design decision, not just a coincidental label match.
- **GPU vendor portability:** n/a at the framework level (ChemGraph orchestrates; it doesn't compute). The underlying scientific tools it wraps (MACE via `mace-torch`, ASE calculators) are PyTorch-based and therefore inherit whatever CUDA/HIP/XPU support their own PyTorch build provides — not independently verified here since MACE/ASE are out of this project's scope.
- **State model:** checkpointable at the LangGraph level (SQLite checkpointer, durable across process restarts) and at the job-tracking level (`JobTracker`'s `persist_file`); not restart-required by design for either subsystem.
- **Data locality:** `shares_filesystem` is an explicit, first-class backend property (not an assumption) — ChemGraph is unusually disciplined about this compared to most tools surveyed in this toolkit, and treats it as something every MCP tool's transport logic must branch on rather than something baked into deployment scripts.
- **Staging burden:** MACE foundation-model weights (`model` field, e.g. `medium-mpa-0`), ASE/MACE Python environment. Not independently sized here (out of scope).
- **Container availability:** not established in this sweep — no Dockerfile found under a quick pass of `tools/ChemGraph/` root; k8s manifests exist (`tools/ChemGraph/k8s/`) suggesting a containerized deployment path exists for the Streamlit/agent-serving side, not independently verified for the MCP HPC servers specifically.

## Failure modes & what the agent must check
- **Loud failure:** `TaskSpec` validation (Pydantic) rejects malformed task specs at construction. Missing Globus Compute credentials fail the `_get_gc_client()` lazy-init with a caught, logged warning (not a crash) — `JobTracker.get_status` degrades to "cannot recover this task's result" rather than raising.
- **Silent bad output / degraded state ChemGraph's own code explicitly defends against:**
  - **Orphaned tasks on reload**: `JobTracker._load()` explicitly flags tasks reloaded from disk with neither a `globus_task_id` nor a cached `result` as orphaned ("their results cannot be recovered") and logs a warning naming up to 5 examples — a real, named failure mode of the async-remote job-tracking pattern: if the MCP server restarts *before* a submitted Globus Compute task's UUID was captured (a 3-second best-effort wait window, `_wait_for_globus_task_ids(timeout=3.0)`), that task's outcome is permanently unrecoverable. This is directly relevant to any P4 job-tracking design our own agent builds — the capture-then-persist race is real and ChemGraph's own code promotes it from a debug log to a warning specifically so it isn't missed.
  - **Repeated tool-call cycles**: `_is_repeated_tool_cycle()` in `single_agent.py` is itself a defense against a silent LLM failure mode (the agent loops on an identical tool call indefinitely) — worth adopting as a generic guard in any agent loop we build, not just for this project's oracle-in-the-loop design.

## Verdict
**Mine for patterns; do not adopt as a runtime dependency, and do not run alongside.** ChemGraph solves a different scientific problem (computational chemistry/materials, not protein design) and adopting it as a dependency would import a large, actively-changing LangGraph/LangChain-pinned surface (`langgraph==1.2.11`, `langchain==1.4.0`, plus Academy/Globus/Parsl extras) for zero protein-design capability. The value is entirely architectural and should be captured as design guidance for our own agent, specifically: (1) `CGFastMCP`'s auto-wrap-into-`TaskSpec`-with-`is_async_remote`-branching pattern for exposing HPC jobs as MCP tools, (2) `JobTracker`'s disk-persisted batch/task tracking with the orphaned-task failure mode explicitly named, (3) the `shares_filesystem` backend property as a first-class transport decision rather than an assumption, and (4) the repeated-tool-call-cycle guard. None of these require running ChemGraph itself — they are patterns to re-implement directly against this project's own tool set, informed by having read ChemGraph's real, working code rather than inventing the pattern from scratch.
