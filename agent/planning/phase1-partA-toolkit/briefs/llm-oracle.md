# LLM Oracle (remote frontier APIs, ANL Argo/ALCF gateways, self-hosted vLLM)

**One-line identity.** The external heavyweight LLM that IMPRESS-A's control mode B hands reasoning to — not a scientific tool but a P5 infrastructure dependency, reachable inline from any target compute node given the full-outbound-HTTPS assumption this project's taxonomy already establishes.

This brief is evidence-based where evidence exists in `impress-a-refcodes/` — specifically `tools/ChemGraph/`, which vendors real, working provider-endpoint adapters for Argo (Argonne's internal LLM gateway) and ALCF's hosted inference endpoints — and WebSearch-derived for pricing, current model availability, and rate-limit/determinism behavior, which are all time-sensitive facts no refcode can carry.

## Identity
- **Version / release examined:** no single "version" — this brief covers a pattern plus three concrete access paths found in evidence: (1) direct provider APIs (Anthropic, OpenAI, Google), (2) ANL's **Argo** gateway (`tools/ChemGraph/src/chemgraph/models/endpoints/argo.py`), (3) **ALCF inference endpoints** (`tools/ChemGraph/src/chemgraph/models/endpoints/alcf.py`), (4) self-hosted **vLLM** (`tools/ChemGraph/src/chemgraph/models/endpoints/vllm.py`).
- **Provenance:** Anthropic, OpenAI, Google (direct APIs, commercial, each with its own ToS); Argo — Argonne National Laboratory internal service (`apps.inside.anl.gov/argoapi`, ANL-network/credential-scoped); ALCF inference endpoints — Argonne Leadership Computing Facility (`inference-api.alcf.anl.gov`, Globus-authenticated, ALCF-account-scoped); vLLM — Apache-2.0, `vllm-project/vllm`.
- **Maturity:** direct provider APIs — production, the industry-standard access path. Argo/ALCF — production ANL infrastructure with real, versioned adapter code in ChemGraph (not a prototype integration: `argo.py` has a documented, actively-maintained model-name mapping covering GPT-4o through GPT-5.6 and Claude Opus 4.1 through Claude Sonnet 5, i.e. current as of this writing). vLLM — production, the de facto standard OSS inference server.

## Scientific role
Not a scientific tool — it is the reasoning layer IMPRESS-A's design explicitly names ("control mode B hands reasoning to an external heavyweight LLM"). Occupies an **analyze/decide** role that sits above every other tool in this toolkit: interpreting intermediate structural/scoring output, proposing the next design move (which mutations to shortlist, which backbone to regenerate, when to pivot problem framing), and synthesizing multi-tool state into a decision an autonomous outer loop acts on. Applies across all four problem classes uniformly, as orchestration infrastructure rather than a problem-class-specific tool.

## Invocation & I/O contract

### Direct provider APIs
HTTPS POST, JSON in/out. Anthropic Messages API, OpenAI Chat Completions API, Google Gemini API — each with its own wire format; a provider-abstraction layer (see below) is what lets an agent treat these uniformly.

### Argo (ANL internal gateway) — verified from refcode
`tools/ChemGraph/src/chemgraph/models/endpoints/argo.py` implements **two protocols behind one prefix**: Claude-prefixed `argo:` models route through **Anthropic-native** transport (`is_argo_anthropic_model`, base URL `https://apps.inside.anl.gov/argoapi`, `ChatAnthropic`-compatible, `client_kwargs` include `max_tokens=4000`, `streaming=True`); all other `argo:` models (GPT, Gemini, o-series) route through **OpenAI-compatible** transport (base URL `https://apps.inside.anl.gov/argoapi/v1`). A real, live-maintained model map (`ARGO_MODEL_MAP`, lines 44–83) translates friendly names to Argo's internal wire names, e.g. `"argo:claude-sonnet-5": "claudesonnet5"`, `"argo:gpt-5.6-luna": "gpt56luna"`, `"argo:gemini-3.5-flash": "gemini35flash"` — this confirms Argo currently proxies Claude, GPT, and Gemini families behind one ANL-operated gateway. **Identity/auth is an Argonne username, not an API key** (`ARGO_CREDENTIAL = CredentialPolicy(required=False)`; identity resolved via `request.argo_user` or `ARGO_USER` env var, defaulting to `"chemgraph"` — code comment: *"Argo routes use an Argonne username rather than an API key. Keep their identity isolated from explicit API keys... so an OpenAI credential can never be forwarded to an Argo endpoint."*).

### ALCF inference endpoints — verified from refcode
`tools/ChemGraph/src/chemgraph/models/endpoints/alcf.py` + `supported_models.py` document **three separate serving clusters**, each a distinct base URL:
- **Sophia** (NVIDIA A100, **vLLM-served**, the default) — `https://inference-api.alcf.anl.gov/resource_server/sophia/vllm/v1` — serves Llama 3.1/3.3/4, Mistral/Mixtral/Devstral, `openai/gpt-oss-20b`/`120b`, Argonne's own AuroraGPT family, Gemma, and others (`supported_alcf_models`, ~20 entries).
- **Minerva** (NVIDIA B200) — separate base URL, serves `nemotron-3-ultra` and `inkling-bf16`.
- **Metis** (SambaNova SN40L) — separate base URL, **chat-completions only, no tool calling** ("ALCF does not offer tool calling on this cluster, so ChemGraph's tool-driven workflows cannot use it" — verbatim code comment) — a real, named constraint on using Metis for any agentic (tool-calling) oracle role.
- **Auth:** `ALCF_ACCESS_TOKEN`, obtained via a documented Globus-based flow (verbatim from the module's own missing-key help text: `pip install globus_sdk`; download `inference_auth_token.py` from `argonne-lcf/inference-endpoints`; `python inference_auth_token.py authenticate`; export the resulting access token) — see `https://docs.alcf.anl.gov/services/inference-endpoints/#api-access`.

**This is the concrete evidence this brief was asked to find**: ALCF runs its own production, vLLM-backed, tool-calling-capable hosted inference service, entirely separate from any Aurora/Polaris compute-job allocation, reachable the same way any other P5 endpoint is reachable.

### Self-hosted vLLM — verified from refcode
`tools/ChemGraph/src/chemgraph/models/endpoints/vllm.py` treats a self-run vLLM server identically to any other OpenAI-compatible endpoint: base URL from `VLLM_BASE_URL` env var, API key from `VLLM_API_KEY` (or a dummy placeholder key, since local vLLM servers commonly run without real auth). Launch pattern (standard vLLM usage, not refcode-specific): `vllm serve <model> --tensor-parallel-size N`, exposing an OpenAI-compatible `/v1/chat/completions` endpoint.

## Compute pattern
- **Pattern:** **P5** (network service over HTTPS) for direct provider APIs, Argo, and ALCF-hosted calls — no local resource cost, failure modes are latency/quota/outage per the taxonomy's own definition. Self-hosted vLLM is **P1 (GPU-node-local, in-job) / P4 (external HPC job)**, genuinely dual-mode per the taxonomy's rule 2: P1 when co-located on GPUs the agent's own allocation already holds (e.g., a spare GPU slice alongside RFdiffusion/MPNN work), P4 when run as a separate, persistent serving job on a dedicated node that the agent's job talks to over HTTPS — record both, since which one applies is a deployment decision, not a property of vLLM itself.
- **GPU vendor portability:** n/a for the P5 remote-call case (no local compute at all). For self-hosted vLLM: **CUDA is vLLM's primary, most mature backend**; a ROCm build exists for AMD (Frontier) but per-model validation coverage is less universally confirmed than CUDA; Intel XPU (Aurora) support is more experimental. Notably, **ALCF's own hosted vLLM deployment (Sophia) runs on NVIDIA A100, not on Aurora's Intel hardware** — i.e., even ANL's own production inference service sidesteps the Aurora-XPU-vLLM question rather than answering it, which should be read as a real signal about the current maturity of that specific combination, not just an absence of evidence.
- **State model:** stateless per call (the oracle itself); campaign-level state (conversation history, decision log) is the calling agent's responsibility, not the API's — see the checkpointing discussion below.
- **Data locality:** streamable (HTTPS request/response, no shared-FS requirement) for P5 calls; self-hosted vLLM inherits whatever the taxonomy already says about P1/P4 data locality.
- **Staging burden:** none for P5 calls. Self-hosted vLLM: model weights, potentially large (see VRAM table below).
- **Container availability:** official vLLM images exist (`vllm/vllm-openai` on Docker Hub); n/a for the P5 hosted paths.

## Deployment on DOE & ACCESS
Full outbound HTTPS from compute nodes (confirmed in `compute-pattern-taxonomy.md`) makes direct provider APIs reachable inline from **any** of Frontier/Aurora/Polaris/ACCESS without brokering. **Argo and ALCF are ANL-scoped, not DOE-leadership-wide**: Argo's base URL is `apps.inside.anl.gov`, and ALCF's auth is a Globus token tied to an ALCF account — both are realistically usable from **Aurora and Polaris** (Argonne-operated machines) for users with the corresponding ANL affiliation/credentials, but there is no evidence in this search that either is reachable or authorized for **Frontier (ORNL-operated)** or **ACCESS** users without separate ANL access. Treat this as an access-scope caveat to resolve per-platform, not a technical limitation — the network path is HTTPS either way, the gate is credentials and authorization. **No equivalent OLCF-hosted inference-endpoint service was found in this search**; if one exists, it needs a direct check with OLCF rather than an assumption drawn from ALCF's pattern. For Frontier and ACCESS specifically, the practical oracle options reduce to: (a) direct provider APIs with a provider API key, or (b) self-hosted vLLM on allocation GPUs.

## Agentic surface
- **Native MCP:** n/a in the conventional sense. In the evidence examined, the oracle sits *underneath* the agent framework as the reasoning engine rather than being exposed *as* a tool — ChemGraph's own LangGraph nodes call `llm.bind_tools(tools=tools)` directly (per `chemgraph.md`), not through an MCP wrapper around the LLM call itself. MCP in this project's context is how the oracle *reaches other tools*, not how the oracle itself is invoked.
- **Parameters worth exposing for autonomous variation:**

| Parameter | Type | Sane range | Default | Trade-off |
|---|---|---|---|---|
| provider/model choice | enum | see cost table below | task-dependent | cost/quality/latency; also determines which resilience path (direct API vs. Argo vs. ALCF vs. vLLM) is even reachable from the current platform |
| `temperature` | float | 0.0–1.0 | 0.0 for steering decisions, higher for exploratory brainstorming sub-tasks | direct reproducibility trade-off — see Determinism below; this is a scientific-integrity knob, not just a quality knob |
| `max_tokens` / context budget | int | task-dependent | model-dependent | cost and truncation-risk; must be tracked explicitly by the agent, not assumed enforced by the provider (see Failure modes) |
| `reasoning_effort` (reasoning-capable models) | enum | low/medium/high (model-dependent) | task-dependent | cost/quality/latency; AgentRosetta (`agent-rosetta.md`) already exposes and logs this separately from `content` for its own oracle calls |
| retry/backoff policy (agent-level, not a model parameter) | config | see Failure modes | exponential + jitter, capped retries | resilience vs. wasted wall-clock; must be tuned to the campaign's risk tolerance, not left at a library default without review |

- **Parameters that must NOT be agent-varied:** **model version pinning must not float mid-campaign.** Switching from one dated model snapshot to a newer default partway through a multi-day autonomous run silently changes the reasoning distribution steering the rest of the campaign — a genuine reproducibility hazard, not just a quality change. Pin an explicit, dated model identifier per campaign (not a floating alias like "latest") and record it in the provenance log described below. The system prompt / tool schema presented to the model should also be version-controlled and not silently regenerated per call in a way that isn't logged — a changed tool schema mid-campaign is functionally the same hazard as a changed model version.

## Failure modes & what the agent must check

### This failure mode is not hypothetical
**This project has already lost four subagents to a 429 in this very session** — the toolkit-writing agents drafting the other ~31 briefs in this directory were killed mid-task by exactly the rate-limit failure mode this section describes, which is the direct, live reason this brief exists as a distinct entry rather than an assumed-reliable dependency. A multi-hour autonomous HPC campaign calling the oracle repeatedly must be designed to **survive** this failure mode, not merely log it after the fact.

- **Loud failure — HTTP 429 (rate limit exceeded).** Anthropic's API (and most providers') enforces per-tier limits across requests-per-minute, input-tokens-per-minute, and output-tokens-per-minute simultaneously; exceeding any one triggers a 429. Providers commonly return a `Retry-After` header stating the minimum wait — **respect it exactly, don't under- or over-wait**. A subtlety worth designing around: a rejected request can still consume quota in some provider accounting models, so **blind fast retries can make the problem worse**, not better.
- **Loud failure — HTTP 529 (Anthropic-specific "overloaded"), distinct from 429.** This fires when the provider's own capacity is saturated, independent of the caller's own tier/quota — it needs a different response than a 429 (a longer, less quota-aware backoff, since retrying sooner doesn't help if the provider itself is the bottleneck) and should be distinguished in the agent's error-handling logic, not folded into the same retry path as a plain rate limit.
- **Loud failure — auth failure, malformed request/schema mismatch.** Correctable, should fail fast rather than retry.
- **Silent/degraded failure — truncated response.** A response cut off at `max_tokens` without the caller checking `stop_reason`/`finish_reason` looks like a complete, valid answer but isn't — the agent must check the stop reason on every call, not just parse whatever text came back.
- **Silent/degraded failure — tool-call hallucination.** The model can claim to have information from a tool call it didn't actually make, or invent plausible-looking arguments; validate every tool-call's schema and provenance before executing it, don't trust the model's own narration of what it did.
- **Silent/degraded failure — context-window overflow.** Some provider/client combinations truncate silently (dropping earlier turns) rather than erroring when a conversation exceeds the context window; the agent must track its own token budget explicitly rather than assuming the provider will complain when it runs out.

### Recommended resilience posture — concrete, not aspirational
1. **Exponential backoff with jitter, respecting `Retry-After`** when present; cap the retry count and give up to the degraded-mode path below rather than retrying indefinitely against a dead endpoint.
2. **Checkpoint agent state *before* issuing an oracle call, not after.** A call that fails mid-flight (429, 529, timeout, connection drop) should cost at most the one in-flight decision, never accumulated campaign state — this is the same durability lesson ChemGraph's own `JobTracker` encodes for async remote job submission (`tools/ChemGraph/src/chemgraph/execution/job_tracker.py`, mined in `chemgraph.md`): capture a call's identifying hash/ID *before* sending it, so a post-restart retry can detect and skip a call that actually succeeded rather than double-submitting or losing track of it.
3. **Explicit degraded-mode fallback policy, decided in advance, not improvised at failure time.** When the oracle is unreachable beyond the retry budget: fall back to a smaller self-hosted model (vLLM, co-located) for routine steering decisions that don't need frontier-model reasoning quality, or fall back to a deterministic default policy (e.g., "continue the current physics-only pipeline without new LLM-proposed moves, log the gap, flag for human review") — **the agent must never let a multi-hour, potentially expensive GPU allocation sit idle blocking on an external oracle retry loop.** The cost asymmetry is stark: idling a multi-GPU allocation for minutes-to-hours waiting on an API is far more expensive than the API call itself ever would have been.
4. **Circuit breaker.** After N consecutive failures against the primary provider, stop retrying it for a cool-down window; if a provider-abstraction layer is in place (see below), fail over to a secondary provider (Anthropic → OpenAI → Gemini, or direct API → Argo → ALCF where platform-reachable) rather than only ever retrying the one that's down.

### Determinism and reproducibility — a scientific-integrity issue, not just an engineering one
An LLM oracle **cannot be treated as a deterministic function the way a physics simulation or a fixed-seed ΔΔG predictor can**, and this is a real departure from the reproducibility standard the rest of this toolkit implicitly assumes — every other Core tool briefed in this project (Rosetta, RFdiffusion3, ProteinMPNN) is at least nominally seed-reproducible on a fixed hardware/software stack; the oracle is categorically not, for reasons worth stating precisely:
- **`temperature=0` does not guarantee determinism.** Even pure greedy decoding can diverge run-to-run due to floating-point non-associativity under parallel/batched execution, mixture-of-experts routing artifacts (where applicable), and server-side scheduling variance — this persists even with temperature fixed at 0 and a seed supplied, per direct empirical study of the phenomenon.
- **Seed support is inconsistent and, where present, not guaranteed.** **The Anthropic API does not expose a `seed` parameter at all.** OpenAI exposes `seed` plus a `system_fingerprint` for best-effort reproducibility tracking, but does not guarantee bit-identical output. Google's Gemini API accepts a `seed` parameter but explicitly does not guarantee determinism from it.
- **Required practice, given the above:** since the oracle's exact output cannot be forced to be bit-reproducible, the campaign's audit trail must instead capture **full provenance for every prompt/response pair** — the exact request payload (pinned, dated model ID; temperature and all sampling parameters; the full tool schema in effect at call time) and the full response (including any reasoning/thinking content the model surfaced), timestamped and logged durably. This lets a campaign's LLM-driven decisions be **audited and reconstructed** after the fact even though the LLM's own output cannot be regenerated bit-for-bit on replay — the downstream physics steps a decision triggered are still deterministic and inspectable even when the decision-making step itself is not. Treat this provenance log as on par with recording a Rosetta score-function version or an RFdiffusion checkpoint hash: **the campaign's scientific record is incomplete without it**, and an agent design that doesn't log this is not meeting the same reproducibility bar the rest of the toolkit is held to.

## Cost per unit of work

### Self-hosted vLLM — VRAM and topology
| Model class | Approx. VRAM (bf16/fp16 weights) | Typical topology | Notes |
|---|---|---|---|
| ~8B (e.g. Llama-3.1-8B) | ~16 GB | 1 GPU, co-locatable alongside other P1 work | good candidate for the degraded-mode fallback model — small enough to sit on a spare allocation GPU without displacing RFdiffusion/MPNN/Boltz work |
| ~70B | ~140 GB fp16 (~70 GB at FP8, fitting one H100-80GB) | 2–4 GPUs at fp16, 1 at FP8, via `--tensor-parallel-size` | a realistic "primary self-hosted oracle" size if call volume justifies a dedicated allocation |
| ~405B-class | ~230 GB at Q4 | 4× H100-80GB / 3× H200-141GB minimum | dedicated-node territory; only justified at very high call volume or strict data-residency requirements |

Tensor parallelism in vLLM splits model layers across GPUs within a node via a single `--tensor-parallel-size N` flag; KV-cache memory additionally scales with context length × batch size on top of the weight footprint in the table above.

### Frontier-model API pricing (September 2026, $/1M tokens, input/output) — worked example
| Model | Input | Output |
|---|---|---|
| Claude Haiku 4.5 | $1 | $5 |
| Claude Sonnet 5 | $2 | $10 |
| Claude Opus 5 | $5 | $25 |
| GPT-5 (base tier) | ~$1.25 | ~$10 |
| Gemini 3 Pro (≤200K context) | $2 | $12 |

(Pricing shifts quickly and varies by sub-variant within each family — these are order-of-magnitude anchors as of this writing, not a locked reference; re-check before budgeting a large campaign. Batch APIs commonly offer ~50% off both directions where supported; prompt caching commonly cuts cached-input cost by ~90% — both are real, usable levers for a campaign that resends similar context repeatedly.)

**Worked example:** a campaign making 5,000 oracle calls (e.g., one design-review call per candidate across a large multi-day campaign), each with ~5K input tokens (structure summary + running scores + conversation context) and ~1K output tokens, on Claude Sonnet 5, uncached: input = 25M tokens × $2/1M = $50; output = 5M tokens × $10/1M = $50; **total ≈ $100 for 5,000 calls.** With prompt caching on the repeated-context portion of the input (plausible if most of each 5K-token prompt is a stable structure/history block reused across calls), realistic cost reduction is 60–80%, bringing the same campaign to roughly **$20–40**. Scaling to a full multi-week campaign with tens of thousands of calls plausibly lands in the **low-to-mid hundreds of dollars** — genuinely cheap relative to the GPU/CPU-hour cost of the compute the oracle is steering (a single Rosetta `cartesian_ddg` saturation scan alone already costs thousands of CPU-hours per `ddg-predictors.md`/`rosetta-ddg.md`), **but not free, and cost scales linearly with call frequency** — an agent design calling the oracle per-candidate rather than per-batch-decision can balloon this by one to two orders of magnitude, so batching decisions where possible is a real cost lever, not just a latency one.

**Self-hosted vLLM cost model is structurally different:** no per-token bill, but it consumes real GPU-hours from the project's own allocation, competing for the same GPUs the campaign needs for RFdiffusion3/MPNN/Boltz/ESM work. Self-hosting only wins economically at very high call volume, or when reliability/data-residency requirements outweigh the API's per-token cost — for most campaign sizes in the worked example above, the API's few-hundred-dollar bill is cheaper than the opportunity cost of dedicating a GPU to hosting a model instead of running the toolkit's other P1 work.

- **Checkpointable:** n/a — individual oracle calls are seconds-scale and should never be scheduled as discrete checkpointed tasks; the checkpointing that matters is at the campaign-state level described in the resilience posture above, immediately before each call, not the call itself.

## Provider abstraction: LiteLLM vs. LangChain — recommendation
Two real, evidenced approaches exist in this project's own toolkit sweep:
- **AgentRosetta** (`agent-rosetta.md`) uses **LiteLLM** — `agent_rosetta/model.py` mediates Anthropic, OpenAI, and OpenRouter through a single `litellm`-based call surface, configured per-run via `configs/model/*.yaml`.
- **ChemGraph** (`chemgraph.md`, and directly re-examined here) instead hand-rolled its own per-provider endpoint-adapter layer (`tools/ChemGraph/src/chemgraph/models/endpoints/{alcf,argo,vllm,openai_direct,...}.py`, dispatched through a `registry.py`) on top of **LangChain's** `ChatAnthropic`/`ChatOpenAI` client classes.

**Recommend LiteLLM as IMPRESS-A's default provider-abstraction layer.** Reasoning: IMPRESS-A needs a thin, swappable multi-provider chat/completion surface (Anthropic, OpenAI, Gemini, and potentially Argo/ALCF/self-hosted-vLLM, nearly all effectively OpenAI-compatible-wire-protocol except Anthropic-native) sitting *underneath* its own orchestration logic — not a full agent framework with its own message classes, memory abstractions, and graph machinery. LiteLLM is exactly that thin layer, with retry/backoff/failover/cost-tracking built in — directly addressing the resilience posture required above — without pulling in LangChain's much larger and, per `chemgraph.md`'s own finding, actively-changing dependency surface (`langgraph==1.2.11`, `langchain==1.4.0`, version-pinned rather than floor-pinned specifically because the maintainers found it necessary to manage compatibility actively). ChemGraph's choice of LangChain is explained by a different constraint that doesn't apply to IMPRESS-A by default: it needed LangChain's tool-calling/graph machinery anyway for its LangGraph-based agent runtime, so layering provider routing on top of clients it already depended on was the path of least resistance for that specific project — it is not evidence that LangChain is the better choice for a project that hasn't (yet) committed to LangGraph as its orchestration substrate. If IMPRESS-A does later adopt a LangGraph-style graph orchestration layer, ChemGraph's endpoint-adapter code is a directly useful reference for wiring Argo's non-standard auth (Argonne username instead of API key) and ALCF's Globus-token flow underneath a generic client — but that's a reason to *read* ChemGraph's code, not to adopt LangChain as the default abstraction today. LiteLLM's custom-provider/proxy support can accommodate Argo/ALCF's non-standard auth without requiring a framework switch.

## Verdict
**Core.** IMPRESS-A's own design (control mode B) assumes an LLM oracle exists as a reachable dependency — it is not optional the way a specific scientific tool might be. This verdict is nuanced by access path:
- **Direct frontier provider APIs (Anthropic/OpenAI/Google) via HTTPS: Core**, must ship with the full resilience posture above (retry/backoff, pre-call checkpointing, an explicit degraded-mode fallback, provenance logging) as a non-negotiable requirement, not an optional hardening pass — the 429 failure mode is demonstrated, not hypothetical, within this very project.
- **Self-hosted vLLM: Recommended**, both as the degraded-mode fallback target and as a cost-control lever at high call volume. The CUDA path (Polaris/ACCESS) is low-risk; Frontier (ROCm) and Aurora (XPU) self-hosting should be **Defer** pending a dedicated validation spike, given vLLM's CUDA-primary maturity profile and the observation that even ALCF's own production hosted service runs vLLM on NVIDIA hardware rather than Aurora's Intel GPUs.
- **ALCF/Argo hosted endpoints: Recommended** for campaigns running on Aurora/Polaris with genuine ANL-affiliated credentials — this is real, working, tool-calling-capable production infrastructure (Sophia cluster) with a documented breadth of open-weight models, and worth using directly rather than re-implementing. **Defer/n-a** for Frontier or ACCESS-only users without ANL access, pending confirmation of whether either gateway is reachable/authorized outside Argonne's own user base.
- **LiteLLM as the provider-abstraction layer: Recommended**, load-bearing for the resilience posture even though it is an implementation choice rather than a scientific tool in its own right.
