# Foundry (rc-foundry)

**One-line identity.** The shared training/inference infrastructure package — `BaseInferenceEngine`, checkpoint registry, Hydra config system, and the `foundry` checkpoint-management CLI — that RFD3, RFD3NA, RF3, and MPNN are all built and packaged on top of within a single monorepo.

## Identity
- **Version / release examined:** `tools/foundry/pyproject.toml` — `name = "rc-foundry"`, `dynamic = ["version"]` via `hatch-vcs` (git-tag-derived, `fallback-version = "0.0.0"`, `tag-pattern = "^v(?P<version>.*)$"`). `requires-python = ">=3.12"`. `[project.scripts] foundry = "foundry_cli.download_checkpoints:app"`.
- **Provenance:** RosettaCommons / Institute for Protein Design (`authors = [{name = "Institute for Protein Design", email = "contact@ipd.uw.edu"}]`). BSD license (`tools/foundry/LICENSE.md`). Refcode: `tools/foundry/` (the whole monorepo — `src/foundry`, `src/foundry_cli`, plus `models/{rfd3,rfd3na,rf3,mpnn}` as sub-packages).
- **Maturity:** active research infrastructure with real engineering discipline visible in the refcode — a mypy strict-typing ratchet fully cleared across `foundry.*`, `foundry_cli.*`, `mpnn.*`, `rfd3.*`(partial), `rfd3na.*` (per the detailed `[tool.mypy]` override comments in `pyproject.toml`), pre-commit formatting enforced, and a live community Slack linked from the top-level README. Not a stable 1.0 — `fallback-version = "0.0.0"` and the CI-constraints churn documented in the `atomworks.md` brief both point to an actively moving target.

## Scientific role
Not a problem-class solver itself — it is the **orchestration and lifecycle layer** underneath every model in this cluster: `BaseInferenceEngine` (`src/foundry/inference_engines/base.py`) is the shared parent class every model's own `*InferenceEngine` extends for checkpoint loading, Hydra config resolution, and accelerator selection; the checkpoint registry (`src/foundry/inference_engines/checkpoint_registry.py`) is the single source of truth for where every model's weights live; the `foundry` CLI is how an operator (or an autonomous agent, at setup time) provisions those weights before any of the other four tools can run. It touches every pipeline stage (generate/inverse-fold/predict) transitively, exactly as `atomworks` does, but one layer higher — `foundry` is infra-for-models, `atomworks` is infra-for-data.

## Invocation & I/O contract
- **How a unit of work is invoked:** CLI, via the `foundry` entrypoint (`foundry = "foundry_cli.download_checkpoints:app"`, a Typer app with subcommands `install`, `list-available`, `list-installed`, `clean`). All four are real, verified commands in `src/foundry_cli/download_checkpoints.py`:
  ```bash
  foundry install base-models --checkpoint-dir <path/to/ckpt/dir>
  foundry install rfd3 rfd3na rf3 mpnn --checkpoint-dir ./checkpoints
  foundry install all --force
  foundry list-available
  foundry list-installed
  foundry clean --no-confirm
  ```
  `install base-models` expands to `["rfd3", "rfd3na", "proteinmpnn", "ligandmpnn", "rf3"]` (real expansion logic in `install_model`/`install`); `install all` expands to every key in `REGISTERED_CHECKPOINTS` (10 entries observed, including preprint-vintage RF3 checkpoints and legacy MPNN variants).
  Programmatically, `foundry.inference_engines.base.BaseInferenceEngine` is the class every model subclasses — an agent orchestration layer would extend or call subclasses of this (e.g. RFD3's or MPNN's own engine), not `BaseInferenceEngine` directly, since its `run()` raises `NotImplementedError` by design.
- **Inputs:** for the CLI — model names (`rfd3`/`rfd3na`/`rf3`/`mpnn`/`proteinmpnn`/`ligandmpnn`/`solublempnn`/`all`/`base-models`) and an optional `--checkpoint-dir`/`-d`. For the Hydra config system every model rides on — `key=value` override strings (see the RFD3/RFD3NA briefs for real examples).
- **Outputs:** downloaded checkpoint files under `~/.foundry/checkpoints` (default) or `$FOUNDRY_CHECKPOINT_DIRS` (colon-separated, persisted into a `.env` file by `append_checkpoint_to_env` when one exists — real code in `download_checkpoints.py::_resolve_checkpoint_dirs`), with SHA256 verification support (`download_file(..., verify_hash=...)`) though none of the currently registered checkpoints carry a hash (`RegisteredCheckpoint.sha256: None = None` — every actual entry in `REGISTERED_CHECKPOINTS` leaves this at the default `None`).
- **A concrete example**, real command from `tools/foundry/README.md`:
  ```bash
  foundry install base-models --checkpoint-dir <path/to/ckpt/dir>
  ```
  and `foundry list-installed` output format (real, from `download_checkpoints.py::list_installed`): a per-file line `{path} {size:8.2f} GB` followed by a `Total: {total:.2f} GB` line — useful as a literal post-hoc staging check an agent can parse.

## Compute pattern
- **Pattern:** **P5 (network service over HTTPS)** for `foundry install` specifically (it is a checkpoint-fetch operation against `files.ipd.uw.edu`, egress-dependent, no local GPU/scheduling cost) with a secondary **P6 (in-process library)** role for `BaseInferenceEngine`/Hydra config resolution, which every model's actual inference call uses in-process. Per the taxonomy's rule 2, recording both is appropriate since `foundry` is genuinely dual-mode across its CLI-tool role and its library role — but neither role is itself a P1 GPU-bound unit of work; `foundry` never runs a model, it only provisions and configures the engines that do.
- **GPU vendor portability:** n/a for the CLI/checkpoint-download role (pure HTTPS file transfer, no compute). For the shared accelerator-selection code every model relies on (`src/foundry/utils/ddp.py::set_accelerator_based_on_availability`), the classification matches the RFD3/MPNN briefs: **CUDA+SYCL-XPU, proven; HIP unproven** — this single function is the actual place in the codebase where `torch.cuda` → `torch.xpu` → `torch.backends.mps` → `cpu` priority is decided for every model in the suite, so it is worth flagging as the one chokepoint where a future HIP code path would need to be added if Frontier support is ever pursued.
- **State model:** `install` is idempotent/resumable at the file level — re-running `foundry install X` skips an already-present checkpoint unless `--force` is passed (real logic in `install_model`), which is a reasonable substitute for true checkpointing given these are single-file downloads.
- **Data locality:** shared-FS strongly recommended — `~/.foundry/checkpoints` (or `$FOUNDRY_CHECKPOINT_DIRS`) should be a location visible to every compute node that will run inference, so the download happens once per cluster rather than once per job.
- **Staging burden:** this **is** the staging-burden mechanism for the whole cluster — sizes vary per model (RFD3/RFD3NA ~3 GB each per the installation tutorial, RF3 unspecified but large per typical structure-prediction checkpoints, MPNN variants tens of MB each). `foundry list-installed`'s total-size reporting is the concrete tool an agent or operator should use to verify staging completed before a campaign starts.
- **Container availability:** official — `rosettacommons/foundry` on Docker Hub, built from the reference `Dockerfile` at `tools/foundry/examples/docker/Dockerfile` (real, present in refcode). That Dockerfile: base image `ubuntu:22.04` (no CUDA/ROCm base image baked in — relies entirely on the pip-installed `torch` wheel for GPU support), installs via `uv venv --python 3.12 && uv pip install ".[all]"`, then runs `foundry install base-models --checkpoint-dir /app/foundry/checkpoints` at build time so the published image ships weights pre-baked (per Docker Hub listing: `latest` tag ~18 GB, `slim` tag without weights). Explicitly documented as NVIDIA-oriented in Docker Hub usage examples (`apptainer run --nv`) and stated as **not ARM-compatible**.

## Deployment on DOE & ACCESS
- **Polaris / ACCESS (Delta, Bridges-2, Expanse — CUDA):** the official container is the path of least resistance; `apptainer run --nv rosettacommons/foundry:latest foundry install ...` (or any model's CLI) works with no custom build. Alternatively `pip install "rc-foundry[all]"` inside a conda/venv environment built from a CUDA-capable module stack.
- **Aurora (Intel XPU):** the official Docker image does **not** cover this path (ubuntu:22.04 base + `--nv`-oriented usage, no XPU variant published) — deployment must be a custom build following the README's documented order: install torch's XPU wheel first (`pip install torch --index-url https://download.pytorch.org/whl/xpu`), then `pip install "rc-foundry[all]"` via **pip, not uv** (README's explicit warning: `uv` re-resolves dependencies and can silently replace the XPU torch build). This is real, working code (the `src/foundry/utils/xpu/` plugin classes), not aspirational — but it is a from-source deployment on Aurora, not a container pull.
- **Frontier (AMD MI250X/HIP):** **no supported path today.** Neither the official container nor the pip/uv extras system has any HIP/ROCm awareness — confirmed by a full-repository grep (`hip`/`rocm`/`amd`, zero hits across `.py`/`.md`/`.toml`/`.yaml`). The `set_accelerator_based_on_availability` chokepoint identified above is exactly where HIP support would need to be added (a fourth branch checking for a ROCm-specific signal, since `torch.cuda.is_available()` on a ROCm PyTorch build would already return `True` and could mis-route through the CUDA/cuEquivariance branch rather than a correct HIP-aware one). Treat Frontier as **not currently deployable** for this suite, not merely "unoptimized."
- No license gates were found for any of the four models or for `foundry` itself — BSD-licensed throughout, checkpoints served from an open HTTPS endpoint (`files.ipd.uw.edu`) with no authentication observed in `download_checkpoints.py`.

## Agentic surface
- **Native MCP:** no. Repo-wide grep across all of `tools/foundry` (every model, every shared-infra file) for `mcp`/`model context protocol`/`modelcontextprotocol` returns zero hits outside this project's own brief template. This confirms, at the infra level, the same conclusion reached per-model: **foundry has no MCP scaffolding anywhere**, consistent with the stated earlier sweep finding for both foundry and IMPRESS.
- **Parameters worth exposing for autonomous variation:**

| Parameter | Type | Sane range | Default | Trade-off |
|---|---|---|---|---|
| `models` (positional, `foundry install`) | list[str] | any of `all`/`base-models`/individual registry keys | required | Controls which checkpoints get staged; an agent's setup phase should call this explicitly rather than relying on lazy on-demand downloads mid-campaign |
| `--checkpoint-dir` / `-d` | path | any writable, ideally shared-FS path | `~/.foundry/checkpoints` | Determines whether checkpoints are node-local (fast but re-downloaded per node) or shared (slower first access, one-time cost cluster-wide) |
| `--force` / `-f` | bool | — | `False` | Re-downloads and overwrites an existing checkpoint; agent should only set this on an explicit "refresh weights" instruction, not routinely |
| `num_nodes` / `devices_per_node` (Hydra, `BaseInferenceEngine.__init__`) | int / int | 1 / 1 for single-GPU inference; higher only for training | 1 / 1 | These exist primarily for multi-GPU **training**; for inference calls in this cluster they should stay at 1/1 — see "must not vary" below |

- **Parameters that must NOT be agent-varied:**
  - `num_nodes` / `devices_per_node` for **inference** calls — these are real constructor parameters on `BaseInferenceEngine` and every model's engine, but per the P1 classification of every model in this cluster (single-GPU-node-local inference), an agent should not scale these up expecting a distributed-inference speedup; foundry's distributed-training machinery (Lightning Fabric `devices_per_node`/`num_nodes`/`grad_accum_steps`, documented in the RFD3/RFD3NA READMEs' "Distributed Training" sections) is a training-time concern that doesn't apply to a single design/inference call.
  - `--force` on `foundry install` — silently re-downloads and overwrites potentially-in-use checkpoint files; should require an explicit human/ops decision, not routine agent variation.
  - Anything touching `FOUNDRY_CHECKPOINT_DIRS`/`.env` persistence mid-campaign — `_resolve_checkpoint_dirs` writes to a `.env` file as a side effect of `install`; an agent should not repeatedly invoke `install` with varying `--checkpoint-dir` values, since it mutates shared environment state that other concurrent jobs may depend on.

## Failure modes & what the agent must check
- **Loud failure:** unknown model name to `foundry install` (`console.print(f"[red]Error:[/red] Unknown model '{model_name}'")` then `raise typer.Exit(1)` — real code in `install_model`), a checkpoint download hash mismatch would raise `ValueError` and delete the corrupted file (though as noted, no registered checkpoint currently carries a hash to check against — this safety net is present in the code but not yet exercised by any real entry), network failure during download (caught generically, re-raised as `typer.Exit(1)` with the underlying exception message printed).
- **Silent bad output:** the most important one for an autonomous agent — **`foundry install` currently has no hash verification for any real checkpoint** (every `RegisteredCheckpoint.sha256` is `None`), so a truncated or corrupted download that nonetheless completes without an HTTP error would produce a checkpoint file foundry considers "present" (checked only via `dest_path.exists()`), which would then fail *inside* a model's `torch.load` call later, or worse, load successfully but produce degraded model behavior. **The agent must not treat `foundry list-installed`'s presence-and-size report as a correctness guarantee** — it confirms staging happened, not that the file is uncorrupted. A cheap mitigation: compare `list-installed` reported size against the known checkpoint size (~3 GB for RFD3/RFD3NA per the installation tutorial) as a sanity floor before first use.
- Config-resolution silent failures: `BaseInferenceEngine._override_checkpoint_config` merges CLI/Hydra overrides via `OmegaConf.merge` — a typo'd dotted-key override (e.g. `inference_sampler.stepscale` instead of `inference_sampler.step_scale`) would silently create a new, unused config key rather than erroring, and the run would proceed with the *default* value for the intended parameter. An agent generating Hydra overrides programmatically should validate override keys against the known config schema (e.g. via `prevalidate_inputs=True` where the model supports it) rather than trusting that an override was applied just because the command didn't error.

## Cost per unit of work
`foundry install` of one model: dominated by network transfer time for a multi-GB (RFD3/RFD3NA) or tens-of-MB (MPNN) file over HTTPS — seconds to a few minutes depending on link speed, a one-time setup cost per checkpoint dir, not a per-campaign cost. `foundry list-available`/`list-installed`/`clean`: sub-second, local filesystem/static-registry operations (P6-scale, should never be scheduled as a task). `BaseInferenceEngine.initialize()` (checkpoint load + model construction, shared by every model): several seconds to tens of seconds depending on model size and storage speed — happens once per inference-engine lifetime, not once per design, so an agent orchestration layer should reuse a live engine across multiple `run()` calls rather than re-initializing per design where possible.

## Verdict
**Core.** Foundry is the substrate the entire generative/inverse-folding cluster is built on — its checkpoint registry, `BaseInferenceEngine`, and Hydra config system are exactly the mechanisms the RFD3, RFD3NA, and MPNN briefs describe when they cite real argv and config defaults; there is no meaningful way to deploy or drive those three tools without going through foundry's install CLI and shared inference-engine base class. The one genuine finding here that changes planning, not the verdict: checkpoint integrity currently has no real safety net (no hashes populated), and the shared `set_accelerator_based_on_availability` function is the single chokepoint where Frontier/HIP support would need to be added if that platform is ever pursued — both are concrete, actionable follow-ups rather than reasons to defer.
