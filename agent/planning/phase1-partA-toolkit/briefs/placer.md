# PLACER (Protein-Ligand Atomistic Conformational Ensemble Resolver)

**One-line identity.** An atom-level graph neural network (formerly ChemNet) that stochastically denoises corrupted atomic coordinates to predict small-molecule conformations and binding-site side-chain geometry jointly, given only atom composition/bonding and protein context — usable for ligand docking, active-site conformer ensembles, and side-chain repacking without any hand-authored geometric constraints.

## Scientific role
Serves **enzyme/catalytic design** and **small-molecule binding** directly — the two problem classes this toolkit's Rosetta `match`/`enzyme_design` brief (`rosetta-enzyme-design.md`) identified as bottlenecked on expert-authored theozyme geometry. PLACER also has a secondary role in **stability/thermostabilization** and **de novo binder design** wherever apo side-chain conformational ensembles are useful (it runs on protein-only inputs via `--target_res`/`no-use_sm`, with no ligand at all). Pipeline stage: **predict / score** — specifically atomic-coordinate prediction plus a co-emitted confidence signal, not sequence design and not inverse folding.

PLACER was trained (README) "to recapitulate the correct atom positions from partially corrupted input structures from the Cambridge Structural Database and the Protein Data Bank." Given a protein structure and a ligand's identity/bonding (from the input file itself, or refined via a `.sdf`/`.mol2`/CCD-code reference), it corrupts atoms in and around the binding site and iteratively denoises them back to a full-precision atomic model — of the ligand's conformation, its docked pose, and/or the surrounding side chains, depending on what is fixed vs. predicted. Because it is a stochastic denoiser, running it `nsamples` times produces a genuine **conformational ensemble**, not a single point estimate.

### Relationship to `rosetta-enzyme-design.md`: does PLACER reduce the theozyme/cstfile burden?
`rosetta-enzyme-design.md` identified the dominant autonomy risk in Rosetta's enzyme-design pipeline as **hand-authored theozyme geometry and `.cst` constraint files** — a mechanistic-chemistry judgment call that Rosetta does not generate or validate, and that fails *silently* (a design can satisfy every numeric `CONSTRAINT::` tolerance while being chemically meaningless, because the constraints only encode what a human told the optimizer to care about).

PLACER changes this in one specific, bounded way: **it does not require distance/angle/torsion constraints at all.** There is no `.cst`-equivalent input anywhere in PLACER's argument list or `PLACERinput` API. Instead of being told "this histidine Nε2 must sit 2.0 Å ± 0.3 Å from this carbon at this angle," PLACER is given the ligand's identity and the protein context and predicts where the ligand and nearby side chains *actually* want to sit, using a geometry prior learned from the CSD+PDB rather than a geometry a chemist typed in. This is a genuine reduction in one specific failure mode: **PLACER cannot "successfully" converge to a numerically-satisfied-but-chemically-wrong theozyme, because it was never given a theozyme to satisfy in the first place** — its confidence score (`prmsd`/`plddt`) reflects the network's own learned notion of plausible atomic geometry, not conformance to a human-specified target.

What PLACER does **not** do is remove the need for a human (or a validated template) to decide *which reaction mechanism, which catalytic residues, and which transition-state-like ligand geometry* are being pursued in the first place — that is still a scientific hypothesis PLACER has no opinion on. Its practical role is therefore **downstream and orthogonal to theozyme authoring, not a replacement for it**: after `match`/`enzyme_design` (or any other route) produces a candidate active site with a ligand placed by hand-authored constraints, PLACER can **independently re-predict the ligand pose and active-site side-chain conformation from scratch, with no knowledge of the `.cst` file**, and its agreement (or disagreement) with the constraint-derived pose is a genuinely orthogonal consistency check — a different architecture, trained on different data, with no mechanism by which it could rubber-stamp a constraint-satisfying-but-chemically-wrong geometry the way re-scoring with Rosetta's own energy function might. This directly targets the silent failure mode `rosetta-enzyme-design.md` flagged as the hardest to catch: "constraint satisfaction achieved geometrically but chemically meaningless." A low PLACER `prmsd` on an independently-repredicted pose that also matches the Rosetta-matched geometry is meaningfully stronger evidence than either tool's self-reported score alone; a *high* PLACER `prmsd` on a pose Rosetta scored as constraint-satisfying is a concrete, actionable red flag that the theozyme geometry itself may be internally inconsistent with what real atomic environments look like.

A second, narrower reduction in burden: PLACER's `--mutate` flag lets an agent introduce a point mutation and re-predict local side-chain/ligand geometry in the same call, without a separate resfile/task-operation setup — useful for rapidly probing whether a candidate active-site mutation preserves a plausible catalytic geometry before committing to a full Rosetta redesign pass.

## Invocation & I/O contract
- **How a unit of work is invoked:** both CLI and Python API, confirmed in the refcode's own `README.md` and `examples/`.
  - **CLI** (`run_PLACER.py`), real examples from `examples/commandline_examples.sh`:
    ```bash
    # predicting the binding of an inhibitor in a P450 pocket, while keeping heme fixed
    python ../run_PLACER.py --ifile inputs/4dtz.cif --odir example_out_CLI \
        --rerank prmsd --suffix D-LDP-501 -n 10 --predict_ligand D-LDP-501

    # predicting sidechains in apo denovo protein, defining crop center to a residue
    python ../run_PLACER.py --ifile inputs/dnHEM1_apo.pdb --odir example_out_CLI \
        --suffix A149 -n 10 --target_res A-149

    # mutating a residue to a non-canonical, loading it from a JSON residue definition
    python ../run_PLACER.py --ifile inputs/denovo_SER_hydrolase.pdb --odir example_out_CLI \
        --suffix 75I -n 10 --mutate 128A:75I --residue_json ligands/75I.json --no-use_sm
    ```
  - **Python API** (`PLACER.py`), from `README.md`'s own documented pattern (also `examples/API_examples.py`):
    ```python
    import sys; sys.path.append("<PLACER_path>")
    import PLACER
    placer = PLACER.PLACER()                       # loads default checkpoint
    pl_input = PLACER.PLACERinput()
    pl_input.pdb("examples/dnHEM1.pdb")
    pl_input.name("heme_test")
    pl_input.ligand_reference({"HEM": "examples/ligands/HEM.mol2"})
    outputs = placer.run(pl_input, 50)              # dict output, one entry per sample
    PLACER.protocol.dump_output(outputs, "out/heme_test")   # writes CSV + multimodel PDB
    ```
  Entrypoint confirmed at `PLACER.py:32` (`class PLACER`), `run_PLACER.py:23` (`placer = PLACER.PLACER(weightsfile)`), `modules/placer_input.py` (`PLACERinput`). There is no `[project.scripts]`/pip entrypoint — PLACER is not pip-installable (README: "currently not pip-installable"), invoked by `sys.path.append`/`PYTHONPATH` against the cloned repo.
- **Inputs:** a PDB or mmCIF structure (mmCIF *must* be RCSB-formatted — README states other mmCIF sources are "problematic because of differences in formatting"); optional `.sdf`/`.mol2` ligand reference files (`--ligand_file LIG:ligand.sdf`) to correct atom typing/hybridization/bonding beyond what the PDB alone encodes; optional custom-residue JSON for non-canonical amino acids or novel ligands not in PLACER's internal CCD copy. **SMILES input is not supported** — "the docked ligand must be present in the input PDB/mmCIF file" (README FAQ #8); PLACER cannot start from an apo protein plus a bare ligand identity.
- **Outputs:** per the CLI/`dump_output` (`modules/protocol.py:236`): `{prefix}.csv` (one row per sample — `fape`, `lddt`, `rmsd`, `kabsch`, `prmsd`, `plddt`, `plddt_pde`) and `{prefix}_model.pdb` (multimodel PDB, one MODEL per sample, **per-atom `prmsd` written into the B-factor column** — README FAQ #5, letting per-residue confidence be read directly off the structure without parsing the CSV separately).
- **Confidence signal:** three related but distinct scores, defined in the README FAQ verbatim — `prmsd` (predicted RMS deviation of atomic positions; the *recommended* score, "we have seen prmsd offer the best performance in docking tasks," threshold guidance: **prmsd < 2.0 trustworthy, < 4.0 acceptable if plddt/plddt_pde > 0.8**), `plddt`/`plddt_pde` (predicted lDDT from the 1D and 2D network tracks respectively). Note that `fape`/`lddt`/`rmsd`/`kabsch` are computed **against the input structure's own ligand coordinates**, not an independent ground truth — for a genuine novel-design task (no crystallographic reference), these four columns measure agreement with whatever pose the *input* structure already had, which is a legitimate independent-repredicition check (see Scientific role above) but is not itself a stand-alone accuracy claim; only `prmsd`/`plddt`/`plddt_pde` are true blind confidence estimates usable when no reference exists.
- **A concrete example:** the CLI three-liner above is copied verbatim from the repo's own `examples/commandline_examples.sh`; `examples/inputs/4dtz.cif` and `examples/ligands/HEM.mol2` are real, runnable inputs shipped in the refcode.

## Compute pattern
- **Pattern:** **P1** (GPU-node-local, in-job). A CPU fallback exists and is functionally correct (see Cost below) but is not viable at campaign scale — classify by dominant cost per the taxonomy's rule 1, which is GPU.
- **GPU vendor portability:** **CUDA-only, by evidence — the strongest form of this claim in the toolkit.** Three independent pieces of evidence: (1) PLACER's own device-selection ladder, `PLACER.py:38` — `torch.device('mps' if torch.backends.mps.is_available() else 'cuda:0' if torch.cuda.is_available() else 'cpu')` — has **no XPU branch at all**, unlike the foundry models (`rfdiffusion3.md`, `proteinmpnn-ligandmpnn.md`) which explicitly check `torch.xpu.is_available()`; PLACER was never written with Intel GPUs in mind. (2) `modules/model.py` hard-imports `dgl` (line 7) and the shipped `envs/placer_env.yml` pins `dgl=2.4.0.th23.cu121` from the `dglteam/label/th23_cu121` conda channel alongside `nvidia/label/cuda-12.1.0` — DGL (Deep Graph Library) has no official ROCm/HIP or SYCL/XPU backend; this is a structural blocker independent of PLACER's own code. (3) `modules/SE3_network.py` builds its equivariant layers on `se3_transformer.model.SE3Transformer`, installed via `pip: se3-transformer @ git+https://github.com/NVIDIA/DeepLearningExamples.git#subdirectory=...` — an NVIDIA-authored package. Given all three, treat PLACER as **CUDA-only** for GPU acceleration; Aurora (XPU) support would require replacing the DGL dependency, not a config change, and Frontier (HIP) is unproven with no positive or negative evidence found. This is a non-issue for the project's stated primary platforms (Polaris, NSF ACCESS — both NVIDIA/CUDA); it matters only if Aurora is later promoted.
- **State model:** stateless per call — each `placer.run(...)` (or CLI invocation) loads the checkpoint once and produces `nsamples` independent samples in a loop (`PLACER.py:137`, `for sample in range(nsamples)`); no resumability/checkpoint-within-a-run mechanism found. `--cautious` mode (CLI) provides *inter-run* skip-if-output-exists behavior, not intra-run resumability.
- **Data locality:** self-contained — one structure file (+ optional small `.sdf`/`.mol2`/JSON) in, CSV + multimodel PDB out; no shared-FS dependency beyond the checkpoint itself.
- **Staging burden:** model weights only, **small** — `weights/PLACER_model_1.pt` is 61 MB, negligible relative to RFD3/RF3-class diffusion checkpoints (`rfdiffusion3.md`) and comparable to the ThermoMPNN/Stability Oracle class (`ddg-predictors.md`). Also ships a bundled CCD ligand database (`data/ligands.json.gz`, loaded at `PLACER.py:74`) and an internal `pdbx` parser (third-party, per the README's disclaimer) — no external database download required.
- **Container availability:** **none found.** No `Dockerfile`, Apptainer/Singularity definition, or `.dockerignore`-adjacent artifact anywhere in the refcode (`find . -iname "*dockerfile*" -o -iname "*.def"` returns empty); deployment is conda-only via the shipped `envs/placer_env.yml`, which is itself CUDA-12.1-pinned (see portability above).

## Deployment on DOE & ACCESS
- **Polaris / NSF ACCESS (NVIDIA, primary per shared context):** straightforward. `conda env create -f envs/placer_env.yml` installs a CUDA-12.1-toolkit-pinned environment (PyTorch 2.3 cu121, DGL 2.4.0 cu121, e3nn, OpenBabel 3.1.1). No license gate — BSD-3, weights included in the git clone (no separate weight-download step, unlike AlphaFold/ESM-scale checkpoints). This is the cleanest deployment story of any GPU-diffusion-adjacent tool in this toolkit precisely because there is no license friction and the weights ship in the repo.
- **Aurora (Intel XPU):** **not viable without replacing the DGL dependency.** No XPU code path exists in PLACER itself (see portability evidence above), and DGL has no SYCL/XPU backend to fall back to. This is a real, structural gap, not an unverified-but-plausible one — flag it plainly rather than assuming CPU fallback is an acceptable substitute (see Cost below for why it is not, at campaign scale).
- **Frontier (AMD HIP):** unproven, no evidence either way found; consistent with the project's deprioritization of Frontier, this is not worth resolving now.
- **Module vs. conda vs. apptainer:** conda is the only demonstrated path; building an Apptainer image from the conda env is possible but has not been done upstream — budget engineering time for this if container-first deployment is a hard requirement elsewhere in the toolkit's deployment posture.

## Agentic surface
- **Native MCP:** no. No MCP server for PLACER was found in this search (community or otherwise) — mark **no**, not "community/unverified," since no lead at all surfaced (contrast with ESM/AlphaFold-adjacent tools in this toolkit, which at least have an unverified community candidate).
- **Parameters worth exposing for autonomous variation:**

| parameter | type | sane range | default | trade-off |
|---|---|---|---|---|
| `nsamples` / `-n` | int | 10–200+ | 10 | ensemble size; README FAQ: "50-100 is a good number in most cases," >200 only if too few high-confidence models emerge at 50-100 — linear GPU-time cost, see Cost below |
| `--rerank` | enum | `prmsd` / `plddt` / `plddt_pde` | none | which score orders the output CSV/PDB; README recommends `prmsd` for docking-style tasks |
| `--fixed_ligand_noise` | float | model default (`sigma_bb`) up to several Å | `sigma_bb` from checkpoint params | how much a *fixed* ligand's coordinates are perturbed before denoising; higher explores more but risks losing the fixed pose's intended role |
| `--predict_ligand` / `--fixed_ligand` | selector | any ligand `name3`/`chain-name3-resno` in the input | all ligands predicted unless one is fixed | which ligand(s) PLACER treats as unknown vs. given — directly controls whether this call is "dock this ligand" or "validate the shell around a ligand I trust the pose of" |
| `--exclude_common_ligands` | bool | — | `False` | drops crystallographic solvents/additives (AlphaFold3 supplementary list) automatically — useful default-on when feeding raw RCSB structures |
| `--mutate` | selector | any position(s) | none | probes a point mutation's effect on local geometry in one call; **should not be used as a substitute for a full MPNN/Rosetta redesign pass** — it re-predicts local geometry around the mutation, not a globally repacked shell |

- **Parameters that must NOT be agent-varied:** the **crop size** (an emergent property of `--target_res`/`--crop_centers`/the model's own 20 Å corruption cutoff, `run_PLACER.py`'s `cutoff = 20` at the crop-graph step) should not be pushed past what the model was trained on — README FAQ #6 states plainly: "The model was not trained with more atoms [>600], so unexpected behavior and reduced confidence is very likely if one tried." An agent auto-expanding the crop to capture more context is silently leaving the model's trained regime. **`--corruption_centers` for blind/global docking** is a documented weak use case, not a tunable-for-more-coverage knob — README FAQ #9: "Technically yes... This is not ideal, and we should also note that PLACER was not explicitly developed for this task"; an agent should not treat wide `--corruption_centers` sweeps as equivalent in reliability to a properly-scoped `--predict_ligand` call with a known approximate site.

## Failure modes & what the agent must check
- **Loud failure:** missing input files, malformed `--bonds`/`--mutate` argument strings (`run_PLACER.py` calls `sys.exit(...)` on parse errors), a bonded-atom pair not present in the computed crop (`PLACER.py` explicitly prints "ERROR!! ... Atom {ctr.name} is not in the crop!" and `sys.exit(1)` — `PLACER.py:283-289`), an unrecognized ligand with no CCD entry and no `--ligand_file` reference.
- **Silent bad output — the modes the agent must actively check for:**
  - **Wrong atom hybridization/bonding from an under-specified input.** README FAQ #10, verbatim: aromatic rings coming out non-planar is "a potential cause... PLACER assigned wrong atom hybridization and bond features to some of the atoms." This happens specifically **when predictions are run on PDB files without providing a `.sdf`/`.mol2` reference** — the fix is procedural (always pass `--ligand_file`/`ligand_reference` for any non-trivial ligand), and the detecting check is equally procedural: **inspect output ring planarity** (e.g., improper-torsion/RMS-from-plane on aromatic rings) rather than trusting a good `prmsd` alone, since the README notes distorted molecules "occasionally" still get a not-obviously-bad confidence score.
  - **Overconfident geometry on an over-large crop.** No hard error occurs past the ~600-atom trained regime; the failure is silent reduced-confidence/garbage geometry per FAQ #6. The check: track crop atom count (available from the model's own `L = len(G)` at `PLACER.py:150`) and treat any run near or above 600 atoms as suspect regardless of its reported `prmsd`.
  - **`prmsd`/`plddt` disagreement across replicate samples treated as a single point estimate.** Because PLACER is stochastic (`nsamples` independent denoising runs), an agent that only inspects the single best-`prmsd` sample discards the ensemble's own uncertainty signal. Check the **spread of `prmsd` across the sample set**, not just its minimum — a tight, low-`prmsd` cluster is stronger evidence than one lucky low-`prmsd` outlier among widely scattered samples.
  - **`rmsd`/`kabsch`/`lddt` columns misread as blind accuracy on a genuinely novel design.** These are computed against the *input* structure's own coordinates (see Invocation & I/O contract) — for a design with no independent reference pose, a good `rmsd` only says "PLACER agrees with whatever pose was already in the file it was handed," which is a real and useful independent-repredicition check against, e.g., a Rosetta-matched geometry, but must not be reported or logged as "docking accuracy" the way it legitimately can be for a rediscovery benchmark against a crystal structure.
- **Cross-check role for enzyme design (recommended agentic practice):** run PLACER on any Rosetta-`enzyme_design` output with the catalytic ligand set via `--predict_ligand` and the rest of the structure fixed; a low `prmsd` (< 2.0) that also lands close (low `rmsd`/`kabsch` against the Rosetta-matched pose) is corroborating evidence the theozyme geometry is physically sensible, not just constraint-satisfying; a high `prmsd` or a large pose disagreement is a concrete, actionable flag to route back to human review per `rosetta-enzyme-design.md`'s recommended human-in-the-loop gate.

## Cost per unit of work
- **1 sample, GPU:** README FAQ #12, verbatim: "One model of an average ligand-protein complex will be predicted on a GPU within 1-3 seconds, depending on how powerful the GPU is." Larger-automorphism ligands (many symmetric substructures) take longer.
- **1 sample, CPU:** same FAQ entry — "~7 minutes" on 1 core, "~1 minute" on 8 cores. That is a **~150–400× slowdown vs. GPU** depending on core count — CPU is functionally correct but not a viable substitute for any campaign-scale ensemble (a 50-sample ensemble is ~2–3 minutes on GPU vs. ~6 hours on 1 CPU core / ~50 minutes on 8 cores).
- **A full `nsamples=50-100` ensemble (README's own recommended range):** ~1–5 minutes total on one GPU; this is the unit an agent should budget per PLACER call, not per-sample.
- **Checkpointable:** no — sub-few-minute P1 calls of this shape should never be individually scheduled/checkpointed at the job level, per the taxonomy's P6-adjacent guidance for cheap in-job work; batch an entire `nsamples` ensemble as one call.

## Verdict
**Recommended, as a validation/cross-check layer for enzyme and small-molecule design, not a Rosetta replacement.** PLACER is the only tool in this toolkit that predicts ligand/active-site atomic geometry **without requiring a hand-authored theozyme or `.cst` file**, which makes it a genuinely useful, architecturally-independent check on the single hardest-to-catch silent failure mode identified in `rosetta-enzyme-design.md` — geometrically constraint-satisfying but chemically meaningless active-site placements. It does not remove the need for a human (or template library) to specify the catalytic hypothesis in the first place, and its own accuracy is bounded by the same "no SMILES-only start, needs correct ligand chemistry input" caveat that plagues every tool in this cluster (`ligand-parameterization.md`). Its BSD license, small weight footprint (61 MB, bundled in-repo), and fast per-sample cost (1-3 s/GPU-sample) make it cheap to run routinely as a post-hoc check on any Rosetta enzyme-design or Boltz/Chai-derived small-molecule pose, which is where its verdict-worthy value sits. Its CUDA-only supply chain (via DGL) is a real but currently inconsequential platform risk given Polaris/ACCESS are this project's primary targets.
