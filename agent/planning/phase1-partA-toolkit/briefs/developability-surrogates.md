# Developability surrogates (solubility, expression, aggregation)

**One-line identity.** A curated set of fast, sequence/structure-based predictors — NetSolP, Protein-Sol, CamSol, SoluProt for solubility/expression; Aggrescan3D and the AGGRESCAN/TANGO/WALTZ sequence-only lineage for aggregation; SolubleMPNN as a design-time intervention; ESM likelihood as a general-purpose weak proxy — that close a real Part A coverage gap: **a design can be stable and well-folded in silico and still be unexpressible.**

None of these tools are present in `impress-a-refcodes/tools/`. This brief is WebSearch-derived from upstream papers, repos, and comparative-benchmarking literature, in the same spirit as `ddg-predictors.md` and `esm-scoring.md` — numbers are reported-by-source, not independently reproduced, and are flagged as such throughout.

## Solubility / expression predictors

### Identity
- **NetSolP** — DTU Health Tech (Technical University of Denmark); GitHub `TviNet/NetSolP-1.0` (standalone `PredictionServer/` directory, `predict.py --MODEL_TYPE ESM12 --PREDICTION_TYPE S`), also a hosted webserver (`services.healthtech.dtu.dk/service.php?NetSolP`). Built on ESM1b/ESM12 protein-language-model embeddings (Meta AI, MIT — see `esm-scoring.md`) with a downstream classifier head. Paper: Thumuluri et al., *Bioinformatics* 38(4), 2022.
- **Protein-Sol** — University of Manchester (Hebditch, Warwicker et al.); a linear model over 35 sequence-derived features, fitted to the Niwa et al. (2009) *E. coli* cell-free expression dataset (~3,000 proteins). Webserver at `protein-sol.manchester.ac.uk`; a standalone downloadable package was not independently confirmed in this search — treat as web-server-primary pending verification.
- **CamSol** — University of Cambridge (Vendruscolo lab, Sormanni et al.); a physicochemical propensity-scale method with an intrinsic (sequence-only) and a structurally-corrected variant, plus a newer pH-dependent version (CamSol 3.0). Webserver-primary (`www-vendruscolo.ch.cam.ac.uk/camsolmethod.html`); local/standalone distribution not independently confirmed.
- **SoluProt** — Loschmidt Laboratories, Masaryk University; a gradient-boosted-tree classifier over sequence/structural features. Paper: Hon et al., *Bioinformatics* 37(1), 2021. Webserver-primary; standalone package not independently confirmed in this search.

None of these four licenses were independently read in full in this search (mirrors the license-verification caveat already carried by ThermoMPNN/Stability Oracle in `ddg-predictors.md`); treat as academic-web-tool defaults pending direct confirmation before any redistribution/bundling decision.

### Scientific role
**Score** stage, serving the **stability/thermostabilization** problem class' missing developability axis directly, and applicable as a post-hoc filter across all four problem classes — any generated sequence, regardless of which generator produced it, can be scored. All four predict a binary or continuous solubility/expression outcome **specifically in the *E. coli* expression context** their training data comes from (PSI:Biology structural-genomics data for NetSolP/SoluProt comparisons, Niwa cell-free data for Protein-Sol) — this is a real scope limitation, not a detail: a design destined for a different expression host, cell-free system, or in-vitro synthesis is being scored against a proxy for a different question than the one that will actually determine its outcome.

### Invocation & I/O contract
- **NetSolP:** `python predict.py --FASTA_PATH in.fasta --OUTPUT_PATH out.csv --MODEL_TYPE ESM12 --PREDICTION_TYPE S` (documented usage from the `TviNet/NetSolP-1.0` README) — input a FASTA sequence, output a per-sequence solubility score/class plus (via `--PREDICTION_TYPE U`) a usability-for-purification classification. Pretrained ONNX-converted models ship from the repo's Downloads tab.
- **Protein-Sol / CamSol / SoluProt:** sequence (FASTA) in via each tool's webserver form; CamSol's structurally-corrected and pH-dependent variants additionally accept a structure. No repo-local example exists for any of the three; exact batch/API invocation was not independently confirmed for any of them in this search — flag this as a real deployment-friction finding, not an oversight (see Deployment below).

### Compute pattern
- **NetSolP:** **P1** (GPU-node-local, in-job) when using its PLM embeddings at any throughput worth batching — same shape as ESM2 scoring (`esm-scoring.md`); CPU-viable for small batches.
- **Protein-Sol / CamSol (intrinsic):** **P6** (in-process library call) by architecture — both are closed-form linear/propensity-scale formulas over sequence features, sub-second, no learned forward pass, no GPU — *if* a local reimplementation or standalone package is used; as currently deployed (web-server-primary) they are **P5** (network service) instead, which is a materially worse scheduling posture for an autonomous campaign (see Deployment).
- **SoluProt:** **P6**-shaped (gradient-boosted trees, no GPU) under the same web-server-vs-local caveat as above.

### Deployment on DOE & ACCESS
NetSolP is the only one of the four with a **confirmed, standalone, locally-runnable code path** (`PredictionServer/predict.py`) — straightforward `pip install` of its ESM1b/ESM12 dependency on Polaris/ACCESS, no license gate found. Protein-Sol, CamSol, and SoluProt are **web-server-primary tools with no independently-confirmed batch/local-install/API path** in this search. This is a genuine deployment problem for an autonomous HPC agent, structurally identical to the friction `rosetta-ddg.md`/`ddg-predictors.md` flagged for FoldX's license gate, except the blocker here is *absence of a documented programmatic interface* rather than licensing. **Do not assume these three are one-line `pip install`s** — verify a batch path exists (a downloadable command-line version, a documented REST API, or a locally-reimplementable published formula) before building pipeline dependencies on them; where none exists, either drop the tool from the autonomous loop or reimplement its published, closed-form scoring formula in-process (viable for Protein-Sol and CamSol-intrinsic, both linear-combination-of-features methods with published weights; not viable for SoluProt's tree ensemble without its actual trained model file).

## Aggregation predictors

### Identity
- **Aggrescan3D (A3D)** — Laboratory of Computational Biology, University of Warsaw, with the Laboratory of Protein Folding and Conformational Diseases, University of Barcelona. Standalone Python package (PyPI `Aggrescan3D`, conda, Docker), **MIT license, "free for academic and non-profit users"** per the package's own distribution terms. Repository: `bitbucket.org/lcbio/aggrescan3d`. Paper: Zambrano et al. (original A3D, *NAR* 43(W1), 2015); Kuriata et al. (standalone package, *Bioinformatics* 35(19), 2019). **Flag:** the standalone package was released as a Python 2.7 package per its 2019 paper; Python 2.7 is end-of-life — verify a maintained Python 3 fork/port exists before depending on it for a Phase-1-era pipeline. This was not independently confirmed in this search and is a real, concrete deployment risk if unresolved.
- **AGGRESCAN (1D)** — same Barcelona lab lineage, the original sequence-based aggregation-propensity method (Conchillo-Solé et al., *BMC Bioinformatics* 2007). Webserver-primary (`bioinf.uab.es/aggrescan`); no standalone package independently confirmed.
- **TANGO** — CRG (Centre for Genomic Regulation), Barcelona; statistical-mechanics-based β-aggregation predictor (Fernández-Escamilla et al., *Nat. Biotechnol.* 2004). **License-gated**: `tango.crg.es/academic-license-info` requires registration/login for the downloadable academic-license binary — the same license-gate posture as FoldX in `ddg-predictors.md`, and should be resolved the same way (confirm academic eligibility explicitly, do not assume it applies).
- **WALTZ** — SWITCH Laboratory (VIB/KU Leuven); amyloid-specific hexapeptide aggregation predictor (Maurer-Stroh et al., *Nat. Methods* 2010), narrower in scope than the others — tuned specifically for cross-β amyloid propensity, not general colloidal/expression aggregation. Webserver-primary (`waltz.switchlab.org`); no standalone package independently confirmed.

### Scientific role
**Score** stage, targeting a distinct failure mode from solubility/expression predictors above: a sequence can express solubly and still aggregate later (in storage, in formulation, or in vivo) if it carries exposed aggregation-prone regions. Aggrescan3D is structurally distinguished from the other three by being **structure-aware**: it corrects the sequence-only AGGRESCAN propensity scale using actual per-residue solvent accessibility in the folded structure, directly addressing the well-known failure mode of sequence-only aggregation predictors — "these regions may be buried [in native globular proteins]... the algorithms display a large set of false positive predictions when analyzing folded states" (per the A3D paper's own stated motivation). For any design coming out of this toolkit's structure-generation stages (RFD3, RFD3NA), a structure is already in hand, so there is no reason to accept sequence-only false-positive risk when the structure-aware alternative is a standard `pip install` away.

### Invocation & I/O contract
- **Aggrescan3D:** CLI/Python package taking a PDB structure, outputting a per-residue aggregation profile and an overall aggregation score; documented usage pattern per its own paper and PyPI listing, not independently re-verified against a local install in this pass.
- **AGGRESCAN / TANGO / WALTZ:** sequence in, per-residue propensity profile out, via each tool's own webserver form (or TANGO's license-gated binary); no repo-local example available for any of the three.

### Compute pattern
- **Aggrescan3D:** **P2**-shaped (CPU, structural post-processing over a single input structure, not a learned forward pass) once locally installed — cheap, embarrassingly parallel across candidate structures.
- **AGGRESCAN / TANGO / WALTZ:** nominally **P6**-shaped (simple sequence-window scoring, formula/table-lookup based, no GPU) but, as with Protein-Sol/CamSol above, **effectively P5** (web-service-bound) as currently deployed for AGGRESCAN and WALTZ, and license-gated for TANGO — the same deployment caveat as the solubility cluster applies here with equal force.

### Deployment on DOE & ACCESS
Aggrescan3D is the only aggregation tool in this cluster with a clean, license-clear, standalone-package deployment story for Polaris/ACCESS — **pending the Python 2.7 verification flagged above**. TANGO requires resolving its academic license explicitly, the same way `ddg-predictors.md` requires resolving FoldX's, before any production dependency. AGGRESCAN and WALTZ have the same undocumented-batch-path problem as Protein-Sol/CamSol; their underlying propensity-scale methods are published and, for AGGRESCAN specifically, small enough to be plausible to reimplement in-process if a local dependency is required, but this has not been done or verified here.

## SolubleMPNN — a design-time intervention, not a scoring-time filter

### Identity
Already covered as part of the MPNN family in `proteinmpnn-ligandmpnn.md` (checkpoint `solublempnn_v_48_020.pt`, `foundry install solublempnn`, BSD license, Institute for Protein Design). Original weights: `dauparas/ProteinMPNN`, `soluble_model_weights/` (two noise levels, 0.1 Å and 0.2 Å). Paper context: *Nature* 2024, 10.1038/s41586-024-07601-y (soluble analogues of membrane proteins).

### Scientific role
**This is the one tool in this brief that belongs at design time, not scoring time, and that distinction is deliberate and worth stating plainly.** Every other tool in this brief takes a sequence (or structure) that already exists and predicts whether it will be soluble — a purely retrospective judgment an agent can only act on by discarding or down-ranking the candidate. SolubleMPNN instead **retrains the inverse-folding step's own sampling distribution**: it was trained on the same backbone-to-sequence task as ProteinMPNN, but with transmembrane PDB entries excluded from training, so its sampled sequences are systematically biased away from surface-exposed hydrophobic patches *before a candidate sequence exists to be scored at all*. An agent choosing SolubleMPNN over plain ProteinMPNN/LigandMPNN at the inverse-fold stage for a given backbone is making a generative choice that shifts the whole distribution of what gets proposed, not filtering after the fact.

**Practical implication for pipeline design:** run SolubleMPNN as the default inverse-folder whenever solubility is a stated campaign objective and the backbone has no hard requirement for LigandMPNN's ligand-conditioning (the two are not simultaneously usable per checkpoint — verify against `proteinmpnn-ligandmpnn.md`'s own parameter table); reserve the scoring-time predictors above for **candidates that did not go through SolubleMPNN** (e.g., anything from LigandMPNN, ESM-IF1, or a legacy sequence pool) and as a **second-opinion check even on SolubleMPNN's own output** — a generative bias is not a guarantee, and nothing in this brief licenses skipping the scoring-time check just because the design-time one was used.

### Invocation & I/O contract
Identical CLI/API surface to ProteinMPNN/LigandMPNN, with `solublempnn` selected as the checkpoint — see `proteinmpnn-ligandmpnn.md` in full; not repeated here to avoid drift between the two briefs.

### Compute pattern
Identical to ProteinMPNN/LigandMPNN (P1, GPU-node-local, in-job; see `proteinmpnn-ligandmpnn.md` for the full portability evidence) — same checkpoint family, same inference engine, only the trained weights differ.

### Deployment on DOE & ACCESS
Same as ProteinMPNN/LigandMPNN with one SolubleMPNN-specific note: it requires an explicit `foundry install solublempnn` beyond the default `foundry install base-models` (which installs ProteinMPNN + LigandMPNN only).

## ESM likelihood as a weak general proxy

Already covered in full in `esm-scoring.md`, which is the normative source for this signal's scope, accuracy, and failure modes (masked-marginal scoring, model sizes, VRAM, licensing). It is listed here only to be explicit about its (limited) role in the developability cluster: ESM2 pseudo-likelihood is a **general sequence-plausibility signal**, not a solubility-specific one — it answers "does this look like something evolution would produce," which correlates weakly and indirectly with expression success, and `esm-scoring.md` already documents that this correlation **collapses specifically for de novo designed sequences with no evolutionary history** — precisely this toolkit's dominant design-generation mode. Do not stand up ESM likelihood as a solubility gate on its own; use it, if at all, as one more weak vote in an ensemble alongside the dedicated predictors above, with the same "ranking-only, never a gate" posture `esm-scoring.md` already assigns it for stability.

## Agentic surface
- **Native MCP:** no, for every tool in this cluster — no MCP server (native or community) was found for NetSolP, Protein-Sol, CamSol, SoluProt, Aggrescan3D, AGGRESCAN, TANGO, or WALTZ in this search.
- **Parameters worth exposing for autonomous variation:**

| Parameter | Tool(s) | Type | Sane range | Trade-off |
|---|---|---|---|---|
| classification threshold | NetSolP, SoluProt, any binary-output predictor | float | dataset-dependent, default 0.5 | shifting toward "more permissive" widens the shortlist at the cost of more false accepts; given the accuracy numbers below, tightening the threshold is generally safer than loosening it |
| noise level (0.1 Å vs 0.2 Å checkpoint) | SolubleMPNN | enum | per-checkpoint | same trade-off shape as ProteinMPNN's own `structure_noise` — higher noise, more sequence diversity, somewhat lower recovery |
| structural vs. intrinsic mode | CamSol, Aggrescan3D | selector | — | structure-aware variants correct sequence-only false positives on buried regions; prefer structural mode whenever a structure is already in hand (true for essentially every design in this toolkit) |
| ensemble agreement requirement | agent-level, not a tool flag | int/float | e.g. "≥2 of {NetSolP, CamSol, SoluProt} agree" | see the gate-vs-signal table below — cross-predictor agreement is more informative than any single predictor's threshold |

- **Parameters that must NOT be agent-varied:** the **expression-host assumption** (almost universally *E. coli*, cytoplasmic, across this entire cluster) must never be silently generalized to "solubility" as a host-agnostic property — a design intended for a different host, a cell-free system, or a fundamentally different downstream use should not be scored against an *E. coli*-trained predictor and reported as "solubility," full stop; if the campaign's actual expression context differs from the training context, say so in the provenance record (see below) rather than relabeling the score.

## Failure modes & what the agent must check

### The accuracy picture, stated plainly — named benchmarks, not vibes
This is the section `ddg-predictors.md` modeled for this toolkit, and the honest picture here is **worse**, not better, than the ΔΔG predictor cluster:

- **NetSolP** is the strongest-benchmarked tool in this list: on the **PSI:Biology "Solubility" 5-fold cross-validation set** (11,226 sequences), AUC 0.73 ± 0.02, MCC 0.29 ± 0.04, accuracy 0.70 ± 0.02; on an **independent test set** of 1,323 proteins (620 soluble / 703 insoluble), AUC 0.760, MCC 0.402, accuracy 0.728, precision 0.773 (Thumuluri et al., *Bioinformatics* 2022). These are respectable numbers for a binary classification task, but MCC ≈ 0.4 means the classifier is meaningfully better than a coin flip, not a precise instrument.
- **SoluProt**, on its own paper's comparative benchmark, reports accuracy **58.5%**, AUC **0.62** — beating PROSO II (58.0%), SWI (55.9%), and **CamSol (54.1%)** on the *same* benchmark (Hon et al., *Bioinformatics* 2021). **State this plainly: on this apples-to-apples comparison, every tool except NetSolP clusters within a few points of chance-level accuracy for a roughly-balanced binary classification task.** CamSol's 54.1% figure here is specifically its performance as a generic *E. coli* binary solubility classifier — a task it was not primarily designed or validated for (see below).
- **PLM_Sol**, a newer transformer-ensemble tool (2024, not independently vetted here as a toolkit candidate), reports a 9.0% F1 improvement over SoluProt on an updated *E. coli* benchmark — evidence the field is improving, and a name worth revisiting, but not yet load-bearing.
- **CamSol's much stronger headline correlations belong to a narrower claim than "predicts solubility of a novel protein."** Sormanni et al. report Pearson r = 0.97 (VH-domain-only) / 0.93 (combined-chain) for **ranking antibody variants of the same scaffold family** — an intra-family, homologous-variant ranking task, not cross-protein classification. CamSol 3.0's pH-dependent predictions likewise report r > 0.67, up to 0.9–0.92 with correction, but **for a small set of well-studied individual proteins (BSA, HSA, lysozyme) against their own published solubility-vs-pH curves**, not a held-out novel-protein benchmark. Both of these are genuinely strong results for the narrow task CamSol was built and validated for; neither licenses treating CamSol as a general accept/reject classifier for arbitrary novel designs, where its own comparative accuracy (54.1%, above) is near chance.
- **Aggregation predictors are more qualitative than the solubility cluster in this search.** No independent-benchmark AUC/accuracy figure comparable to NetSolP's PSI:Biology numbers was found for AGGRESCAN, TANGO, or WALTZ. The field's own trajectory is informative here: AggrescanAI (a newer entrant, not covered as a primary recommendation in this brief) is reported to outperform *both* AGGRESCAN and Aggrescan3D — meaning the lab that produced Aggrescan3D itself now has a tool it considers an improvement on it. Treat AGGRESCAN/TANGO/WALTZ output as **qualitative propensity profiles for triage**, not calibrated probabilities, and treat Aggrescan3D as the better-grounded (structure-aware) default among the mature options while noting it, too, may already be superseded.
- **The de novo design generalization gap is the same one `esm-scoring.md` and `ddg-predictors.md` already documented, and it applies here with full force.** None of these predictors were trained on computationally-designed sequences; all were trained on natural or natural-derived proteins expressed by conventional means. The most directly relevant evidence: a benchmark of **614 experimentally characterized de novo designed monomers** across 11 design studies (2012–2021) found that confidence metrics from structure-prediction/design-evaluation models showed only moderate ability to discriminate expression/solubility/folding success from failure, that **many failed designs scored better than successful ones**, and that this was **topology-dependent** (bioRxiv 2025.07.29.667290 / PMC12817478 — the same paper already cited in `esm-scoring.md` for ESM2's parallel failure on de novo miniproteins). This is not a hypothetical caveat: it is the literature-documented reason none of the predictors above should be trusted more on a de novo RFD3/RFD3NA-derived design than the same literature already says to distrust ESM2 or ΔΔG confidence on the same design. **A newer tool, Pro4S** (2026, single-paper, not independently vetted here), reports it was built specifically to close this gap — claiming a 52.7% reduction in false-negative (non-expressed) predictions on de novo designs while retaining 96.7% of true positives — worth watching, not yet worth depending on given its single-source status.

### Which signals are safe as autonomous accept/reject gates vs. soft ranking only

| Signal | Gate or ranking-only? | Why |
|---|---|---|
| Any single solubility/aggregation predictor's raw score (NetSolP, SoluProt, Protein-Sol, CamSol, AGGRESCAN, TANGO, WALTZ) | **Ranking only.** | Best-case independent accuracy (NetSolP) is MCC ≈ 0.4; most of the cluster sits within a few points of chance on a fair benchmark; none were trained on de novo-designed sequences, which is the toolkit's dominant design-generation mode. |
| Cross-predictor agreement (e.g. NetSolP + SoluProt + CamSol all flag the same design as poor) | **Usable as a soft inclusion/exclusion signal**, still not a hard gate. | Different training data and architectures make correlated false positives less likely; disagreement is itself informative (same logic `ddg-predictors.md` applies to ThermoMPNN-vs-Stability-Oracle disagreement) but no validation study of this specific ensemble was found — treat as principled, not proven. |
| Aggrescan3D structure-aware aggregation score | **Ranking only, but the better-grounded ranking signal of the aggregation cluster.** | Structure-awareness removes a documented, mechanistic false-positive source (buried regions flagged by sequence-only methods); still no independent-benchmark accuracy figure found to promote it further than ranking. |
| SolubleMPNN as a design-time choice | **Not a gate at all — a generative bias, evaluate its output with the scoring-time tools above like any other candidate.** | Shifts the sampling distribution; does not certify any individual sampled sequence. |
| ESM likelihood, on solubility specifically | **Ranking only, weakest signal in this cluster.** | General sequence-plausibility proxy, not solubility-specific; documented failure on de novo sequences per `esm-scoring.md`. |
| Final accept for any downstream commitment (synthesis, expression, campaign pivot) | **Never on any in-silico developability surrogate alone, full stop.** | No predictor in this cluster has demonstrated accuracy, on a fair out-of-distribution benchmark, strong enough to license an irreversible or expensive downstream action without a measured value. This is the honest default the evidence supports, and it is the reason the rest of this brief is about making measured values a drop-in replacement rather than about trusting the surrogates harder. |

## Cost per unit of work
- **NetSolP, SoluProt-class ML predictors:** sub-second to a few seconds per sequence on CPU or GPU, effectively free at campaign scale — same order of magnitude as ThermoMPNN (`ddg-predictors.md`) and ESM2 scoring (`esm-scoring.md`).
- **Protein-Sol, CamSol-intrinsic (closed-form/linear methods):** sub-second per sequence if run in-process; if run via their current web-server-primary deployment, cost is dominated by **network latency and manual/scripted form submission**, not compute — this is a real practical cost an agent's scheduler must account for and is a strong argument for reimplementing the published formula locally rather than depending on the webserver.
- **Aggrescan3D:** low seconds per structure on CPU (structural post-processing, not a learned forward pass), embarrassingly parallel across a candidate batch.
- **AGGRESCAN / TANGO / WALTZ:** comparable per-call cost to Protein-Sol/CamSol once a local formula/binary path exists; effectively free.
- **SolubleMPNN:** identical cost profile to ProteinMPNN/LigandMPNN — see `proteinmpnn-ligandmpnn.md`.
- **Checkpointable:** n/a for all — every tool in this cluster is sub-minute P1/P2/P6-shaped work and should be batched as a single call per candidate set, never individually scheduled, per the taxonomy's guidance for cheap in-job work.

## Designing for experimental replacement

This is the reason this brief exists, and the design requirement is already partially settled elsewhere in this project — this section states it for the developability surrogates specifically and points at where the rest of the abstraction lives, rather than inventing a second, competing scheme.

**The predicted-vs-measured distinction, and why it should not be two quantities.** A predicted solubility and a measured solubility answer the same scientific question — *is this design soluble* — with radically different authority: one is a proxy trained on a biased, host-specific historical dataset with MCC ≈ 0.3–0.4 at best (see accuracy discussion above); the other is a direct physical observation. If a campaign models these as unrelated fields (`predicted_solubility` vs. `measured_solubility`), every objective definition, every Pareto computation, every policy prompt, and every downstream consumer that reasons about "solubility" has to be rewritten the day the first robotic-lab assay result arrives. The correct design instead treats them as **the same property, `solubility`, carrying different `source`, `authority`, and `confidence`** — a campaign objective declared as `minimize aggregation_propensity` or `require solubility > threshold` is satisfiable by a surrogate today and by an assay tomorrow with no change to the objective's name or the code that evaluates it.

**This is not a proposal — it is already the decided design for this project.** Decision record `docs/decisions/0012-one-property-two-sources.md` establishes exactly this move ("a predicted value and a measured value for the same quantity are the same `Property` type with different `source`, `authority`, and `confidence` — not two unrelated quantities"), and `docs/phase1-partB-architecture/09-measurement-and-experimental-seam.md` works out the resulting data model in full: a `Property` dataclass (`name`, `value`, `unit`, `source`, `confidence`, `observed_at`, `provenance`), a `PropertySource` protocol distinguishing `kind: "predicted" | "measured"` and carrying a `latency_class` and an integer `authority`, and — critically for this brief — Part B's own source table **already lists the exact tools covered here** (NetSolP/Protein-Sol/CamSol as `predicted`/`low authority`, ESM likelihood as `predicted`/`lowest authority`, a future robotic-lab assay as `measured`/`highest authority`). This brief's job is to confirm that table is honestly grounded — it is: nothing above claims accuracy strong enough to justify anything but `low` authority for any surrogate in this cluster.

**What a measurement needs that a prediction does not**, per the same architecture document: assay identity and protocol version, instrument and laboratory, conditions (buffer, temperature, pH, concentration, expression host — the exact variable these surrogates are trained on a fixed, narrow value of), replicate count and dispersion rather than a bare point value, sample lineage, dates for both sample and measurement, and explicit failure/ambiguity states (`assay_failed`, `below_detection`, `inconclusive`) that have no analogue in a predictor, which is always total and always returns a number. Coercing a `below_detection` result to zero, or discarding an ambiguous assay, corrupts the record in a way a predictor's failure modes never do.

**How a Pareto front should treat measured vs. predicted values for the same objective:** the measurement supersedes the prediction — higher `authority` wins for ranking and objective evaluation — but the prediction is **not deleted**; the predicted/measured pair for the same design node, once both exist, is itself the calibration signal a surrogate's real-world accuracy can eventually be checked against, which nothing in this cluster's published literature currently offers (every accuracy number above comes from the surrogate's own training-adjacent benchmark, not from paired predictions-and-assays on this project's own designs). A front that mixes measured and predicted evidence for the same objective must record which is which — collapsing them into one undifferentiated ranking silently compares two different levels of evidence, and a node promoted on an optimistic prediction must be allowed to be demoted once its own assay comes back worse. The front is not monotonic once measurements start arriving, and any consumer of it must tolerate that.

**Latency, and why a measurement is not a task result.** A surrogate call in this brief returns in milliseconds to low seconds (Cost section above); a robotic-lab assay returns in **days to weeks**, and the returning result routinely outlives the design cycle that requested it and, not infrequently, the campaign itself. This is not P4 (external HPC job) shape — P4 work finishes in hours and the agent polls it; an assay is out-of-band and asynchronous on a wholly different timescale. The taxonomy (`compute-pattern-taxonomy.md`) forward-declares exactly this as **pattern P8 — external experiment**, currently unused by any tool in the Part A roster, precisely so that this shape does not need to be retrofitted later. Practically: a measurement must arrive as an **update to an existing design node** through the campaign's control plane (`ingest_measurement`, per Part B `09`), not as a return value the requesting cycle waits on — and it must be acceptable for that update to land against a paused or even terminated campaign, since campaign storage is append-only for exactly this reason.

**The minimal abstraction that keeps today's surrogates and tomorrow's robotic-lab queries interchangeable** — four commitments, already adopted by decision `0012` and Part B `09`, restated here as the concrete requirement this brief's tools must be built against:
1. Objectives are declared against the property **name** (`solubility`, `aggregation_propensity`) — never against a source-qualified name like `netsolp_score` or `assay_result`.
2. Every value carries `source`, `authority`, and `confidence` as first-class fields, not as a comment or a separate lookup table.
3. Design-node records are append-only, so a later, higher-authority measurement supersedes rather than overwrites — the surrogate-vs-assay gap stays visible.
4. An ingestion path exists on the control plane that accepts a measurement for any node at any campaign state (running, paused, or terminated).

With those four in place, adding a robotic lab later is registering one new `PropertySource` with `kind="measured"` for each property this brief covers and wiring its callback — not redesigning anything the surrogates above were built against.

## Verdict
**NetSolP: Recommended**, as the best-evidenced soft ranking signal in the solubility cluster — the only tool here with an independent-benchmark MCC meaningfully above zero, a confirmed local/batch invocation path, and no license gate. Never an accept/reject gate (accuracy does not support it), and never trusted more on a de novo design than the literature already says to distrust its own PLM backbone (`esm-scoring.md`) on the same design class.

**CamSol, SoluProt: Recommended as ensemble members, not primary signals.** Real, differently-architected value for cross-predictor agreement/disagreement detection alongside NetSolP; CamSol's own strongest validated use (antibody-variant ranking, pH-dependent curves for known proteins) is narrower than "general novel-protein solubility classifier," and its accuracy on the fair general-classification benchmark (54.1%) reflects that — use it for the task it is validated for and as an ensemble vote, not as a stand-alone general classifier. Verify a local/batch invocation path for both before depending on either in an autonomous loop.

**Protein-Sol, AGGRESCAN, TANGO, WALTZ: Defer**, pending resolution of the same deployment-friction problem across all four — either a confirmed batch/API path, a license clearance (TANGO), or a verified local reimplementation of the published formula. None has an accuracy story strong enough to justify absorbing that integration cost ahead of the tools already Recommended above.

**Aggrescan3D: Recommended**, as the default aggregation-propensity check for any design with a structure already in hand (true for essentially everything this toolkit produces) — structurally better-grounded than the sequence-only lineage it descends from, MIT-licensed, standalone-installable — **conditional on verifying a maintained Python 3 path**, given the flagged Python 2.7 packaging risk.

**SolubleMPNN: Recommended**, as the default inverse-folder whenever solubility is a stated campaign objective and ligand-conditioning is not required — already Recommended in `proteinmpnn-ligandmpnn.md`; this brief adds the design-time-vs-scoring-time framing and makes explicit that its output must still pass through the scoring-time predictors above, not substitute for them.

**ESM likelihood as a solubility signal: Recommended only as a weak ensemble member, never primary** — fully consistent with, and not exceeding, its existing `esm-scoring.md` verdict.

**The experimental-replacement design requirement: satisfied by adoption, not by anything this brief invents.** The `Property`/`PropertySource`/P8 abstraction already exists in this project's own architecture (decision `0012`, Part B `09`) and already accounts for every tool covered here at `low`/`lowest` authority. This brief's contribution is confirming, with the accuracy numbers above, that the low-authority assignment is honestly earned — none of these surrogates should be trusted at a higher authority tier than "soft ranking signal, supersede on first measurement."
