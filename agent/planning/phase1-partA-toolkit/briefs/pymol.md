# PyMOL

**One-line identity.** The field-standard molecular visualization/scripting system, notable in this toolkit for one specific reason: it has a **verified, live, native MCP server** in this very session — one of the few genuinely confirmed (not just claimed) MCP entries across the entire toolkit.

## Identity
- **Version / release examined:** open-source core at `schrodinger/pymol-open-source` on GitHub; the MCP integration examined directly in this session, tool-by-tool, via the session's own MCP tool registry (`mcp__pymol__*`, 24 tools). Cross-referenced against **Arcadia-Science/agentic-pymol** (MIT license): its documented architecture — "runs as a plugin within a live PyMOL GUI session, listening on a local TCP socket, **default port 9877**" — matches this session's own connection error verbatim (`ConnectionError: could not connect to PyMOL plugin at 127.0.0.1:9877 ([Errno 111] Connection refused)` when `status` was called with no PyMOL GUI running), which is strong fingerprint evidence for the specific server identity, though not a byte-for-byte confirmed match against the repo's own tool-name list (the repo's public docs describe tool *categories* — "alignments, geometry, session inspection, rendering" — rather than enumerating exact names).
- **Provenance:** PyMOL core — originally Warren DeLano (2000), later acquired and now maintained by **Schrödinger, LLC**, which publishes the open-source foundation (`pymol-open-source`, permissive BSD-like license, copyright assigned to Schrödinger) alongside a commercial **Incentive PyMOL** product with support/maintenance and some closed-source extensions. The MCP layer (`agentic-pymol` or an architecturally identical fork) is a third-party plugin, MIT-licensed, built on top of either PyMOL variant.
- **Maturity:** PyMOL core — production, one of the two or three most widely used molecular visualization tools in structural biology, decades of continuous use. The MCP plugin layer — new (2025/2026-era), actively developed, genuinely exercised in this session's own tool registry rather than merely claimed.

## Scientific role
PyMOL itself is not a generator, predictor, or scorer — it is a **structure inspection, measurement, and visualization** tool. Its MCP-exposed surface serves two distinct agent-facing roles relevant to this toolkit:
1. **Programmatic structural analysis** — superposition, RMSD, distance measurement, atom-property iteration, sequence/chain extraction — usable as a lightweight, general-purpose structural-QC utility across all four in-scope problem classes (stability, binder design, enzyme design, small-molecule binding), overlapping in places with `us-align.md` (superposition/RMSD) and `structure-libraries.md` (atom-level property access).
2. **Human-in-the-loop visualization and campaign reporting** — rendering images/sessions for a human reviewer, the one genuinely irreplaceable role none of this toolkit's other structural tools cover.
Pipeline stage: **analyze** (measurement/comparison) primarily, **visualize/report** secondarily; never generate/predict.

## Invocation & I/O contract
- **How a unit of work is invoked:** MCP tool calls in this session, one per PyMOL operation — `mcp__pymol__<tool>` — each a typed wrapper around a specific `cmd.*` PyMOL API call, plus two escape hatches (`do`, `run`) for anything not covered by a dedicated tool. Verified directly against this session's own tool schemas (not inferred):
  - **Structural comparison:** `align(mobile, target, method="align"|"super", cutoff=2, cycles=5, transform=True, object_name="")` (sequence-aware Needleman-Wunsch + iterative refinement, or structure-aware `super` for distant homologs); `cealign(mobile, target, transform=True)` (Combinatorial Extension, sequence-independent, best for very low sequence identity); `rms(mobile, target, fit=False, matchmaker=0)` (RMSD without new superposition — `fit=True` calls `cmd.rms` with iterative outlier rejection, `fit=False` calls `cmd.rms_cur` on current coordinates).
  - **Geometry/measurement:** `get_distance(atom1, atom2, state=-1)` (Å between two single-atom selections); `get_extent(selection="all")` (axis-aligned bounding box).
  - **Atom-level data:** `iterate(selection, properties, state=-1)` → `list[dict]`, capped at 200,000 rows, arbitrary PyMOL atom attributes (`resi`, `resn`, `name`, `chain`, `b`, `x`, `y`, `z`, ...); `get_coords`, `get_model` (fuller structured access); `alter` (mutate atom properties in-session).
  - **Session/object management:** `load(filename, object_name="", state=0, format="")` (PDB/CIF/MOL2/SDF/MAE and more, format auto-detected from extension); `fetch(code, name="", type="cif", path="")` (synchronous RCSB fetch — a **P5** operation, see Compute pattern); `save`; `get_names`, `get_object_list`, `get_chains`, `count_atoms`, `count_states`; `get_view`/`set_view`.
  - **Sequence extraction:** `get_fastastr(selection="all", state=-1)`.
  - **Rendering:** `render`, `screenshot`.
  - **Escape hatches:** `do(command)` — runs a verbatim PyMOL CLI string through `cmd.do(...)`, returns unstructured stdout text, **does not raise on PyMOL errors** (failures come back as text in the output, so the agent must inspect the return string rather than rely on exception handling); `run(code, return_expr="")` — arbitrary Python `exec` inside the PyMOL process namespace, with `cmd`/`pymol`/`np` pre-imported, explicitly documented by the tool's own schema as unsandboxed: *"Anything Python can do — open files, make network calls, import modules, shell out — is in scope. The only thing standing between this tool and full remote code execution on the host is the shared-secret auth token... Treat that token like an SSH key."*
- **Inputs:** local structure files (any format PyMOL's `load` supports) or an RCSB code via `fetch`; PyMOL selection strings (its own selection-algebra language) for every operation that takes a `selection`/`mobile`/`target` argument.
- **Outputs:** typed JSON-serializable results per dedicated tool (floats for distances/RMSD, dicts/lists for `iterate`/`get_model`, strings for FASTA/chain lists); unstructured text for `do`/`run`.
- **A concrete example (from this session's own tool schema, not invented):** a self-consistency check equivalent to `us-align.md`'s workflow —
  ```
  load("designed_backbone.pdb", object_name="design")
  load("predicted_refold.pdb", object_name="refold")
  cealign(mobile="refold", target="design")
  rms(mobile="refold", target="design", fit=True)
  ```

## Compute pattern
- **Pattern:** **P6 (primary)** for every operation except `fetch`, which is **P5** (a real network call to RCSB — the taxonomy's own rule 5 applies: "egress-dependent tools are P5 even when they have a local fallback," and `load` of an already-downloaded local file is the fallback). All measurement/alignment/iteration calls are sub-second, single-structure, in-process operations against an already-loaded PyMOL session — the same scheduling class as RDKit (`rdkit.md`) and US-align (`us-align.md`). `render`/`screenshot` are the slowest single calls (image rendering, potentially seconds for high-resolution/ray-traced output) but remain single-call P6 work, never worth scheduling.
- **GPU vendor portability:** n/a for the measurement/scripting surface (CPU-bound geometry/string operations); PyMOL's OpenGL-based rendering path can use a GPU for interactive display but does not require one for the headless/batch `render`/`screenshot` calls this MCP surface exposes — no CUDA/HIP/SYCL dependency of the kind that gates the toolkit's structure-prediction models.
- **State model:** **stateful across a session** — unlike RDKit/US-align/DSSP (stateless per-call), PyMOL's MCP surface operates against a persistent, long-lived PyMOL process with a named-object session state (`load` populates it, `align`/`cealign` mutate coordinates in place unless `transform=False`, `get_names`/`get_object_list` reflect accumulated state). This is architecturally different from every other P6 tool in this toolkit and matters for agent design: **the agent must track what is currently loaded in the PyMOL session**, not assume each call is independent.
- **Data locality:** shared-FS required for `load`/`save` (local file paths passed directly to the PyMOL process, which must be able to read/write them) or streamable via `fetch` (network).
- **Staging burden:** none beyond the PyMOL installation itself.
- **Container availability:** community (PyMOL is packaged on conda-forge, `conda install -c conda-forge pymol-open-source`); the MCP plugin layer is a separate pip-installable/GitHub-cloned component, not bundled in the base PyMOL package.

## Deployment on DOE & ACCESS
**This is where the MCP-server architecture creates a genuine, non-obvious deployment gap.** The verified architecture — a plugin running *inside a live, GUI-capable PyMOL process*, listening on a local TCP port (`127.0.0.1:9877`), started manually via "Plugin → Start Listening" — is fundamentally a **desktop/workstation pattern**, not a headless-compute-node pattern. Frontier, Aurora, Polaris, and ACCESS compute nodes are headless by construction (no display server, no interactive GUI session, and typically no persistent long-lived background process a remote MCP client can dial into on a stable local port across a batch job's lifetime). This session's own connection-refused error when calling `status` with no PyMOL GUI actually running is the concrete demonstration of exactly this gap: **the MCP tool schemas are available and callable, but the underlying PyMOL process was not live** — the tools existing in the registry does not imply a reachable PyMOL session exists.
- **Two separate deployment paths follow from this, and the agent architecture needs both, for different purposes:**
  1. **Headless PyMOL scripting** (`pymol -cq script.pml`, or `import pymol; pymol.finish_launching(['pymol', '-qc'])` from Python) runs identically and without the GUI/MCP-plugin dependency on any of Frontier/Aurora/Polaris/ACCESS — this is the path for any *autonomous, in-loop* use of PyMOL's scripting/measurement capability (superposition, distance, `iterate`) during a campaign, and it is CPU-only and portable everywhere. This is not the MCP surface, but the same underlying `cmd.*` API the MCP tools wrap — an agent could call it directly as a Python library rather than through the MCP round-trip, consistent with the P6 discipline this toolkit applies elsewhere (`rdkit.md`'s "an MCP wrapper is the wrong integration point" argument).
  2. **The live MCP server** is realistically a **workstation/login-node, human-attended** deployment — a researcher (or a supervising agent with desktop/browser access, per this platform's own `claude-in-chrome`/computer-use tooling) runs PyMOL with the plugin active on their own machine or a login node with a GUI session, and an agent reaches it for interactive visualization/review, not as a component embedded inside a batch job on a compute node.
- **License gate:** the open-source PyMOL core has no license gate for either deployment path. The MCP plugin layer itself is MIT-licensed, no gate. **Incentive PyMOL** (Schrödinger's commercial variant, with additional maintenance/support and a small number of closed-source extensions) is not required for anything this brief covers — every MCP-exposed operation (align/cealign/rms/measurement/iteration/rendering) is available in the open-source core.

## Agentic surface
- **Native MCP: yes — verified live in this session.** 24 tools registered under `mcp__pymol__*`; schemas fetched and inspected directly (not inferred from documentation). Strong evidence this is (or is architecturally identical to) **Arcadia-Science/agentic-pymol** (MIT, `github.com/Arcadia-Science/agentic-pymol`) based on matching default port (9877) and matching shared-secret-token security model, though the exact tool-name-for-name match against that specific repo's source was not independently confirmed via a full code read in this pass (only its own README-level description) — record as **native MCP, high-confidence identified, not byte-for-byte source-verified**, per the template's downgrade rule for unverifiable claims.
- **Parameters worth exposing for autonomous variation:**

| Parameter | Type | Sane range | Default | Trade-off |
|---|---|---|---|---|
| `align`/`cealign` choice | enum | n/a | n/a | `align` (sequence-aware) is faster and appropriate above ~30% sequence identity; `cealign` (sequence-independent, CE algorithm) is the right choice for structurally-similar-but-sequence-divergent comparisons — see the self-consistency recommendation below |
| `align` `method` | enum {`align`,`super`} | n/a | `align` | `super` (structure-aware refinement) is more robust than sequence-aware `align` for distant homologs where the initial sequence alignment is unreliable |
| `rms` `fit` | bool | n/a | `False` | `fit=True` (`cmd.rms`, iterative outlier rejection) discards poorly-aligned atoms from the RMSD calculation — appropriate for "core fold" RMSD, inappropriate if the agent needs the true, unfiltered whole-selection RMSD |
| `rms`/`iterate` `state` | int | -1 (current), 0 (all), 1..N | -1 | `state=0` yields N_atoms × N_states rows for a multi-model/NMR-ensemble/trajectory object — a real cost multiplier the agent should not trigger unintentionally |
| `iterate` `properties` list | list[str] | n/a | n/a | Larger property lists cost more serialization per row but avoid a second round-trip; capped at 200,000 rows regardless |

- **Parameters that must NOT be agent-varied:** `transform=True` on `align`/`cealign` **mutates the loaded object's coordinates in place** — an agent computing a comparison metric for logging/scoring purposes and not intending to permanently reorient a session object must pass `transform=False`, or it will silently corrupt the session state for any subsequent operation against that object. `do`/`run` must never be exposed to an untrusted or loosely-scoped autonomous loop without the same review discipline applied to any arbitrary-code-execution surface — both tools' own schemas flag this explicitly (`do` swallows PyMOL errors as text rather than raising; `run` is unsandboxed Python `exec` with full filesystem/network/subprocess reach, gated only by a bearer-token-style shared secret).

## Failure modes & what the agent must check
- **Loud failure:** malformed/unreadable structure file on `load` (non-zero/exception); a `get_distance`/`align`/`cealign` call against a selection that matches zero atoms typically raises or returns an explicit empty/error result rather than a plausible-looking wrong number — PyMOL's selection algebra is generally strict about this.
- **Silent bad output — `do` swallowing errors:** by the tool's own documented behavior, `cmd.do` does **not** raise on a PyMOL-internal error; a malformed command silently returns failure text in the string result rather than raising a catchable exception. **Check:** any agent code calling `do` must parse the returned string for PyMOL's own error-message patterns rather than assuming a returned-without-exception call succeeded — this is a structurally different failure contract from every dedicated tool in the same server.
- **Silent bad output — stale/wrong session-state assumptions:** because the MCP surface is stateful (unlike every other P6 tool cataloged in this toolkit), an agent that issues a measurement against an object name it believes is loaded, but which was never loaded or was overwritten by a prior call with a colliding `object_name`, gets whatever selection PyMOL's algebra resolves to — which may be an unintended object, not an error. **Check:** call `get_object_list`/`get_names` to confirm the expected object set before any measurement the agent intends to trust, rather than assuming session state persisted exactly as expected across a long tool-call sequence.
- **Silent bad output — unintended coordinate mutation:** `transform=True` (the `align`/`cealign` default) permanently moves the `mobile` object; a subsequent operation against that same object (a second alignment, a distance measurement) now operates on already-reoriented coordinates, which can silently compound into a wrong result several calls downstream with no single call appearing wrong in isolation. **Check:** default to `transform=False` for any comparison whose only purpose is to produce a metric, and reserve `transform=True` for the specific case where the agent (or a human reviewer via `render`) actually wants the reoriented structure.

## Cost per unit of work
- **Single measurement/alignment call** (`get_distance`, `align`, `cealign`, `rms`, `iterate` on a typical single-domain protein): sub-second to low-single-digit seconds, dominated by PyMOL's own structural-superposition algorithm cost, roughly comparable to a single US-align invocation.
- **`fetch`:** network-latency-bound (RCSB round trip), seconds, P5 cost profile — no local compute cost beyond the download and parse.
- **`render`/`screenshot`:** seconds, higher for ray-traced/high-resolution output; still single-call, never worth scheduling.
- **Resource shape:** single CPU core per call; no GPU requirement for any operation this brief covers.
- **Checkpointable:** n/a for individual calls (fast, atomic in effect if not in mechanism); the PyMOL **session itself** is the state an agent must consider "checkpointing" in the sense of tracking which objects are loaded — there is no PyMOL-native session-save/restore exposed by this MCP tool set beyond `get_view`/`set_view` (camera state only, not full session serialization).

## Verdict
**Recommended, not Core, with a clear split by use case.** For the **self-consistency metric** specifically (the RMSD/TM-score check that closes the loop on every generative design step, per `us-align.md`), **prefer US-align/TM-align over PyMOL's `align`/`cealign`/`rms`.** Three reasons: (1) US-align's TM-score is length-normalized and field-calibrated (TM-score ≥ 0.5 = "same fold" is a citable, widely-used threshold — `us-align.md`), whereas PyMOL's `rms`/`cealign` return RMSD without a comparably standardized normalized score in this MCP surface; (2) US-align is stateless/CPU-trivial and requires no persistent process, matching this toolkit's P6 discipline exactly, while PyMOL's MCP path requires a live, stateful, GUI-attached process with the headless-deployment gap documented above — a real operational cost for something that needs to run unattended inside thousands of campaign iterations; (3) US-align has zero platform/licensing friction on every DOE/ACCESS target, while PyMOL's MCP path is realistically workstation/login-node-bound. **Where PyMOL genuinely earns a place is different from where US-align does:** ad hoc catalytic-geometry distance checks (`get_distance` for a designed active site's key atom-atom distances — a measurement US-align does not provide at all), atom-property inspection (`iterate`) during interactive debugging of a specific candidate, and — the one role nothing else in this toolkit covers — **human-in-the-loop visualization and campaign reporting** via `render`/`screenshot` for a reviewer who needs to actually look at a structure, not just read a score. Recommend: **headless PyMOL scripting (direct `cmd.*`/Python API, not the MCP path) as a supplementary in-loop geometry-measurement utility; the live MCP server as a human-facing review tool, not an autonomous-campaign component.**
